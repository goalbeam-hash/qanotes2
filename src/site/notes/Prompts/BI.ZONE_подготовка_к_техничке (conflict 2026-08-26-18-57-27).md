# A. pytest — самые вероятные вопросы

Это ядро этапа. Здесь надо отвечать без пауз.

### A1. «Что такое фикстура и зачем она нужна?»

> Фикстура — это подготовка состояния для теста и его уборка после. Тест не должен сам создавать себе окружение: он должен получить готовое. В pytest фикстура объявляется декоратором и запрашивается тестом по имени аргумента — это инъекция зависимости, а не глобальные переменные.
>
> Всё, что до `yield`, — setup; всё, что после, — teardown, и он выполнится даже если тест упал.

```python
import pytest

@pytest.fixture
def api_client():
    client = ApiClient(base_url=settings.BASE_URL)
    client.login(settings.USER, settings.PASSWORD)
    yield client                # тест работает здесь
    client.logout()             # выполнится даже при падении теста

def test_license_is_active(api_client):
    resp = api_client.get("/licenses/42")
    assert resp.status_code == 200
    assert resp.json()["status"] == "active"
```

### A2. «Какие бывают scope у фикстур?»

Пять: `function` (по умолчанию), `class`, `module`, `package`, `session`.

> Правило простое: скоуп выбирается по цене создания и по риску связности. Дорогое и неизменяемое — `session`: браузер, соединение с БД, токен. Всё, что тест меняет, — `function`, иначе тесты начнут влиять друг на друга и порядок запуска станет значимым, а это худший вид флака.

```python
@pytest.fixture(scope="session")
def browser():
    with sync_playwright() as p:
        browser = p.chromium.launch()
        yield browser
        browser.close()

@pytest.fixture(scope="function")
def page(browser):
    context = browser.new_context()   # чистое состояние на каждый тест
    page = context.new_page()
    yield page
    context.close()
```

**Вероятный добор:** «а если session-фикстура, а тесты бегут в несколько процессов через xdist?» → Каждый воркер — отдельный процесс, поэтому session-фикстура отработает **в каждом воркере**. Если внутри создаётся общий ресурс (запись в БД, файл), будет конфликт — нужен либо изолированный ресурс на воркер, либо блокировка.

### A3. «Что такое conftest.py?»

> Файл, куда выносятся фикстуры и хуки, общие для тестов в этой директории и всех вложенных. Импортировать его не надо — pytest подхватывает автоматически. Иерархия работает: корневой `conftest.py` для всего проекта, вложенный — для своего каталога, ближний переопределяет дальний.
>
> Практически: в корневом держу конфигурацию сред, клиентов, авторизацию; в `tests/ui/conftest.py` — браузерные фикстуры; в `tests/api/conftest.py` — HTTP-клиент.

### A4. «Как параметризовать тест?»

```python
@pytest.mark.parametrize(
    "days_left, expected_status",
    [
        (30, "active"),
        (1, "active"),
        (0, "expired"),      # граница
        (-1, "expired"),
    ],
    ids=["month", "last_day", "expiry_day", "after_expiry"],
)
def test_license_status(days_left, expected_status):
    assert license_status(days_left) == expected_status
```

> `ids` даю всегда — иначе в отчёте будет `test_license_status[0-active]`, и при падении непонятно, какой кейс упал.

**Вероятный добор:** «а если два декоратора parametrize?» → Получается декартово произведение: 3 значения × 2 значения = 6 тестов. Удобно для матриц «версия продукта × тип лицензии», но легко получить взрыв количества — тогда лучше явный список кортежей.

**Ещё добор:** «чем parametrize отличается от цикла внутри теста?» → Цикл — это один тест: упал первый кейс, остальные не проверились, и в отчёте одна строка. Parametrize — N независимых тестов, каждый со своим результатом. Для диагностики это принципиально.

### A5. «Что такое маркеры и зачем?»

```python
# pytest.ini
[pytest]
markers =
    smoke: критичные сценарии, гоняем на каждый пуш
    regress: полный набор, по расписанию
    slow: долгие тесты
```

```python
@pytest.mark.smoke
def test_login(): ...
```

Запуск: `pytest -m smoke`, `pytest -m "regress and not slow"`.

> Маркеры — это то, как строится гейт. Быстрый набор на пуш, полный ночью. Регистрирую их в `pytest.ini`, иначе pytest ругается на неизвестный маркер, и опечатка `@pytest.mark.smok` тихо создаст новый маркер вместо ошибки.

Плюс встроенные: `@pytest.mark.skip(reason=...)`, `@pytest.mark.skipif(sys.platform == "win32", reason=...)`, `@pytest.mark.xfail` — известный баг, тест ожидаемо красный, но не ломает прогон.

**Важная позиция, которую могут проверить:** `xfail` — для известного заведённого дефекта; `skip` — когда сценарий неприменим в этой среде. Использовать их, чтобы прятать нестабильные тесты, — нельзя, это скрытие проблемы.

### A6. «Как проверить, что код бросает исключение?»

```python
def test_invalid_license_key_raises():
    with pytest.raises(ValidationError) as exc_info:
        parse_license_key("not-a-key")
    assert "invalid format" in str(exc_info.value)
```

> Проверяю не только факт исключения, но и его содержание — иначе тест пройдёт на любой ошибке, в том числе на опечатке в коде теста.

### A7. «Какие встроенные фикстуры знаешь?»

- `tmp_path` — временная директория на тест, сама убирается.
- `monkeypatch` — подменить переменную окружения, атрибут, функцию на время теста.
- `caplog` — перехват логов, проверить, что нужное записалось.
- `capsys` — перехват stdout/stderr.
- `request` — метаданные о тесте, доступ к параметрам фикстуры.

```python
def test_uses_staging_url(monkeypatch):
    monkeypatch.setenv("BASE_URL", "https://staging.example.com")
    assert build_client().base_url == "https://staging.example.com"
```

### A8. «Как запускаешь тесты?»

```bash

pytest -k "license and not expired"  # отбор по имени
pytest --lf                          # только упавшие в прошлый раз
pytest -x                            # остановиться на первом падении
pytest -vv --alluredir=allure-results
```

# B. Python для автоматизатора

Спрашивать будут не язык целиком, а то, что реально всплывает в тестах.

**Точно надо уметь без запинки:**

```python
# comprehension'ы
active = [i for i in installations if i["status"] == "active"]
by_id = {i["id"]: i for i in installations}

# распаковка
first, *rest = versions
a, b = b, a

# f-строки
f"/api/v1/installations/{inst_id}/licenses"

# работа с JSON
import json
data = json.loads(raw)
payload = json.dumps({"version": "2.1.0"})

# классы для POM
class BasePage:
    def __init__(self, page):
        self.page = page

class LoginPage(BasePage):
    def login(self, user, password): ...
```

**Вопросы, которые любят задавать:**

- **«Изменяемые и неизменяемые типы?»** → Неизменяемые: `int`, `str`, `tuple`, `frozenset`. Изменяемые: `list`, `dict`, `set`. Практическое следствие для тестов — **мутабельный аргумент по умолчанию**:

```python
def add_tag(tags=[]):     # ❌ список создаётся ОДИН раз при определении функции
    tags.append("x")
    return tags

def add_tag(tags=None):   # ✅
    tags = tags or []
```

Это классическая ловушка, её любят на собесах.

- **«Разница между `is` и `==`?»** → `==` сравнивает значения, `is` — идентичность объекта. В ассертах почти всегда `==`; `is` уместен для `None`, `True`, `False`.

- **«Что такое декоратор?»** → Функция, которая оборачивает другую функцию, не меняя её код. Весь pytest на них построен — `@pytest.fixture`, `@pytest.mark.parametrize`. Уметь прочитать и объяснить достаточно; писать свой на собесе просят редко, но простой ретрай-декоратор стоит уметь набросать (см. блок G).

- **«Контекстный менеджер?»** → `with` — гарантирует освобождение ресурса. `with open(...)`, `with pytest.raises(...)`, `with sync_playwright()`.

- **«Как работать с API?»**

```python
import requests

resp = requests.get(url, headers={"Authorization": f"Bearer {token}"}, timeout=10)
resp.raise_for_status()
data = resp.json()
```

`requests.Session()` — когда нужны общие заголовки и переиспользование соединения.

# C. Тест-дизайн

Назван прямым текстом, значит будет обязательно. Отвечать **не определением из учебника, а применением к их продукту**.

### C1. Классы эквивалентности и граничные значения

> Эквивалентность — разбиваю входные данные на группы, где система ведёт себя одинаково, и беру по одному представителю из каждой. Границы — проверяю ровно на краях групп, потому что именно там живут ошибки на единицу.
>
> На вашем продукте: срок действия лицензии. Классы — активная, истекает сегодня, истекла, отозвана, отсутствует. Границы — последняя секунда перед истечением, момент истечения, первая секунда после. Отдельно — часовой пояс: истечение считается по UTC или по локали инсталляции? Это классический источник расхождения на сутки.

### C2. Таблица решений

> Когда результат зависит от комбинации нескольких условий, я строю таблицу: условия по строкам, комбинации по столбцам, ожидаемый результат внизу. Она сразу показывает, какие комбинации не описаны в требованиях.
>
> Пример для вас: применять ли обновление? Условия — лицензия активна, версия совместима, инсталляция онлайн, есть свободное место. Восемь-шестнадцать комбинаций, и часть из них наверняка в требованиях не расписана — вот это и есть находка на этапе анализа, ещё до кода.

### C3. Тестирование состояний и переходов

Это **ваш главный козырь на их домене** — доставка обновления по сути конечный автомат:

```
pending → downloading → downloaded → applying → applied
              ↓              ↓           ↓
           failed         failed      failed → rolled_back
```

> Проверяю не только счастливый путь, но и запрещённые переходы: можно ли из `failed` попасть в `applied` минуя `applying`; что происходит при обрыве связи в каждом состоянии; идемпотентен ли повтор — если команда «применить обновление» пришла дважды, применилось один раз или два.

### C4. Попарное тестирование (pairwise)

> Когда параметров много, полный перебор невозможен: пять параметров по четыре значения — это 1024 комбинации. Pairwise покрывает все пары значений примерно двумя десятками комбинаций, исходя из того, что большинство дефектов вызывается взаимодействием двух факторов, а не пяти.
>
> У вас это прямо просится: версия продукта × ОС инсталляции × тип лицензии × канал обновления.

### C5. Приоритизация: с чего начинать покрытие

> Не «покрыть всё», а по риску: вероятность отказа × цена отказа. Сначала critical path — то, что ломает продукт для клиента. Для вашего сервиса это, скорее всего, три вещи: инсталляция не получила обновление, лицензия неверно определена как истёкшая, телеметрия потеряна или задублирована. Дальше happy path остальных сценариев, потом расширение по impact-анализу.

### C6. Что ещё могут спросить

- **Smoke vs регресс:** smoke — узкий набор «система вообще работает», минуты, на каждый пуш; регресс — широкий, ловит деградацию, по расписанию.
- **Impact-анализ:** от изменения строю карту затронутых областей — какие модули, какие интеграции, какие сценарии, — и гоняю целевой регресс вместо полного.
- **Позитивные и негативные тесты:** негативных обычно больше, и они важнее — счастливый путь разработчик проверит сам.
- **Как оценить достаточность покрытия:** не процентом строк, а покрытием рисков и критичных путей. Покрытие кода — вспомогательная метрика, 90% покрытых строк с плохими ассертами хуже, чем 40% с хорошими.

# D. UI-автоматизация

### D1. «Как строишь Page Object?»

```python
class BasePage:
    def __init__(self, page):
        self.page = page

    def open(self, path=""):
        self.page.goto(f"{settings.BASE_URL}{path}")


class InstallationsPage(BasePage):
    SEARCH = "[data-testid='installations-search']"
    ROW = "[data-testid='installation-row']"
    STATUS = "[data-testid='installation-status']"

    def search(self, query):
        self.page.fill(self.SEARCH, query)
        self.page.press(self.SEARCH, "Enter")
        return self

    def status_of(self, name):
        row = self.page.locator(self.ROW, has_text=name)
        return row.locator(self.STATUS).inner_text()
```

> Правило: в Page Object — только взаимодействие со страницей и получение данных. **Ассертов внутри Page Object нет** — они в тесте, иначе страница начинает знать про ожидания и её нельзя переиспользовать.

### D2. «Какие локаторы предпочитаешь и почему?»

> Иерархия: `data-testid` → роль и доступное имя → текст → CSS → XPath в последнюю очередь.
>
> `data-testid` я договариваюсь ставить с разработкой — это дешевле, чем ловить падения после каждого рефакторинга вёрстки. XPath по абсолютному пути — худший вариант: ломается от любой вставки div. Локаторы по видимому тексту рискуют при локализации.

Это ровно тот аргумент, который зашёл на первом этапе в СБС, — он работает.

### D3. «Как борешься с флаком?»

Сильная позиция — и её любят проверять:

> Флак — это не «тест плохой», это сигнал. Сначала я классифицирую причину:
>
> **Ожидания.** Никаких `sleep`. Ждать надо состояние, а не время: элемент видим, запрос завершён, спиннер исчез. В Playwright автоожидание встроено, в Selenium — явные ожидания через `WebDriverWait` с `expected_conditions`.
>
> **Данные.** Тесты делят одну учётку или одну запись — начинают мешать друг другу при параллели. Лечится изоляцией: свои данные на тест, создание через API, уборка после.
>
> **Среда.** Тест стартовал раньше, чем поднялась зависимость. Лечится healthcheck'ом и ожиданием готовности, а не ретраем.
>
> **Само приложение.** Иногда флак — настоящий баг: гонка, которая воспроизводится в одном случае из двадцати. Это самый ценный флак, и его нельзя гасить ретраями.
>
> Ретраи я допускаю только как временную меру с обязательной пометкой и разбором — иначе они превращают красный прогон в зелёный и скрывают деградацию.

### D4. «Playwright или Selenium?»

> В Python оба живые. Playwright даёт автоожидания, изоляцию через контексты, трассировку с записью действий — на новом проекте я бы выбрал его. Selenium — если в компании уже есть экспертиза и инфраструктура селениум-грида: тогда стоимость перехода выше выгоды.
>
> На моём прошлом проекте мы отказались от небольшого legacy на Selenide в пользу Playwright, потому что кода было мало, а автоожидания снимали основной источник флака.

**Не переобещать:** если спросят про `pytest-playwright` конкретно — сказать честно, что боевой код писали на TS-версии, а Python-биндинг знаете как API: те же `page`, `locator`, `expect`, встроенная фикстура `page`.

### D5. «Как проверять то, что не видно на UI?»

> UI-тест не должен заканчиваться на «увидел зелёную плашку». Если операция асинхронная, я проверяю результат там, где он реально появляется: статус через API, запись в БД, сообщение в очереди. UI подтверждает, что пользователю показали правду, а не что операция прошла.

# E. API, интеграции, асинхрон

### E1. Схема-валидация

> Проверять только значения полей недостаточно: если бэкенд переименует поле или сменит тип, тест на конкретное значение может остаться зелёным. Поэтому валидирую ответ по схеме — в Python это Pydantic.

```python
from pydantic import BaseModel
from datetime import datetime

class License(BaseModel):
    id: int
    status: str
    expires_at: datetime
    product: str

def test_license_schema(api_client):
    resp = api_client.get("/licenses/42")
    License.model_validate(resp.json())   # упадёт при любом расхождении контракта
```

### E2. Контрактное тестирование

> Когда сервис общается со многими продуктами, интеграционные тесты «всё вместе» дорогие и медленные. Контрактные проверяют, что потребитель и поставщик договорились о формате: потребитель описывает ожидаемый контракт, поставщик проверяется против него. Инструмент — Pact.
>
> Для вашего Security Cloud это прямо в точку: один сервис, много продуктов-потребителей разных версий. Контракты дешевле, чем поднимать всю линейку.

### E3. Идемпотентность

> Операция идемпотентна, если повтор не меняет результат. В сервисе доставки обновлений это критично: сеть ненадёжна, клиент ретраит, и «применить обновление» не должно примениться дважды.
>
> Проверяю так: отправляю два одинаковых запроса с одним ключом идемпотентности, затем проверяю инвариант — одна запись в БД, один переход состояния, статус финальный один и тот же.

### E4. Race condition

> Гонка — когда результат зависит от порядка выполнения параллельных операций, и хотя бы один порядок даёт неверный итог.
>
> Воспроизвожу в тесте так: параллельные запросы к одному ресурсу плюс инверсия порядка ответов в моке, чтобы принудительно получить «неудобный» порядок. Проверяю не выдачу, а инвариант: один ключ — одна запись, счётчик не разъехался, статус не откатился назад.

*(Это тема, на которой вы просели на финале Сбера. Формулировка выше — рабочая, проговорить вслух.)*

### E5. Eventual consistency

> В распределённой системе после записи данные появляются не мгновенно. Поэтому в тестах — не `sleep`, а polling с таймаутом: опрашиваю статус до достижения ожидаемого или до истечения бюджета времени, и падаю с внятным сообщением, если не дождался.

```python
def wait_for(condition, timeout=30, interval=1):
    deadline = time.monotonic() + timeout
    while time.monotonic() < deadline:
        result = condition()
        if result:
            return result
        time.sleep(interval)
    raise AssertionError(f"Условие не выполнилось за {timeout}с")
```

# F. Домен: обновления, телеметрия, лицензии

Это то, что отличает «кандидата с pytest» от «инженера, который уже думает про их систему». Если вы назовёте эти острые места сами — этап сделан наполовину.

### F1. Доставка обновлений

Что может пойти не так и как проверять:

| Риск | Как проверяю |
|---|---|
| Инсталляция офлайн в момент выкатки | догоняющая доставка при возвращении в сеть; обновление не потерялось |
| Обрыв на середине загрузки | докачка или чистый повтор; нет полуприменённого состояния |
| Обновление применено дважды | идемпотентность по ключу; один переход состояния |
| Несовместимая версия | обновление отклонено с внятной ошибкой, а не применено «частично» |
| Откат | после `failed` система возвращается в рабочее состояние, а не зависает |
| Массовая выкатка | сотни инсталляций одновременно — очередь не переполняется, порядок не критичен |
| Старая инсталляция, новый сервис | обратная совместимость протокола |

### F2. Лицензии

Богатейший источник граничных кейсов — и именно тут стоит показать тест-дизайн:

- Момент истечения: последняя секунда, ровно ноль, первая секунда после.
- **Часовой пояс:** истечение по UTC или по локальному времени инсталляции? Расхождение на сутки — классика.
- Лицензия отозвана, пока инсталляция работает — когда узнает и что делает.
- Оффлайн-проверка: инсталляция не может достучаться до сервиса — грейс-период или немедленная блокировка? **Это отличный вопрос им**, и он показывает, что вы думаете про поведение системы при отказе.
- Продление в момент истечения — гонка между проверкой и обновлением срока.
- Лицензия на N инсталляций: попытка активировать N+1.

### F3. Телеметрия и статистика

- Потеря части данных при обрыве — переотправка, дедупликация по идентификатору события.
- Дубликаты: одно событие пришло дважды — счётчики не должны удвоиться.
- Порядок доставки: события пришли не в том порядке, что произошли.
- Часы инсталляции разошлись с сервером — по какому времени агрегируем.
- Объём: рост числа инсталляций, разрастание хранилища.

### F4. Кейс-вопрос, который вам почти наверняка дадут

Формат «вопросы близко к боевым задачам» обычно означает что-то вроде: **«Мы раскатываем сервис на новый продукт. Как ты это будешь тестировать?»**

Каркас ответа, чтобы не поплыть, как было на задаче ДМС в Сбере:

1. **Уточняю контекст.** Что именно интегрируется: только доставка обновлений или ещё телеметрия и лицензии? Какая версия протокола у продукта? Есть ли стенд с этим продуктом?
2. **Определяю риски по цене отказа.** Самое дорогое — инсталляция клиента получила битое обновление или потеряла лицензию. Это и есть критичные пути.
3. **Раскладываю по уровням.** Контрактные проверки между сервисом и продуктом — дёшево и ловит большинство расхождений. Интеграционные на стенде с реальной инсталляцией — узкий набор, только критичные пути. UI — что оператор видит корректный статус.
4. **Проверяю не только счастливый путь.** Офлайн, обрыв, повтор, несовместимая версия, откат.
5. **Называю, чем закончится.** Набор в CI, который гоняется перед раскаткой на следующий продукт, и гейт: не прошли — не раскатываем.

**Главное отличие от провала на ДМС:** сначала уточняющие вопросы и структура, потом детали. Не начинать с перечисления тест-кейсов.

# G. Лайвкодинг — 6 типовых задач с решениями

Обещано «чуть-чуть», значит короткие задачи на 5–10 минут. Прогнать глазами и, лучше, руками.

### G1. Параметризованный тест на валидацию

**Задача:** есть функция `is_valid_license_key(key)`. Напиши тесты.

```python
import pytest

@pytest.mark.parametrize(

```

**Что говорить вслух, пока пишете:** «беру по одному представителю на класс эквивалентности, отдельно граничные — пустая строка и None, ids чтобы падение читалось».

### G2. Фикстура с подготовкой и уборкой данных

```python
@pytest.fixture
def installation(api_client):
```

**Комментарий вслух:** «данные создаю через API, а не через UI — быстрее и не зависит от вёрстки; уборка в teardown, чтобы тесты можно было гонять параллельно и повторно».

### G3. Найди ошибки в тесте

Классическая задача «вот код, что не так». Что искать:

```python
def test_update():
    driver.get("http://stand/installations")
    time.sleep(5)                                  # ❌ sleep вместо ожидания
```

### G4. Работа со структурами данных

**Задача:** из списка инсталляций собрать словарь «продукт → количество активных».

```python
def count_active_by_product(installations):
    result = {}
    for inst in installations:
        if inst["status"] != "active":
            continue
        result[inst["product"]] = result.get(inst["product"], 0) + 1
    return result
```

Вариант через стандартную библиотеку, если попросят короче:

```python
from collections import Counter

def count_active_by_product(installations):
    return Counter(i["product"] for i in installations if i["status"] == "active")
```

### G5. Ожидание асинхронного результата

**Задача:** обновление применяется асинхронно, напиши проверку.

```python
def test_update_is_applied(api_client, installation):
    api_client.post(f"/installations/{installation['id']}/updates", json={"version": "2.1.0"})

    status = wait_for(
        lambda: api_client.get(f"/installations/{installation['id']}").json()["update_status"],
        expected="applied",
        timeout=60,
    )
    assert status == "applied"


def wait_for(getter, expected, timeout=30, interval=2):
    deadline = time.monotonic() + timeout
    last = None
    while time.monotonic() < deadline:
        last = getter()
        if last == expected:
            return last
        time.sleep(interval)
    raise AssertionError(f"Ожидали '{expected}', последнее значение '{last}' за {timeout}с")
```

**Что подчеркнуть:** в сообщении об ошибке есть последнее фактическое значение — иначе при падении непонятно, застряло на `downloading` или вообще не стартовало.

### G6. Простой декоратор (если спросят)

```python
import functools, time

def retry(times=3, delay=1):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(times):
                try:
                    return func(*args, **kwargs)
                except AssertionError:
                    if attempt == times - 1:
                        raise
                    time.sleep(delay)
        return wrapper
    return decorator
```

И сразу добавить позицию: «в тестах я такое не применяю — ретрай прячет флак. Это уместно для нестабильной инфраструктуры, не для проверок».

# H. Процесс, CI, флак

- **«Как встроишь тесты в CI?»** → На пуш — линт и smoke, минуты. Полный набор по расписанию ночью, с параллелизмом и сборкой общего отчёта. Гейт: упавшие тесты роняют пайплайн, мержа нет. Артефакты — трейсы, скриншоты, логи — прикладываются к прогону, чтобы падение диагностировалось без локального воспроизведения.
- **«Что делать, если тестов нет, а надо начать?»** → Критичные пути, 10–15 сценариев. Неделя-полторы на каркас, две-три недели на покрытие критичных путей. В пределах месяца у команды есть работающий гейт. Дальше расширение по impact-анализу.
- **«Как понять, что автоматизация приносит пользу?»** → Время приёмки перед релизом, количество дефектов, доехавших до прода, доля падений, оказавшихся настоящими багами. Не количество тестов.
- **«Разработчик просит не заводить баг»** → Завожу всегда. Обсуждать можно severity и priority, сроки, попадёт ли в этот релиз — но не факт существования дефекта. Незаведённый баг — это потерянная информация для всей команды.

*(Последний пункт — ровно тот, на котором вы просели в Сбере. Здесь линию держать твёрдо, ИБ-компания на этом чувствительна вдвойне.)*

# S. Домен безопасности: вопросы, ответы, что доизучить

Отдельная глава, потому что это ИБ-вендор, и разговор почти наверняка свернёт в безопасность. Здесь важно не изображать пентестера, а показать **тестировщика, который понимает риски своей системы и умеет проверять их функционально**.

## S.0. Рамка — как позиционироваться

Скажите один раз, если тема зайдёт глубоко:

> «Я не AppSec-инженер и не пентестер — не буду делать вид. Мой уровень: понимаю модель угроз системы, умею превратить требование безопасности в проверяемый тест-кейс и знаю, где в таком продукте живут типовые дыры. Пентест и анализ кода — это отдельная роль, я с ней работаю рядом, а не вместо неё.»

**Почему это выигрывает:** в ИБ-компании люди мгновенно чувствуют, когда кандидат жонглирует терминами. Честная граница плюс предметное рассуждение внутри неё ценится намного выше, чем попытка звучать экспертом.

---

## S.1. Аутентификация и авторизация

**Вопрос: «Чем отличается аутентификация от авторизации?»**

> Аутентификация — кто ты (проверка личности). Авторизация — что тебе можно (проверка прав). Тестируются они по-разному: первая — сценариями входа, вторая — матрицей «роль × действие × объект».

**Вопрос: «Как тестируешь авторизацию?»**

> Строю матрицу доступа: роли по строкам, действия по столбцам, в ячейках — разрешено или запрещено. Дальше автоматизирую негативную часть, она важнее позитивной: под каждой ролью пытаюсь сделать то, что ей не положено, и жду 403, а не 200 и не 500.
>
> Отдельно — **проверка на уровне API, а не UI**. Скрытая в интерфейсе кнопка ничего не значит: запрос можно отправить напрямую. Поэтому тест на права всегда идёт в обход UI.

**Ключевой класс дефектов, который надо назвать самому — IDOR / BOLA**

> Broken Object Level Authorization — когда сервер проверяет, что ты залогинен, но не проверяет, что объект твой. Классика: меняю `/installations/42` на `/installations/43` и получаю чужую инсталляцию.
>
> Для вашего продукта это риск номер один: сервис общий для всех клиентов, и изоляция арендаторов — то, на чём его надо ломать в первую очередь. Проверяю так: два клиента, у каждого свои инсталляции и лицензии; под токеном первого перебираю идентификаторы второго — по всем эндпоинтам, включая те, что кажутся безобидными: статистика, логи, статусы обновлений.

**Что доизучить:** JWT (структура header/payload/signature, срок жизни, refresh, что подпись проверяется на сервере, а payload не секретен), OAuth2/OIDC на уровне ролей и потоков, mTLS (взаимная аутентификация — вероятна в связке «сервис ↔ инсталляция»), RBAC против ABAC, API-ключи и их ротация.

**Тест-кейсы на токены, которые стоит перечислить:**

- истёкший токен → 401;
- токен другого клиента → 403 на чужие объекты;
- токен с изменённым payload и старой подписью → отвергнут;
- отсутствующий заголовок `Authorization` → 401, а не 500;
- отозванный токен продолжает работать до истечения — это вопрос к архитектуре, а не баг по умолчанию, но его надо задать;
- права понижены во время активной сессии — когда применится.

---

## S.2. Целостность обновлений — сердце их продукта

Это самая релевантная тема: сервис доставляет обновления на инсталляции клиентов. Подмена обновления = компрометация всех клиентов сразу. Именно так работают supply chain-атаки.

**Что должно проверяться:**

| Риск | Проверка |
|---|---|
| Подмена пакета в пути | цифровая подпись пакета проверяется перед применением; битый/подменённый — отклонён |
| Несовпадение хеша | контрольная сумма (SHA-256) сверяется после загрузки |
| Откат на уязвимую версию | downgrade-атака: попытка подсунуть старую версию с известной уязвимостью должна отклоняться |
| Просроченный/отозванный сертификат подписи | обновление не применяется, инсталляция сообщает внятную причину |
| Replay: повтор старого валидного пакета | защита по версии/nonce/времени |
| Path traversal при распаковке | архив с путями вида `../../etc/passwd` не должен вылезти за пределы каталога (zip slip) |
| Частичное применение | обрыв на середине не оставляет систему в полурабочем состоянии; есть откат |

**Как это произнести:**

> Для сервиса доставки обновлений главный риск не функциональный, а целостности: если можно подменить пакет, скомпрометированы все инсталляции разом. Поэтому я бы проверял цепочку доверия целиком — подпись, хеш, срок действия сертификата, отзыв, — и отдельно негативные сценарии: битый пакет, чужая подпись, старая версия, обрыв на середине.

**Что доизучить:** асимметричная подпись в двух предложениях (приватный ключ подписывает, публичный проверяет), хеш-функции и зачем SHA-256 против MD5, что такое цепочка сертификатов и отзыв (CRL/OCSP), понятие supply chain attack на примере — этого достаточно для AQA-уровня.

---

## S.3. Многотенантность и изоляция данных

> Сервис общий для всех продуктов и, вероятно, для многих клиентов. Значит основной класс дефектов — утечка между арендаторами: телеметрия одного клиента видна другому, лицензия применилась не к той инсталляции, статистика агрегировалась по всем.
>
> Тестирую всегда минимум двумя клиентами. Один клиент — принципиально нетестируемая конфигурация: с ним изоляция не проверяется вообще.

**Кейсы:** список сущностей под клиентом A не содержит объектов клиента B; прямой запрос по id чужого объекта; поиск и фильтры не протекают; агрегаты и счётчики считаются в границах клиента; экспорт/выгрузка; сообщения об ошибках не раскрывают существование чужих объектов (`404` вместо `403` там, где сам факт существования — уже утечка).

## S.4. Секреты и чувствительные данные

**Вопрос: «Как хранишь креды для тестов?»** — почти наверняка спросят в ИБ-компании.

> Никогда в репозитории. Тестовые учётки и токены — в переменных окружения, в CI — в защищённых переменных или в vault. В коде только имена переменных. В логах и отчётах секреты маскируются: Allure с приложенным заголовком `Authorization` — это утечка, особенно если отчёты публикуются.
>
> Отдельно — что тестовые данные не должны содержать реальных персональных данных. Для ИБ-вендора это ещё и вопрос комплаенса.

**Что проверять в самом продукте:** секреты не попадают в логи и телеметрию; ключи лицензий маскируются в интерфейсе и выгрузках; сообщения об ошибках не раскрывают внутренние пути, версии и стектрейсы; заголовки ответов не выдают версию сервера.

**Что доизучить:** практики работы с секретами в GitLab CI (masked/protected variables), базово Vault, secret scanning в пайплайне.

---

## S.5. Транспорт и сеть

> TLS для всего трафика, включая внутренний между сервисом и инсталляциями. Что проверяю: соединение по HTTP отклоняется или редиректится, самоподписанный сертификат не принимается по умолчанию, истёкший сертификат приводит к отказу, а не к тихому продолжению.
>
> Отдельный вопрос — **ротация сертификатов**: инсталляции живут годами, сертификаты — нет. Что происходит с инсталляцией, у которой сертификат протух, — она отваливается молча или сообщает.

**Что доизучить:** TLS-рукопожатие на пальцах, mTLS, certificate pinning и его цена при ротации, HSTS, зачем нужны заголовки безопасности (`Content-Security-Policy`, `X-Content-Type-Options`, `Strict-Transport-Security`) — для UI-части это может всплыть.

## S.6. Отказоустойчивость с точки зрения безопасности

**Вопрос, который стоит задать им самому** — он показывает уровень:

> «Что делает инсталляция, если сервис лицензирования недоступен: fail-open — продолжает работать, или fail-close — блокируется? И есть ли грейс-период?»

> Это архитектурный компромисс между доступностью и безопасностью, и он должен быть осознанным решением, а не побочным эффектом. Для средства защиты fail-close может означать, что клиент остался без защиты; fail-open — что лицензионный контроль обходится отключением сети. Что бы ни выбрали, это тестируемое поведение: обрыв связи, длительный оффлайн, возврат в сеть.

## S.7. Типовые уязвимости — минимум, который надо знать

Не углубляться, но уметь назвать и сказать, как проверяется:

| Класс | Суть | Как проверяю |
|---|---|---|
| **BOLA / IDOR** | доступ к чужому объекту по id | перебор id под чужим токеном |
| **Broken authentication** | слабая или обходимая аутентификация | истёкший/поддельный/отсутствующий токен |
| **Injection** (SQL, command) | недоверенный ввод попадает в запрос или команду | спецсимволы в полях, кавычки, `;`, шаблоны |
| **Path traversal** | выход за пределы каталога | `../` в именах файлов и путях распаковки |
| **SSRF** | сервис ходит по URL, который задал пользователь | подстановка внутренних адресов |
| **Mass assignment** | клиент передаёт поле, которое менять не должен | добавить `"role": "admin"` в payload |
| **Rate limiting / DoS** | нет ограничения частоты | шквал запросов, крупные payload |
| **Раскрытие информации** | стектрейсы, версии, внутренние пути в ответах | негативные сценарии и 500-е |

> Формулировка вслух: «Я не провожу пентест, но эти классы держу в голове при проектировании негативных тестов. Часть из них — обычные функциональные проверки, просто со злым умыслом: тот же mass assignment ловится тестом на то, что сервер игнорирует лишние поля.»

**Что доизучить:** OWASP Top 10 и, важнее для их продукта, **OWASP API Security Top 10** — прочитать список и уметь назвать три-четыре пункта с примером.

## S.8. Безопасность в процессе и в CI

**Вопрос: «Как безопасность встраивается в пайплайн?»**

> Три вещи, которые обычно есть: **SCA** — проверка зависимостей на известные уязвимости, **SAST** — статический анализ кода, **secret scanning** — поиск случайно закоммиченных ключей. Динамический анализ (**DAST**) — реже и на отдельном стенде.
>
> Моя зона как автотестировщика — не запускать сканеры, а следить, чтобы их результаты были гейтом, а не отчётом, который никто не читает, и чтобы найденное превращалось в задачи. Плюс мои собственные негативные тесты на права и изоляцию — они закрывают то, что сканер не увидит, потому что это логика, а не паттерн в коде.

**Про свои же зависимости:** тестовый проект — тоже код, и его зависимости тоже могут содержать уязвимости. Упомянуть, что это учитываете, — небольшой, но заметный плюс в ИБ-компании.

**Что доизучить:** что такое CVE и CVSS в двух словах; чем SAST отличается от DAST и SCA; как это выглядит в GitLab CI (там встроенные шаблоны сканирования).

## S.9. Российская специфика ИБ-вендора

Пригодится скорее на финале с руководителем, но лучше знать:

- **ФСТЭК** — сертификация средств защиты; у BI.ZONE такие сертификаты есть. Практическое следствие для разработки: сертифицированная версия фиксируется, изменения в неё вносятся под контролем, а это влияет на процесс релизов и на регресс.
- **ГОСТ Р 56939** — требования к безопасной разработке ПО: статический анализ, управление уязвимостями, реагирование.
- **КИИ** и **152-ФЗ** — если продукты применяются на значимых объектах и обрабатывают персональные данные, к контурам и логированию предъявляются отдельные требования.

Не углубляться. Достаточно уметь сказать: «понимаю, что сертификация фиксирует версию и накладывает требования на процесс изменений — это влияет на то, как строится регресс и релизный гейт».

## S.10. Уточняющие вопросы по домену — задать на этапе

Отобраны так, чтобы каждый показывал понимание системы, а не был праздным любопытством.

**Про архитектуру и доверие:**

1. Как инсталляция аутентифицируется в Security Cloud — сертификат, mTLS, токен? И как это ротируется, учитывая, что инсталляции живут долго?
2. Обновления подписываются? Проверка подписи и хеша на стороне инсталляции или на стороне сервиса?
3. Что происходит, если инсталляция долго офлайн — догоняющая доставка или пропуск обновлений?

**Про изоляцию:**

4. Данные разных клиентов изолированы на уровне БД, схемы или логики приложения? От этого зависит, где я ищу дыры в изоляции.
5. Есть ли сейчас тесты на межклиентскую изоляцию, или это зона, которую надо закрывать?

**Про поведение при отказе:**

6. Лицензионная проверка — fail-open или fail-close? Есть грейс-период?
7. Если сервис недоступен, инсталляция копит телеметрию локально или теряет?

**Про процесс:**

8. Есть ли требования сертификации, которые влияют на регресс перед релизом?
9. Кто сейчас проверяет безопасность: отдельная команда AppSec, сканеры в пайплайне, внешний пентест?
10. Как устроен тестовый контур — можно ли поднять несколько инсталляций разных версий и разных клиентов?

Пятый и девятый — особенно хорошие: они одновременно разведка и заявка на зону ответственности.

# J. Шпаргалка на один экран

**Перед звонком проговорить вслух:**

- Рамку про стек (блок 0) — один раз, в начале.
- Фикстура, scope, conftest, parametrize, маркеры — определения без пауз.
- Три критичных пути их продукта: обновление не доехало, лицензия неверно определена, телеметрия потеряна/задублирована.
- Три риска безопасности: доступ к чужой инсталляции по id, подмена обновления, утечка между клиентами.
- «Завожу баг всегда, обсуждаю severity» — не сдвигаться под нажимом.
- «Я не пентестер, но риск умею превратить в тест-кейс» — рамка по безопасности, один раз.

**Держать под рукой (второй экран, не читать с него в камеру):**

```python
@pytest.fixture(scope="function")          # function class module package session
def x():
    setup(); yield value; teardown()

@pytest.mark.parametrize("a,b", [(1,2)], ids=["case"])
@pytest.mark.smoke
with pytest.raises(ValueError) as e: ...
pytest -m smoke -n auto -k "name" --lf -x
```

**Правила поведения:**

- Отвечать структурой: сначала принцип в одну фразу, потом пример. Не начинать с разгона («это комплексный вопрос, на самом деле…»).
- На задаче — **сначала уточняющие вопросы**, потом решение. Молчаливое ныряние в детали было ошибкой на ДМС.
- Не знаете — сказать «не сталкивался, но рассуждаю так…» и рассуждать. Это оценивается выше, чем угадывание.
- Цифры вместо абстракций: «4 часа → 40 минут», «10–15 критичных сценариев», «месяц до рабочего гейта».
- Короткие предложения. Убрать «в этом есть моя осведомлённость», «глаз наточен», «вайб».
