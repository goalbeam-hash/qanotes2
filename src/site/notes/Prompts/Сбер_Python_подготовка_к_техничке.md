# 1. Что показали два последних этапа — честный диагноз

Сводка провалов из двух разборов. Смотреть на неё неприятно, но именно она задаёт план.

**Три причины, и ни одна не про способности.**

**Иллюзия переносимости.** «Подходы одни и те же, разный синтаксис» — это правда про архитектуру и неправда про руки. Архитектуру можно объяснить словами, код надо написать. На лайвкодинге объяснять нечего.

**Подготовка шла в сторону силы.** Kafka, Docker, 2PC, контрактное тестирование, тест-дизайн — темы, где вы и так сильны. Слабое место при этом не трогалось.

**Не была поставлена честная рамка.** Одна фраза в начале ничего не стоит и полностью меняет восприятие: «переходил бы со стека, синтаксис может подтормаживать» звучит нормально. А «был коммерческий опыт на Python» плюс запинка на двоеточии через двадцать минут — это удар по доверию, который распространяется на весь остальной рассказ.

**Вывод:** этот этап решается не знаниями об автоматизации, а пальцами на клавиатуре. Приоритет — Python и pytest руками, всё остальное потом.

## 4.2. FizzBuzz — выучить наизусть

Именно эта задача была в BI.ZONE и заняла 13 минут. Написать без раздумий за минуту.

```python
def fizzbuzz(n):
    for i in range(1, n + 1):
        if i % 15 == 0:
            print("FizzBuzz")
        elif i % 3 == 0:
            print("Fizz")
        elif i % 5 == 0:
            print("Buzz")
        else:
            print(i)
```

**Ключевая мысль, которую надо проговорить вслух:** проверка на 15 идёт **первой**, потому что `if/elif` останавливается на первом истинном условии — если начать с тройки, кратные пятнадцати никогда не дойдут до `FizzBuzz`.

Вариант через накопление строки — если попросят «а по-другому»:

```python
def fizzbuzz(n):
    for i in range(1, n + 1):
        s = ""
        if i % 3 == 0:
            s += "Fizz"
        if i % 5 == 0:
            s += "Buzz"
        print(s or i)      # пустая строка ложна → печатается число
```

Вариант, возвращающий список, — если попросят покрыть тестами:

```python
def fizzbuzz(n):
    result = []
    for i in range(1, n + 1):
        if i % 15 == 0:
            result.append("FizzBuzz")
        elif i % 3 == 0:
            result.append("Fizz")
        elif i % 5 == 0:
            result.append("Buzz")
        else:
            result.append(str(i))
    return result
```

Третий вариант лучше первого для собеседования тестировщика: функция, которая **возвращает** значение, тестируется, а функция, которая печатает, — нет. Это стоит сказать вслух: «сделаю так, чтобы её можно было покрыть тестом».

# 5. 🔴 Зона 2. pytest — механика, а не слова

Здесь были два прямых провала: `scope` не назван и **pytest не собрал написанный тест**. Оба — про механику инструмента.

## 5.1. Почему pytest может не найти тест 🔴

Именно на этом сломался второй лайвкодинг в BI.ZONE. Правила сборки:

- файл называется `test_*.py` или `*_test.py`;
- функция называется `test_*`;
- класс называется `Test*` **и не имеет `__init__`**;
- запуск из корня проекта, файл в зоне поиска (`testpaths` или текущий каталог).

```python
# файл: test_ip.py
def test_ip_returns_current_address():     # имя начинается с test_
    ...
```

Диагностика, если «ничего не запустилось»:

```bash
pytest --collect-only -q       # что вообще собралось
pytest -v                      # по строке на тест
```

Если вывод пустой — проблема в именовании или в каталоге, а не в коде теста.

## 5.2. Фикстуры

```python
import pytest

@pytest.fixture
def api_client():
    client = ApiClient(base_url=BASE_URL)     # setup
    client.login(USER, PASSWORD)
    yield client                               # тест работает здесь
    client.logout()                            # teardown, выполнится даже при падении


def test_something(api_client):                # запрос по имени аргумента
    assert api_client.get("/health").status_code == 200
```

**Три отличия фикстуры от обычной функции** — назвать все три, в BI.ZONE не были названы:

1. **Внедрение зависимости** — тест не вызывает фикстуру, а объявляет её в аргументах, pytest подставляет сам.
2. **Жизненный цикл** — setup до теста, teardown после `yield`, гарантированно.
3. **Кэширование по scope** — в пределах скоупа результат вычисляется один раз и переиспользуется.

## 5.3. Scope — критический вопрос 🔴🔴

**Пять значений: `function` (по умолчанию), `class`, `module`, `package`, `session`.**

```python
@pytest.fixture(scope="session")
def browser():
    ...          # создаётся один раз на весь прогон

@pytest.fixture(scope="function")
def page(browser):
    ...          # создаётся заново на каждый тест
```

**Вопрос «что прописать, чтобы пользователь создавался один раз за прогон»** → ответ одним словом: **`scope="session"`**.

**Вопрос «зачем ещё нужен session scope»** → **не «для параллелизма»**. Правильно:

> Чтобы дорогую и неизменяемую подготовку не повторять на каждом тесте: авторизационный токен, запуск браузера, соединение с БД, чтение конфигурации. Экономия времени прогона.
>
> И сразу оговорюсь про параллель: при `pytest-xdist` каждый воркер — отдельный процесс, поэтому session-фикстура отработает **в каждом воркере**, а не один раз на весь прогон. Если внутри создаётся общий ресурс — пользователь с фиксированным именем, запись в БД, — будет конфликт. Поэтому всё, что тест меняет, я держу в `function`, а в `session` кладу только то, что не мутирует.

Этот абзац превращает провальный вопрос в демонстрацию понимания. Проговорить вслух пять раз.

## 5.4. conftest.py

# 6. 🔴 Зона 3. SQL

Вчера здесь было два промаха: `JOIN` вместо `UNION` и `UNION ALL` как «декартово множество».

## 6.1. Таблица, которую надо знать намертво

| Конструкция | Что делает | Сколько строк |
|---|---|---|
| `UNION` | склеивает по вертикали, **убирает** дубликаты | ≤ N + M |
| `UNION ALL` | склеивает по вертикали, **оставляет** дубликаты | ровно N + M |
| `JOIN` | соединяет по **горизонтали** по условию | зависит от условия |
| `CROSS JOIN` | **декартово произведение** | N × M |

**Ограничения `UNION`:** одинаковое число колонок; совместимые типы в соответствующих позициях; имена колонок берутся из первого запроса; `ORDER BY` применяется ко всему результату и пишется один раз в конце.

**`UNION` против `UNION ALL` по производительности:** обычный `UNION` вынужден убирать дубликаты, значит сортировка или хеширование по всему набору — это дороже. Если дубликаты не мешают, брать `UNION ALL`.

## 6.2. JOIN'ы

- `INNER JOIN` — только строки, где нашлось совпадение с обеих сторон.
- `LEFT JOIN` — все строки левой, из правой `NULL`, если совпадения нет.
- `RIGHT JOIN` — зеркально.
- `FULL JOIN` — всё с обеих сторон.

**Практический приём для тестировщика** — поиск осиротевших записей:

```sql
SELECT a.id
FROM applications a
LEFT JOIN payment_schedules p ON p.application_id = a.id
WHERE p.id IS NULL;          -- заявка есть, графика платежей нет
```

## 6.3. Группировка

`WHERE` фильтрует строки **до** группировки, `HAVING` — группы **после**.

```sql
SELECT idempotency_key, COUNT(*) AS cnt
FROM applications
WHERE created_at >= now() - interval '1 hour'
GROUP BY idempotency_key
HAVING COUNT(*) > 1;
```

Это ваш готовый ответ на «приведите пример задачи с SQL» — проверка идемпотентности, дубли ловятся только в данных.

## 6.4. Индексы (в требованиях указано прямо)

> Индекс ускоряет выборку и замедляет вставку и обновление, потому что его надо поддерживать. Составной индекс работает слева направо: индекс по `(a, b)` помогает запросу по `a` и по `a, b`, но не по одному `b`. Функция над колонкой в `WHERE` обычно убивает использование индекса. План смотрю через `EXPLAIN ANALYZE`.

## 6.5. Прочее, что могут спросить

- **Оконные функции** — базово: `ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...)`, полезно для «взять последнюю запись по каждому клиенту».
- **`COALESCE`** — вернуть первое не-`NULL`.
- **`NULL` в сравнениях** — `NULL = NULL` даёт не `TRUE`, а `NULL`; проверять через `IS NULL`.
- **Транзакции и ACID** — атомарность, согласованность, изолированность, долговечность. Проговорить без запинки: на финале СБС это уже проваливалось («AST»).

# 7. 🔴 Зона 4. ООП и модификаторы доступа

## 7.1. Четыре принципа — назвать сразу, без подсказок

> **Инкапсуляция, наследование, полиморфизм, абстракция.** И если полезно, покажу, как каждый работает в архитектуре автотестов — у меня весь фреймворк на них построен.

Вторая фраза переводит вопрос в вашу сильную зону.

**Раскрытие, по 20 секунд на принцип, каждый с примером:**

> **Инкапсуляция** — данные и работающие с ними методы в одном объекте, внутреннее устройство спрятано за понятным интерфейсом. У меня это Page Object: локаторы и способ взаимодействия внутри класса, наружу — методы вроде `search(query)`. Поменялась вёрстка — правится один класс, тесты не трогаются.
>
> **Наследование** — класс перенимает поведение родителя и расширяет его. `BasePage` держит общее: драйвер, `open`, ожидание загрузки.
>
> **Полиморфизм** — один вызов работает по-разному в зависимости от типа объекта. Тест вызывает `open()`, не зная, какая это страница. В Python это чаще duck typing: важно не какого ты класса, а есть ли у тебя нужный метод.
>
> **Абстракция** — выделение существенного: описываем **что** объект делает, не раскрывая **как**. Базовый класс задаёт контракт, наследники реализуют.

🔴 **Не путать:**
- **SOLID, DRY, KISS** — это принципы **проектирования**, применяются внутри ООП, но принципами ООП не являются.
- **Магические методы** — это dunder-методы `__init__`, `__repr__`, `__eq__`, к принципам отношения не имеют.
- **Абстракция ≠ инкапсуляция.** Инкапсуляция прячет внутренности конкретного объекта; абстракция задаёт общую модель — что вообще должен уметь такой тип. Вчера они были объяснены одинаково.

## 7.2. Наследование против композиции — почти обязательный добор

> Наследование — когда объект **является** частным случаем родителя. Композиция — когда он **содержит** другой объект. Страница является частным случаем базовой страницы → наследование. Шапка, меню, таблица — не являются страницей, они в ней лежат → композиция, отдельные классы-компоненты как поля.

## 7.3. Модификаторы доступа в Python

> В Python нет настоящих модификаторов доступа, как в Java. Есть соглашение и один механизм языка.
>
> **Одно подчёркивание** — `_method` — соглашение «внутреннее, снаружи не использовать». Технически ничего не запрещает; единственное следствие — не попадает в `from module import *`.
>
> **Два подчёркивания** — `__method` — это **name mangling**: интерпретатор переименовывает атрибут, внутри класса `Base` имя становится `_Base__method`. Снаружи по исходному имени не обратиться, будет `AttributeError`, но зная новое — доступ есть. Задача не защита от злого умысла, а защита от случайного переопределения в наследнике.
>
> **Без подчёркиваний** — публичный интерфейс.
>
> Философия языка: «мы все взрослые люди» — вместо запретов соглашения. Ещё из смежного: `@property` даёт атрибут только на чтение.

Ключевое слово, которое надо произнести — **name mangling**. Без него ответ звучит как «что-то там с подчёркиваниями».

## 7.4. SOLID — если спросят следом

- **S** — единственная ответственность: Page Object описывает взаимодействие, ассерты живут в тесте.
- **O** — открыт для расширения, закрыт для изменения: новая страница добавляется наследником.
- **L** — подстановка Лисков: наследник работает везде, где ожидается родитель.
- **I** — разделение интерфейсов: несколько узких контрактов лучше одного толстого.
- **D** — зависимость от абстракций: тест зависит от интерфейса клиента, а не от реализации на `requests` — так его можно подменить моком.

# 9. Под их продукт: что тестировать в казначействе

Продукт — анализ больших данных и макроэкономическое прогнозирование для банков, бирж и консалтинга. Главная особенность: **тестируются не кнопки, а расчёты**. Если вы придёте с этой мыслью самостоятельно, это выделит вас среди кандидатов, которые пришли по названию стека.

## Что здесь по-настоящему сложно

**Как доказать, что число посчитано правильно.** У аналитического продукта нет очевидного оракула: правильный ответ не «кнопка стала зелёной», а «прогноз совпал с эталоном в пределах допуска». Отсюда вопросы: есть ли эталонные наборы данных, кто их владелец, какое расхождение считается допустимым, что делать с плавающей точкой.

**Воспроизводимость.** Один и тот же вход должен давать один и тот же выход. Если в расчёте есть случайность или зависимость от времени — тест обязан её зафиксировать.

**Границы и вырожденные данные.** Пустой ряд, один элемент, пропуски в середине, отрицательные значения, выбросы, деление на ноль в производных показателях.

**Версионирование данных и моделей.** Пересчитали историю — старые прогнозы изменились задним числом? Это баг или ожидаемое поведение?

**Объём.** Большие массивы означают, что часть дефектов проявляется только на объёме: переполнение, потеря точности, деградация времени ответа.

## Готовые вопросы к ним по домену

1. Чем сверяются результаты расчётов — есть эталонные наборы данных, или проверка идёт по бизнес-правилам?
2. Какое расхождение в числах считается допустимым? Есть ли формализованный допуск?
3. Расчёт детерминирован — один и тот же вход всегда даёт один и тот же выход?
4. Как устроены тестовые данные: срез с боевых или синтетика?
5. Что происходит с уже выданными прогнозами при пересчёте исторических данных?

Первый и третий — самые сильные. Они показывают, что вы поняли природу продукта.

## Ваши карты, которые сюда ложатся

- **Контрактное тестирование** — Артём назвал его прямо как фокус.
- **Схема-валидация** ответов через Pydantic.
- **Идемпотентность и дедупликация** — при потоковой загрузке данных это живой риск.

def wait_for(getter, expected, timeout=30, interval=2):

    last = None
    while time.monotonic() < deadline:
        last = getter()

# 13. Правила поведения на этапе

**Честная рамка — в первые три минуты.** Один раз, спокойно, не повторять.

**Не заявлять коммерческий опыт на Python**, если не готовы это подтвердить кодом через двадцать минут. Расхождение слов и демонстрации бьёт сильнее, чем само незнание, — это дословный вывод из вчерашнего разбора.

**Думать вслух.** Тишина дольше пятнадцати секунд читается как «потерялся». Даже если не знаете — рассуждайте: «мне нужен способ быстро проверить, видел ли я уже этот id…»

**На задаче — сначала уточняющие вопросы, потом код.** Тридцать секунд вопросов дешевле пяти минут кода не в ту сторону.

**Подсказку принимать сразу и благодарно.** В прошлый раз это единственное, что удержало оценку: не спорил, не оправдывался, доводил до конца. Сохранить.

**После проваленного вопроса — возвращаться на свою территорию.** «Здесь плаваю, честно. Зато по этой же теме могу показать…»

**Цифры вместо абстракций.** «4 часа → 40 минут», «покрытие критичных зон 80–85%», «10–15 критичных сценариев».

**Ответ держать в минуту.** Шестиминутный монолог на первый вопрос вчера съел половину времени Артёма, и часть его вопросов просто не была задана.

**Не поднимать тему ИИ первым.** В BI.ZONE это разбилось о «у нас запрещено использовать сторонние модели». Артём сказал, что в Сбере отношение положительное, — но пусть эту тему начнут они.

**Про деньги.** Если всплывёт — не подтверждать 220 автоматически. Механика переоткрытия в `Сбер_Python_AQA_разбор_HR_техскрининга.md`, Приложение 3. Коротко: цифра называлась до того, как стал понятен объём; теперь ясно, что покрытия нет, два тестировщика только переучиваются, и речь о построении с нуля — ориентир 270–290 на руки.
