# pytest — запуск и все ключи: что значит каждая буква

Разбор командной строки pytest по буквам: откуда взялся ключ, что он делает, как читается мнемонически и когда применяется в реальном прогоне. Отдельно — синтаксис выражений в `-k` и `-m`, параллель через xdist, коды выхода и вынос параметров в конфиг.

> Часть ключей — не самого pytest, а плагинов. Это важно на собесе: `-n` появляется только с `pytest-xdist`, `--alluredir` — с `allure-pytest`. Если сказать «стандартный ключ pytest» про `-n`, это заметят.

## 1. Разбор пяти команд из шпаргалки

### `pytest -m smoke -n auto`

| Часть | Расшифровка |
|---|---|
| `-m` | **m**arker — отбор по маркерам. Запустить только те тесты, что помечены `@pytest.mark.smoke` |
| `smoke` | имя маркера (может быть выражением, см. раздел 2) |
| `-n` | **n**umber of processes — количество параллельных процессов. **Ключ плагина `pytest-xdist`** |
| `auto` | вместо числа — «столько процессов, сколько логических ядер у машины» |

Читается: «прогнать только smoke-набор, распараллелив по числу ядер».

### `pytest -k "license and not expired"`

| Часть | Расшифровка |
|---|---|
| `-k` | **k**eyword — отбор по подстроке в имени теста, класса или файла |
| `"license and not expired"` | выражение: имя содержит `license`, но не содержит `expired` |

Важно: `-k` работает **по именам**, а не по маркерам. `test_license_expired_returns_error` под это выражение не попадёт, а `test_license_active` — попадёт.

### `pytest --lf`

| Часть | Расшифровка |
|---|---|
| `--lf` | **l**ast **f**ailed — запустить только те тесты, что упали в прошлый прогон |

Читает кеш из `.pytest_cache`. Основной рабочий режим при починке: чинишь → `--lf` → снова, пока не станет зелёным, вместо прогона всего набора.

Родственники: `--ff` (**f**ailed **f**irst — упавшие первыми, потом остальные) и `--nf` (**n**ew **f**irst — новые файлы первыми).

### `pytest -x`

| Часть | Расшифровка |
|---|---|
| `-x` | e**x**it on first failure — остановиться на первом падении |

Полная форма — `--exitfirst`. Обобщение: `--maxfail=3` — остановиться после трёх падений.

Смысл: если развалилась среда, нет смысла гонять 400 тестов, чтобы получить 400 одинаковых красных.

### `pytest -vv --alluredir=allure-results`

| Часть | Расшифровка |
|---|---|
| `-v` | **v**erbose — подробный вывод: имя каждого теста и его результат отдельной строкой вместо точек |
| `-vv` | ещё подробнее: не обрезает длинные значения в ассертах и в параметрах |
| `--alluredir` | **allure dir**ectory — куда складывать сырые результаты для Allure. **Ключ плагина `allure-pytest`** |

Без `-v` вывод компактный: `....F..s.` — точка это пройденный тест, `F` — упавший, `s` — пропущенный, `E` — ошибка, `x` — xfail.

## 2. Отбор тестов: `-k` и `-m`

Два разных механизма, их часто путают — и это ровно тот вопрос, который могут задать.

| | `-k` | `-m` |
|---|---|---|
| По чему отбирает | **по именам** (тест, класс, модуль) | **по маркерам** `@pytest.mark.*` |
| Откуда берётся | подстрока в идентификаторе | явная разметка в коде |
| Мнемоника | **k**eyword | **m**arker |

### Синтаксис выражений (общий для обоих)

Поддерживаются `and`, `or`, `not` и скобки:

```bash
pytest -k "license"                          # имя содержит license
pytest -k "license or update"                # любое из двух
pytest -k "license and not expired"          # первое есть, второго нет
pytest -k "(license or update) and not slow"
pytest -k "TestLicense and active"           # класс + имя метода
pytest -k "not test_slow_import"             # исключить один тест
```

```bash
pytest -m smoke                              # только smoke
pytest -m "regress and not slow"             # регресс без долгих
pytest -m "smoke or critical"
pytest -m "not ui"                           # всё, кроме UI
```

Подстрока в `-k` регистронезависима и ищется в полном идентификаторе — то есть `-k api` зацепит и файл `test_api.py`, и класс `TestApiClient`, и метод `test_check_api_version`.

### Маркеры: объявление и строгость

```ini
# pytest.ini
[pytest]
markers =
    smoke: критичные сценарии, гоняем на каждый пуш
    regress: полный набор, по расписанию
    ui: тесты через браузер
    slow: дольше 30 секунд
addopts = --strict-markers
```

`--strict-markers` — незарегистрированный маркер становится **ошибкой**, а не предупреждением. Без него опечатка `@pytest.mark.smok` тихо создаёт новый маркер, тест выпадает из `-m smoke`, и никто этого не замечает. На собесе это хороший показатель зрелости — упомянуть стоит.

### Точечный запуск без выражений

```bash
pytest tests/api/test_licenses.py                          # один файл
pytest tests/api/test_licenses.py::test_expired            # один тест
pytest tests/api/test_licenses.py::TestLicense::test_active  # метод класса
pytest "tests/test_x.py::test_status[expiry_day]"          # один параметр из parametrize
pytest tests/api/                                          # каталог
```

Последняя форма — то, ради чего в `parametrize` задаются `ids`: можно перезапустить ровно упавший кейс.

## 3. Полная таблица ключей

### Отбор и объём прогона

| Ключ | Полная форма | Расшифровка буквы | Что делает |
|---|---|---|---|
| `-k EXPR` | — | **k**eyword | отбор по имени |
| `-m EXPR` | — | **m**arker | отбор по маркерам |
| `-x` | `--exitfirst` | e**x**it | остановиться на первом падении |
| — | `--maxfail=N` | — | остановиться после N падений |
| — | `--deselect PATH` | — | исключить конкретный тест/файл |
| — | `--ignore=PATH` | — | не собирать этот путь вовсе |
| — | `--collect-only` / `--co` | **co**llect | показать, что было бы запущено, но не запускать |

`--co` — очень полезная привычка: перед долгим прогоном посмотреть, что вообще попало в выборку. Особенно после правки `-k`.

### Вывод

| Ключ | Полная форма | Расшифровка | Что делает |
|---|---|---|---|
| `-v` | `--verbose` | **v**erbose | по строке на тест |
| `-vv` | — | — | не обрезать длинные значения |
| `-q` | `--quiet` | **q**uiet | компактнее обычного; `-qq` ещё компактнее |
| `-s` | `--capture=no` | **s**how output | не перехватывать `print` и stdout |
| `-l` | `--showlocals` | **l**ocals | показать локальные переменные в трейсбеке |
| `-r CHARS` | — | **r**eport | сводка в конце по типам результатов |
| — | `--tb=STYLE` | **t**race**b**ack | формат трейсбека |
| — | `--durations=N` | — | N самых долгих тестов |

**Буквы для `-r`:**

| Буква | Что показывает |
|---|---|
| `f` | failed |
| `E` | error |
| `s` | skipped |
| `x` | xfailed — ожидаемо упал |
| `X` | xpassed — ожидали падения, а он прошёл |
| `p` | passed |
| `P` | passed с выводом |
| `a` | всё, кроме passed |
| `A` | вообще всё |
| `N` | ничего |

Практично: `-ra` в CI — короткая сводка всех проблем в конце лога, не листая вверх.

### Конфигурация

| Ключ | Что делает |
|---|---|
| `-c FILE` | взять конкретный конфиг вместо найденного автоматически |
| `-o KEY=VALUE` / `--override-ini` | переопределить одну опцию ini прямо из командной строки |
| `-p NAME` | подключить плагин |
| `-p no:NAME` | **отключить** плагин, например `-p no:cacheprovider` |
| `--rootdir=PATH` | явно задать корень проекта |
| `-W FILTER` | как обрабатывать предупреждения, например `-W error::DeprecationWarning` |

## 4. Параллельный запуск: pytest-xdist

Ставится отдельно: `pip install pytest-xdist`.

| Ключ | Значение |
|---|---|
| `-n 4` | четыре процесса |
| `-n auto` | по числу логических ядер |
| `-n logical` | то же, явно про логические ядра |
| `--dist load` | по умолчанию: тесты раздаются воркерам по мере освобождения |
| `--dist loadscope` | тесты одного класса/модуля идут на один воркер |
| `--dist loadfile` | тесты одного файла — на один воркер |
| `--dist loadgroup` | группировка по метке `@pytest.mark.xdist_group` |
| `--dist no` | без распределения |
| `--max-worker-restart=N` | сколько раз перезапускать упавший воркер |

**Что здесь важно понимать (и что спросят):**

Каждый воркер — **отдельный процесс**. Из этого следует три вещи:

1. Фикстуры со `scope="session"` выполнятся **в каждом воркере**, а не один раз на прогон. Если внутри создаётся общий ресурс — запись в БД, файл, пользователь — будет конфликт.
2. Тесты, зависящие от порядка или делящие состояние, при параллели начнут падать. Это не «xdist сломал тесты» — это он вскрыл существующую связность.
3. `--dist loadscope` — компромисс, когда изолировать данные полностью дорого: тесты одного класса гарантированно идут подряд на одном воркере.

Формулировка для собеса:

> Параллель — это не ключ `-n`, это свойство тестов. Если данные изолированы и нет общего состояния, `-n auto` просто ускоряет прогон. Если нет — параллель вскроет связность, и чинить надо изоляцию, а не откатываться в один поток.

## 5. Управление выводом и трейсбеком

### `--tb` — формат трейсбека

| Значение | Что даёт |
|---|---|
| `--tb=auto` | по умолчанию: длинный для первого и последнего падения, короткий для остальных |
| `--tb=long` | полный трейсбек для всех |
| `--tb=short` | одна строка на кадр стека — самый практичный в CI |
| `--tb=line` | одна строка на всё падение |
| `--tb=native` | стандартный питоновский формат |
| `--tb=no` | без трейсбека вообще |

В CI обычно `--tb=short`: лог остаётся читаемым, а детали смотрятся в артефактах.

### `-s` — почему он нужен

По умолчанию pytest перехватывает вывод и показывает его только у упавших тестов. `-s` отключает перехват — всё летит в консоль сразу. Нужен, когда отлаживаешь `print`-ами или когда библиотека пишет что-то важное в stdout.

Полная форма — `--capture=no`. Есть ещё `--capture=sys` и `--capture=fd` — разные уровни перехвата.

<a id="6"></a>

## 6. Кеш прошлого прогона

pytest хранит результаты в каталоге `.pytest_cache`.

| Ключ | Расшифровка | Что делает |
|---|---|---|
| `--lf` | **l**ast **f**ailed | только упавшие в прошлый раз |
| `--ff` | **f**ailed **f**irst | упавшие первыми, потом все остальные |
| `--nf` | **n**ew **f**irst | новые файлы первыми |
| `--cache-clear` | — | очистить кеш перед прогоном |
| `--lfnf=all\|none` | last failed — no failures | что делать, если падений не было: гнать всё или ничего |

Рабочий цикл при починке: `pytest` → упало пять → правка → `pytest --lf` → упало два → правка → `pytest --lf` → зелено → полный прогон для проверки.

В CI `--lf` не используют: там каждый прогон должен быть полным и независимым от кеша.

<a id="7"></a>

## 7. Отладка

| Ключ | Что делает |
|---|---|
| `--pdb` | при падении бросить в интерактивный отладчик прямо в точке ошибки |
| `--trace` | войти в отладчик в начале каждого теста |
| `--setup-show` | показать порядок создания и разрушения фикстур |
| `--setup-plan` | показать план фикстур, ничего не выполняя |
| `-l` | локальные переменные в трейсбеке |

`--setup-show` — лучший инструмент, когда непонятно, почему фикстура не отработала или отработала не в том порядке. На собесе упомянуть уместно: показывает, что вы понимаете, как устроен жизненный цикл фикстур, а не просто пишете декораторы.

<a id="8"></a>

## 8. Отчёты

| Ключ | Плагин | Что делает |
|---|---|---|
| `--alluredir=DIR` | `allure-pytest` | сырые результаты для Allure |
| `--clean-alluredir` | `allure-pytest` | очистить каталог перед прогоном |
| `--junitxml=FILE` | встроен | отчёт в формате JUnit XML — понимают GitLab CI, Jenkins, TeamCity |
| `--html=FILE` | `pytest-html` | самодостаточный HTML-отчёт |
| `--cov=PKG --cov-report=html` | `pytest-cov` | покрытие кода |

Генерация HTML из Allure — отдельный шаг, уже вне pytest:

```bash
pytest --alluredir=allure-results --clean-alluredir
allure generate allure-results -o allure-report --clean
```

<a id="9"></a>

## 9. Коды выхода

Это то, на чём держится гейт в CI: пайплайн смотрит на код возврата.

| Код | Значение |
|---|---|
| `0` | все тесты прошли |
| `1` | часть тестов упала |
| `2` | прогон прерван пользователем |
| `3` | внутренняя ошибка |
| `4` | ошибка в аргументах командной строки |
| `5` | **не собрано ни одного теста** |

Пятый — самый коварный. Опечатались в `-k` или `-m`, тестов не нашлось, прогон «не упал» — а покрытия не было. Поэтому в CI полезно явно ловить код 5 и считать его ошибкой:

```yaml
script:
  - pytest -m smoke --tb=short -ra
  - if [ $? -eq 5 ]; then echo "Не собрано ни одного теста"; exit 1; fi
```

## 10. Вынос параметров в конфиг

Всё, что вы гоняете постоянно, не надо каждый раз писать руками — это выносится в `addopts`.

```ini
# pytest.ini
[pytest]
testpaths = tests
python_files = test_*.py
python_classes = Test*
python_functions = test_*

addopts =
    -ra
    --strict-markers
    --tb=short
    --alluredir=allure-results

markers =
    smoke: критичные сценарии
    regress: полный набор
    ui: браузерные тесты
    slow: дольше 30 секунд
```

Теперь `pytest -m smoke` уже включает в себя сводку, строгие маркеры, короткий трейсбек и allure-каталог.

То же самое можно держать в `pyproject.toml`:

```toml
[tool.pytest.ini_options]
addopts = "-ra --strict-markers --tb=short"
testpaths = ["tests"]
markers = ["smoke: критичные сценарии", "regress: полный набор"]
```

Разовое переопределение без правки файла:

```bash
pytest -o addopts="" -k license      # отключить addopts на один запуск
```

<a id="11"></a>

## 11. Готовые команды под задачи

```bash
# Быстрый гейт на пуш: smoke, параллельно, падаем на первой ошибке
pytest -m smoke -n auto -x --tb=short -ra

# Ночной полный регресс с отчётом
pytest -m "regress and not slow" -n auto --alluredir=allure-results --clean-alluredir -ra

# Починка: только то, что упало
pytest --lf -vv -l

# Отладка одного теста с выводом print
pytest tests/api/test_licenses.py::test_expired -s -vv --tb=long

# Один параметр из parametrize
pytest "tests/api/test_licenses.py::test_status[expiry_day]" -vv

# Посмотреть выборку, ничего не запуская
pytest -m "smoke and not ui" --co -q

# Найти самые медленные тесты
pytest --durations=10

# Разобраться с порядком фикстур
pytest tests/api/test_licenses.py --setup-show

# Прогон без параллели, если подозрение на связность тестов
pytest -m regress -p no:randomly --tb=short
```

Если на собесе спросят про ключ, которого не помните, — честнее сказать «не помню наизусть, смотрю в `pytest --help`» и объяснить, что этот ключ должен делать. Знание, что существует `--setup-show` и зачем он, ценится выше, чем зубрёжка двадцати флагов.
