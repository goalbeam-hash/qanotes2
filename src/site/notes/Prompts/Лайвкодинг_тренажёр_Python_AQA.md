# Протокол: как мыслить и говорить

Главная ошибка на лайвкодинге — молча нырнуть в код. Интервьюер видит курсор и тишину и не понимает, вы думаете или потерялись. Второй по частоте промах — наоборот, сразу писать «красиво», усложняя и путаясь.

Рабочая последовательность — пять шагов. Она же спасает, когда задача незнакомая.

### Шаг 1. Повторить задачу своими словами (15 секунд)

> «Правильно понимаю: на входе список инсталляций, каждая — словарь с продуктом и статусом; на выходе нужно посчитать активные по продуктам?»

Зачем: ловит недопонимание до того, как вы напишете тридцать строк не того. И сразу показывает, что вы слушаете, а не решаете задачу из головы.

### Шаг 2. Уточнить вход, выход и крайние случаи (30 секунд)

Три вопроса, которые уместны почти всегда:

- **Что на входе гарантированно, а что нет?** Может ли список быть пустым, могут ли поля отсутствовать, могут ли быть `None`?
- **Что делать с плохими данными** — падать, пропускать, вернуть значение по умолчанию?
- **Какой объём данных?** Десятки или миллионы — от этого зависит, важна ли сложность.

Это не тянет время, это часть решения. И это ровно то, чего не хватило вам на задаче ДМС в Сбере.

### Шаг 3. Назвать подход вслух до кода (15 секунд)

> «Пойду в лоб: один проход по списку, накапливаю в словарь. Сложность линейная, память — по числу уникальных продуктов. Если хватит, так и оставлю.»

Зачем: если подход неверный, вас поправят сейчас, а не через пять минут кода. И интервьюер видит, что вы оцениваете стоимость, а не пишете наугад.

### Шаг 4. Написать простое рабочее решение

Не оптимизировать заранее. Не выпендриваться однострочниками. Рабочий цикл лучше сломанного comprehension'а.

Комментировать по ходу короткими фразами: «здесь пропускаю неактивные», «тут защищаюсь от отсутствующего ключа».

### Шаг 5. Самому проверить на крайних случаях (30 секунд)

Не ждать вопроса «а если пусто?». Проговорить самому:

> «Проверю на границах: пустой список — вернётся пустой словарь, это ок. Отсутствующий ключ `product` — сейчас упадёт с `KeyError`; если данные могут быть неполными, добавлю `.get`. Дубликаты не мешают, они как раз и считаются.»

Этот шаг стоит копейки, а впечатление меняет сильно: вы не просто написали код, вы его протестировали — что, вообще-то, ваша профессия.

# Уровень 1. Разминка

3–5 минут на задачу. Проверяют, что вы вообще пишете на Python без запинки.

---

## 1.1. Уникальные значения с сохранением порядка

**Условие:** из списка id инсталляций убрать дубликаты, порядок сохранить.

**Что уточнить:** «Порядок важен? Если нет — можно просто `set`, это одна строка. Если важен — нужен проход с запоминанием виденного.»

**Ход мысли вслух:**

> Наивно: для каждого элемента проверять, есть ли он уже в результате. Но `in` по списку — линейный поиск, и на большом входе получится квадрат. Поэтому держу отдельное множество для проверки: `in` по множеству — константа. Память чуть больше, время линейное.

**Решение:**

```python
def unique_ordered(items):
    seen = set()
    result = []
    for item in items:
        if item not in seen:
            seen.add(item)
            result.append(item)
    return result
```

**Чем добьют:**

- *«А если элементы — словари?»* → Словарь нехешируемый, в `set` не положить. Нужен ключ: `seen.add(item["id"])`, либо `frozenset(item.items())`, если сравнивать целиком.
- *«Можно короче?»* → `list(dict.fromkeys(items))` — работает, потому что с Python 3.7 словарь хранит порядок вставки. Но сказать стоит так: «есть короткая форма, я её знаю, однако на собесе явный цикл читаемее — если хотите, перепишу».

---

## 1.2. Группировка по ключу

**Условие:** список инсталляций, вернуть словарь «продукт → список имён».

**Ход мысли вслух:**

> Один проход, накапливаю в словарь списков. Чтобы не проверять наличие ключа на каждой итерации, беру `defaultdict(list)` — он создаёт пустой список сам.

**Решение:**

```python
from collections import defaultdict

def group_by_product(installations):
    result = defaultdict(list)
    for inst in installations:
        result[inst["product"]].append(inst["name"])
    return dict(result)
```

**Чем добьют:**

- *«Зачем `dict(result)` в конце?»* → Чтобы наружу ушёл обычный словарь. У `defaultdict` есть неприятное свойство: обращение к несуществующему ключу молча создаёт запись. В тестовом коде это маскирует ошибки — проверили `result["typo"]`, получили пустой список вместо `KeyError`.
- *«А если ключа `product` может не быть?»* → `inst.get("product", "unknown")`, и это решение надо согласовать: тихо складывать в «unknown» или падать — зависит от того, дефект это или норма.

---

## 1.3. Найти дубликаты

**Условие:** телеметрия прислала события, найти id, которые встретились больше одного раза.

**Ход мысли вслух:**

> Задача на подсчёт, значит `Counter`. Считаю вхождения, потом фильтрую те, где больше одного. Один проход на подсчёт, один на фильтр — обе линейные.

**Решение:**

```python
from collections import Counter

def find_duplicates(events):
    counts = Counter(e["id"] for e in events)
    return [event_id for event_id, n in counts.items() if n > 1]
```

**Связка с доменом — сказать обязательно:**

> Это прямо проверка дедупликации телеметрии: событие пришло дважды из-за ретрая, и счётчики не должны удвоиться. У вас, судя по продукту, такой риск реальный.

---

## 1.4. Развернуть вложенную структуру

**Условие:** есть список клиентов, у каждого список инсталляций. Собрать плоский список всех инсталляций.

**Решение:**

```python
def flatten_installations(clients):
    return [
        inst
        for client in clients
        for inst in client.get("installations", [])
    ]
```

**Ход мысли вслух:**

> Вложенный comprehension читается в том же порядке, что вложенные циклы: сначала внешний, потом внутренний. `.get` с пустым списком по умолчанию — защита от клиента без инсталляций, чтобы не ловить `KeyError` на первом же кривом элементе.

---

## 1.5. Инвертировать словарь

**Условие:** есть `{installation_id: product}`, нужно `{product: [installation_id, ...]}`.

**Решение:**

```python
from collections import defaultdict

def invert(mapping):
    result = defaultdict(list)
    for key, value in mapping.items():
        result[value].append(key)
    return dict(result)
```

**Чем добьют:** *«А если значения уникальны — можно проще?»* → `{v: k for k, v in mapping.items()}`, но только если гарантирована уникальность; иначе последнее значение молча затрёт предыдущие. Проговорить это — плюс: вы видите риск потери данных.

# Уровень 2. Структуры данных и логика

5–10 минут. Здесь уже смотрят на выбор структуры и на аккуратность.

## 2.1. Первый неповторяющийся элемент

**Условие:** из последовательности вернуть первый элемент, который встречается ровно один раз.

**Ход мысли вслух:**

> В лоб — для каждого элемента считать вхождения во всей последовательности: квадрат. Лучше два прохода: первый считает частоты, второй идёт по исходному порядку и возвращает первый с частотой один. Два линейных прохода — всё ещё линейно.

**Решение:**

```python
from collections import Counter

def first_unique(items):
    counts = Counter(items)
    for item in items:
        if counts[item] == 1:
            return item
    return None
```

**Чем добьют:** *«Почему второй проход по `items`, а не по `counts`?»* → Потому что нужен **первый по исходному порядку**. Словарь хранит порядок вставки, так что и по `counts` сработало бы — но по `items` намерение читается яснее, а это важнее экономии.

---

## 2.2. Слияние двух источников истины

**Условие:** данные об инсталляциях приходят из двух систем. У каждой записи есть `id` и `updated_at`. Собрать один список, где при конфликте выигрывает более свежая запись.

**Что уточнить — это половина оценки:**

> Три вопроса. Первый: `updated_at` в одном формате и в одной таймзоне? Второй: что если время совпало — какой источник приоритетнее? Третий: записи, которые есть только в одном источнике, попадают в результат или это ошибка?

**Ход мысли вслух:**

> Складываю в словарь по id. Иду по обоим спискам и кладу запись, только если её ещё нет или она свежее уже лежащей. Один проход по каждому источнику, поиск по id константный.

**Решение:**

```python
def merge_sources(primary, secondary):
    merged = {}
    for record in [*primary, *secondary]:
        existing = merged.get(record["id"])
        if existing is None or record["updated_at"] > existing["updated_at"]:
            merged[record["id"]] = record
    return list(merged.values())
```

**Чем добьют:**

- *«Время строкой сравнивается корректно?»* → Только если это ISO 8601 с одинаковым форматом и таймзоной: там лексикографический порядок совпадает с хронологическим. Надёжнее распарсить в `datetime`. Это стоит сказать самому.
- *«Равное время?»* → Сейчас побеждает первый попавшийся, то есть `primary`, потому что условие строгое `>`. Это осознанное решение, и его надо озвучить, а не оставить случайностью.

Это ровно та задача про два источника истины, которая была на финале в Сбере. Здесь есть шанс закрыть её как следует.

## 2.3. Топ-N по значению

**Условие:** посчитать, у какого продукта больше всего инсталляций, вернуть топ-3.

**Решение:**

```python
from collections import Counter

def top_products(installations, n=3):
    return Counter(i["product"] for i in installations).most_common(n)
```

**Ход мысли вслух:** > `Counter` уже умеет `most_common` — не буду писать сортировку руками. Возвращает список пар «значение, количество», отсортированный по убыванию.

**Чем добьют:** *«А если без `Counter`?»* → `sorted(counts.items(), key=lambda kv: -kv[1])[:n]`. Уметь написать оба варианта.

---

## 2.4. Разница двух наборов

**Условие:** сравнить ожидаемый список инсталляций с фактическим, показать чего не хватает и что лишнее.

**Решение:**

```python
def diff_by_id(expected, actual):
    exp = {i["id"] for i in expected}
    act = {i["id"] for i in actual}
    return {
        "missing": sorted(exp - act),
        "unexpected": sorted(act - exp),
    }
```

**Ход мысли вслух:**

> Списки сравнивать напрямую плохо: они упадут просто из-за разного порядка, и в выводе будет каша. Множества дают внятную диагностику — разность сразу показывает, чего не хватает и что появилось лишнего. `sorted` в конце — чтобы результат был детерминированным, иначе порядок в множестве произвольный и тест станет невоспроизводимым.

Последнее замечание про детерминированность — сильный ход, его редко проговаривают.

## 2.5. Сравнение payload с игнорированием изменчивых полей

**Условие:** сравнить ответ API с эталоном, но игнорировать `id`, `created_at`, `trace_id`.

**Решение:**

```python
IGNORED = {"id", "created_at", "updated_at", "trace_id"}

def normalize(payload, ignored=IGNORED):
    if isinstance(payload, dict):
        return {
            k: normalize(v, ignored)
            for k, v in payload.items()
            if k not in ignored
        }
    if isinstance(payload, list):
        return [normalize(item, ignored) for item in payload]
    return payload
```

**Ход мысли вслух:**

> Сначала написал бы плоскую версию — один уровень. Но ответы обычно вложенные, а изменчивые поля встречаются и внутри, поэтому нужна рекурсия: словарь обходим по ключам, список — поэлементно, скаляр возвращаем как есть.
>
> Отдельно отмечу риск: чем больше полей игнорируем, тем слабее тест. Это компромисс, и список игнорируемых должен быть коротким и осознанным, а не расти каждый раз, когда тест покраснел.

Последний абзац — то, что отличает инженера от исполнителя. Проговорить обязательно.

# Уровень 3. pytest

Здесь проверяют не Python, а то, умеете ли вы писать тесты.

---

## 3.1. Параметризованный тест на валидатор

**Условие:** есть `is_valid_license_key(key)`. Напишите тесты.

**Ход мысли вслух — начинать с тест-дизайна, а не с кода:**

> Сначала разложу входы на классы эквивалентности: валидный ключ, неверный регистр, неверное число групп, без разделителей, пустая строка, `None`. Беру по представителю на класс плюс границы. Оформлю через `parametrize` — так каждый кейс станет отдельным тестом, и в отчёте будет видно, какой именно упал.

**Решение:**

```python
import pytest

@pytest.mark.parametrize(
    "key, expected",
    [
        ("ABCD-1234-EFGH-5678", True),
        ("abcd-1234-efgh-5678", False),
        ("ABCD-1234-EFGH", False),
        ("ABCD12345EFGH5678", False),
        ("ABCD-1234-EFGH-5678-9012", False),
        ("", False),
        (None, False),
    ],
    ids=["valid", "lowercase", "too_few_groups", "no_dashes",
         "too_many_groups", "empty", "none"],
)
def test_is_valid_license_key(key, expected):
    assert is_valid_license_key(key) is expected
```

**Что подчеркнуть:**

- `ids` — чтобы падение читалось и чтобы кейс можно было перезапустить по адресу `test_...[empty]`.
- `is expected`, а не `== expected` — проверяем именно `True`/`False`, а не «что-то истинное». Если функция вернёт `1` или непустую строку, тест это поймает.
- *«Почему `None` в тестах?»* → Потому что реальный вызов может прийти с отсутствующим полем, и функция не должна падать с `AttributeError` вместо внятного `False`.

---

## 3.2. Фикстура с созданием и уборкой данных

**Условие:** нужен тест, который проверяет, что у новой инсталляции нет обновлений.

**Решение:**

```python
@pytest.fixture
def installation(api_client):
    inst = api_client.post("/installations", json={"name": f"test-{uuid4().hex[:8]}"}).json()
    yield inst
    api_client.delete(f"/installations/{inst['id']}")


def test_new_installation_has_no_updates(api_client, installation):
    resp = api_client.get(f"/installations/{installation['id']}/updates")
    assert resp.status_code == 200
    assert resp.json() == []
```

**Ход мысли вслух:**

> Данные создаю через API, а не через UI: быстрее и не зависит от вёрстки. Уборка после `yield` — выполнится даже если тест упал, иначе стенд зарастёт мусором. Имя генерирую уникальным: при параллельном прогоне фиксированное имя приведёт к конфликту между воркерами.

**Чем добьют:**

- *«А если удаление упадёт?»* → Тест уже отработал, но упадёт teardown, и результат будет `ERROR` вместо `PASSED` — это правильно, потому что уборка сломалась и это надо видеть. Если удаление в принципе может отсутствовать, оборачиваю в `try/except` с логом, но тогда нужен отдельный механизм чистки стенда.
- *«Какой скоуп?»* → `function`, потому что тест меняет данные. Общая инсталляция на модуль сделала бы тесты зависимыми друг от друга.

---

## 3.3. Найдите ошибки в тесте (код-ревью)

**Условие:** вот тест, что с ним не так?

```python
def test_update():
    driver.get("http://stand/installations")
    time.sleep(5)
    driver.find_element(By.XPATH, "/html/body/div[2]/div[3]/table/tr[1]/td[2]").click()
    time.sleep(3)
    assert True
```

**Как отвечать — по пунктам, от важного к мелкому:**

> **Первое и главное — ассерт ничего не проверяет.** `assert True` всегда истинен, тест зелёный при любом поведении системы. Это не тест, а имитация.
>
> **Второе — фиксированные задержки.** `sleep(5)` либо тормозит прогон, когда элемент готов раньше, либо не спасает, когда он готов позже. Нужны явные ожидания состояния: `WebDriverWait` с условием видимости или кликабельности.
>
> **Третье — абсолютный XPath.** Сломается от любой вставки `div` в вёрстку. Нужен `data-testid`, о котором договариваемся с разработкой.
>
> **Четвёртое — зависимость от состояния стенда.** Тест берёт первую строку таблицы и предполагает, что она есть и что она нужная. Данные должны создаваться самим тестом.
>
> **Пятое — нет уборки и нет изоляции**, при параллельном прогоне такой тест будет конфликтовать с соседями.
>
> **Шестое, мелкое — имя.** `test_update` не говорит, что проверяется. Имя должно читаться как утверждение: `test_update_applies_to_online_installation`.

**Как переписал бы:**

```python
def test_update_is_visible_for_installation(page, installation):
    installations_page = InstallationsPage(page).open()
    row = installations_page.row_for(installation["name"])
    expect(row.locator("[data-testid='update-status']")).to_have_text("pending")
```

**Почему эта задача важна:** её дают чаще, чем кажется, и она проверяет ровно вашу профессию — не «умеете ли писать», а «видите ли плохое». Отвечать надо структурно и с приоритетами, а не свалкой замечаний.

## 3.5. Разложить набор по маркерам

**Условие:** есть 200 тестов. Как организуете запуск?

Кода почти нет — проверяют мышление.

```python

@pytest.mark.regress
@pytest.mark.slow
def test_full_update_cycle(): ...
```

```ini
[pytest]

    smoke: критичный минимум, на каждый пуш
    regress: полный набор, по расписанию
    slow: дольше 30 секунд
addopts = --strict-markers -ra
```

**Ход мысли вслух:**

> Разделяю по цене и по цели. `smoke` — то, что ломает продукт: минуты, гоняется на каждый пуш и является гейтом на мерж. `regress` — полный набор ночью с параллелью. `slow` — отдельная метка, чтобы можно было исключать: `-m "regress and not slow"`.

## 4.1. Ожидание асинхронного результата

**Условие:** обновление применяется асинхронно. Напишите проверку, что оно применилось.

**Что уточнить:**

> Сколько обычно занимает применение и какой разумный потолок? Есть ли статус, который означает финальный провал — чтобы не ждать таймаут впустую, если уже `failed`?

**Ход мысли вслух:**

> `sleep` не годится: он либо мал и тест флакует, либо велик и прогон тормозит. Нужен опрос с таймаутом. Плюс две вещи, которые обычно забывают: ранний выход на терминальном статусе и внятное сообщение об ошибке с последним фактическим значением.

**Решение:**

```python
import time

TERMINAL_FAILURES = {"failed", "rolled_back"}

def wait_for_status(getter, expected, timeout=60, interval=2):
    deadline = time.monotonic() + timeout
    last = None
    while time.monotonic() < deadline:
        last = getter()
        if last == expected:
            return last
        if last in TERMINAL_FAILURES:
            raise AssertionError(f"Терминальный статус '{last}', ожидали '{expected}'")
        time.sleep(interval)
    raise AssertionError(f"Не дождались '{expected}' за {timeout}с, последний статус '{last}'")


def test_update_is_applied(api_client, installation):
    api_client.post(f"/installations/{installation['id']}/updates",
                    json={"version": "2.1.0"})
    wait_for_status(
        lambda: api_client.get(f"/installations/{installation['id']}").json()["update_status"],
        expected="applied",
    )
```

**Что подчеркнуть:**

- `time.monotonic()`, а не `time.time()`: монотонные часы не прыгнут при синхронизации системного времени.
- Ранний выход на `failed` экономит минуту на каждом падении и делает причину очевидной.
- В сообщении есть последнее значение — без него непонятно, застряло на `downloading` или вообще не стартовало.

## 4.2. Проверка идемпотентности

**Условие:** повторная отправка команды с тем же ключом не должна создавать две записи. Напишите тест.

**Ход мысли вслух:**

> Идемпотентность проверяется не «отправил дважды подряд», а параллельно — последовательные запросы могут пройти по разным веткам кода, чем одновременные. Отправляю несколько одинаковых запросов в потоках и проверяю инвариант: одна запись, один идентификатор результата.
>
> Потоки здесь работают, несмотря на GIL, потому что это ожидание сети, а не вычисления.

**Решение:**

```python
from concurrent.futures import ThreadPoolExecutor

def test_apply_update_is_idempotent(api_client, installation):
    idempotency_key = uuid4().hex
    payload = {"version": "2.1.0"}
    headers = {"Idempotency-Key": idempotency_key}

    def send():
        return api_client.post(
            f"/installations/{installation['id']}/updates",
            json=payload, headers=headers,
        )

    with ThreadPoolExecutor(max_workers=5) as pool:
        responses = [f.result() for f in [pool.submit(send) for _ in range(5)]]

    assert all(r.status_code in (200, 201, 409) for r in responses)

    updates = api_client.get(f"/installations/{installation['id']}/updates").json()
    matching = [u for u in updates if u["version"] == "2.1.0"]
    assert len(matching) == 1, f"Ожидали одну запись, получили {len(matching)}"
```

**Чем добьют:**

- *«Почему `409` считается успехом?»* → Потому что «конфликт, такая операция уже выполняется» — корректный ответ на дубль. Важен инвариант в конце, а не коды по отдельности.
- *«Тест нестабильный?»* → Он вероятностный: гонка может не воспроизвестись за один прогон. Поэтому такие тесты гоняют в несколько повторов и держат в отдельном наборе, а не в smoke.

## 4.3. Валидация контракта через модель

**Решение:**

from pydantic import BaseModel

    name: str

## 4.4. Ретрай с нарастающей задержкой

**Условие:** напишите обёртку, которая повторяет нестабильный запрос.

**Решение:**

```python
import functools, time

def retry(times=3, delay=1, backoff=2, exceptions=(ConnectionError, TimeoutError)):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            current = delay
            for attempt in range(1, times + 1):
                try:
                    return func(*args, **kwargs)
                except exceptions:
                    if attempt == times:
                        raise
                    time.sleep(current)
                    current *= backoff
        return wrapper
    return decorator
```

**Обязательно добавить позицию — иначе ответ читается как «прячу флак»:**

> Оговорюсь: в самих проверках я ретраи не применяю. Ретрай на ассерте превращает красный прогон в зелёный и скрывает нестабильность, в том числе настоящие гонки. Это уместно для инфраструктурных операций — сетевой запрос к стенду, ожидание готовности сервиса. И ловлю здесь только сетевые исключения, а не `Exception`: иначе проглочу и `AssertionError`.

**Про `functools.wraps`:** без него обёрнутая функция теряет имя, и в отчётах вместо теста будет `wrapper`.

## 5.1. Сравнение версий

**Условие:** отсортируйте список версий продуктов: `["2.9.0", "2.10.0", "1.0.0", "2.1.0"]`.

**Подвох:** строковая сортировка даст `"2.10.0" < "2.9.0"`, потому что символ `1` меньше `9`. Это реальный баг, который живёт в проде годами.

**Ход мысли вслух:**

> Сразу отмечу ловушку: как строки версии сортируются неверно — `2.10` окажется раньше `2.9`. Нужно сравнивать покомпонентно, как кортеж чисел. Кортежи в Python сравниваются лексикографически поэлементно, поэтому `(2, 10, 0) > (2, 9, 0)` — то, что надо.

**Решение:**

```python
def version_key(version):
    return tuple(int(part) for part in version.split("."))

sorted(versions, key=version_key)
```

**Чем добьют:**

- *«А если версия вида `2.1.0-rc1`?»* → Мой парсер упадёт на `int("0-rc1")`. Для семантических версий с пре-релизами правильнее взять готовую библиотеку `packaging.version.parse` — она реализует спецификацию semver, включая правило, что пре-релиз меньше релиза.
- *«А разное число компонентов — `2.1` и `2.1.0`?»* → Кортежи разной длины сравнятся, но `(2, 1) < (2, 1, 0)`, что может быть не тем, что вы хотите. Надо договориться о нормализации.

**Тестовый взгляд — добавить самому:**

> Как тестировщик я бы обязательно завёл кейсы `2.9.0` против `2.10.0`, равные версии, и downgrade — попытку применить версию младше установленной. Последнее у вас ещё и вопрос безопасности: откат на уязвимую версию.

## 5.2. Окно действия лицензии с таймзонами

**Условие:** напишите проверку `is_license_active(license, now)`.

**Что уточнить — это и есть главная часть ответа:**

> Первый вопрос: границы включительные или нет — лицензия, истекающая ровно сейчас, активна? Второй: срок считается по UTC или по локальному времени инсталляции? Третий: есть ли грейс-период после истечения?

**Ход мысли вслух:**

> Работаю только с aware-датами. Сравнение naive и aware в Python бросает `TypeError`, и это хорошо — хуже, когда обе naive и код тихо сравнивает разные таймзоны, давая расхождение в сутки.

**Решение:**

```python
from datetime import datetime, timezone

def is_license_active(starts_at, expires_at, now=None):
    now = now or datetime.now(timezone.utc)
    for moment in (starts_at, expires_at, now):
        if moment.tzinfo is None:
            raise ValueError("Ожидаются даты с таймзоной")
    return starts_at <= now < expires_at
```

**Тесты, которые надо назвать самому:**

```python
@pytest.mark.parametrize("offset_seconds, expected", [
    (-1, True),    # последняя секунда до истечения
    (0, False),    # ровно момент истечения — граница исключающая
    (1, False),    # первая секунда после
], ids=["before_expiry", "at_expiry", "after_expiry"])
def test_expiry_boundary(offset_seconds, expected):
    expires = datetime.now(timezone.utc)
    now = expires + timedelta(seconds=offset_seconds)
    assert is_license_active(expires - timedelta(days=30), expires, now) is expected
```

**Что подчеркнуть:**

> Даты вычисляю от текущего момента, а не хардкожу. Захардкоженное `2026-01-01` однажды протухнет, и тест покраснеет сам по себе — это худший вид ложного падения, потому что он приходит внезапно и без изменений в коде.

## 5.3. Дедупликация телеметрии со скользящим окном

**Условие:** события телеметрии могут дублироваться при ретраях. Считать уникальные события за окно в N минут — повтор того же `event_id` в пределах окна игнорируем.

**Что уточнить:**

> Окно скользящее или фиксированные интервалы? Порядок событий гарантирован? Насколько велик поток — держать всё в памяти можно или нужен внешний сторедж?

**Ход мысли вслух:**

> Держу словарь «event_id → время последнего учтённого». При новом событии проверяю: если такой id уже был и разница меньше окна — пропускаю. Иначе учитываю и обновляю время.
>
> Проблема очевидна: словарь растёт бесконечно. Поэтому периодически чищу записи старше окна — иначе на длинном потоке это утечка памяти.

**Решение:**

```python
from datetime import timedelta

def deduplicate(events, window=timedelta(minutes=5)):
    seen = {}
    result = []
    for event in sorted(events, key=lambda e: e["timestamp"]):
        eid, ts = event["id"], event["timestamp"]
        previous = seen.get(eid)
        if previous is not None and ts - previous < window:
            continue
        seen[eid] = ts
        result.append(event)
        # чистка устаревших, чтобы словарь не рос бесконечно
        seen = {k: v for k, v in seen.items() if ts - v < window}
    return result
```

**Честная оговорка, которую стоит сделать самому:**

> Чистка на каждой итерации — это лишняя работа: получается квадратичная сложность. На проде я бы чистил раз в N событий или использовал структуру с автоматическим устареванием. Здесь оставил прямолинейно ради читаемости, но проблему вижу.

Признать слабость своего же решения раньше интервьюера — сильный ход. Это читается как зрелость, а не как неуверенность.

## 5.4. Page Object на живую

**Условие:** напишите Page Object для страницы со списком инсталляций и тест на фильтрацию.

**Решение:**

```python
class BasePage:
    def __init__(self, page):
        self.page = page

    def open(self, path=""):
        self.page.goto(f"{BASE_URL}{path}")
        return self


class InstallationsPage(BasePage):
    SEARCH = "[data-testid='installations-search']"
    ROW = "[data-testid='installation-row']"
    STATUS = "[data-testid='installation-status']"

    def open(self):
        return super().open("/installations")

    def search(self, query):
        self.page.fill(self.SEARCH, query)
        self.page.press(self.SEARCH, "Enter")
        return self

    def rows(self):
        return self.page.locator(self.ROW)

    def status_of(self, name):
        return self.page.locator(self.ROW, has_text=name).locator(self.STATUS)


def test_search_filters_installations(page, installation):
    installations = InstallationsPage(page).open().search(installation["name"])
    expect(installations.rows()).to_have_count(1)
    expect(installations.status_of(installation["name"])).to_have_text("online")
```

**Что проговорить:**

> Локаторы — константами класса, чтобы правка вёрстки чинилась в одном месте. Методы возвращают `self` — получается читаемая цепочка. **Ассертов внутри Page Object нет:** страница описывает, как с ней взаимодействовать, а чего мы ждём — решает тест. Иначе страницу нельзя переиспользовать в сценарии с другими ожиданиями.
>
> И данные для теста приходят из фикстуры, а не берутся «что есть на стенде» — иначе тест зависит от чужого состояния и развалится на параллели.

<a id="антипаттерны"></a>

# Антипаттерны лайвкодинга

Чего не делать — по убыванию вреда.

**Молчать.** Тишина дольше пятнадцати секунд читается как «потерялся». Даже если думаете — думайте вслух: «так, мне нужен способ быстро проверять, видел ли я уже этот id…»

**Нырять в код без уточнений.** Самая дорогая ошибка: пять минут кода не в ту сторону. Тридцать секунд вопросов дешевле.

**Писать «умно».** Вложенный comprehension в три уровня, который вы сами потом не прочитаете. Простой цикл всегда лучше сломанной элегантности. Оптимизировать можно после того, как работает.

**Спорить с подсказкой.** Если интервьюер говорит «а если элементы не хешируемые» — это подсказка, а не нападение. Правильная реакция: «о, точно, тогда так…»

**Оправдываться.** «Я обычно на TypeScript, тут могу напутать» — один раз в начале, как рамка. Повторять после каждой строки нельзя, это разрушает впечатление сильнее самих ошибок.

**Забывать про тестировщика в себе.** Вы не разработчик на собесе — вы тестировщик. Назвать крайние случаи к собственному коду ценится выше, чем идеальный код без них. Это ваше профессиональное преимущество, и его надо использовать в каждой задаче.

**Молча исправлять.** Заметили баг в своём коде — скажите: «вижу, здесь упадёт на пустом списке, чиню». Найденная и озвученная своя ошибка — плюс, а не минус.

# Банк фраз

Заготовки, чтобы не искать слова под давлением.

**Начало:**
- «Правильно понимаю, что…?»
- «Уточню три вещи по входным данным…»
- «Могу пойти в лоб, сложность будет линейная. Если устраивает — начну с этого.»

**По ходу:**
- «Здесь беру множество, потому что проверка вхождения по списку линейная, а мне нужна константа.»
- «Пока напишу прямолинейно, потом посмотрим, надо ли оптимизировать.»
- «Тут защищаюсь от отсутствующего ключа — данные могут прийти неполными.»

**Когда застряли:**
- «Дайте секунду, проговорю варианты вслух.»
- «Пока вижу два подхода: … и … Второй кажется проще, иду по нему.»
- «С этим конкретно не сталкивался. Рассуждаю так…»

**Проверка себя:**
- «Проверю на границах: пустой вход, один элемент, дубликаты.»
- «Вижу слабое место в своём решении: …»
- «Если данных будет много, здесь станет узко — тогда переделал бы на…»

**Взгляд тестировщика:**
- «Как тестировщик я бы обязательно завёл кейсы на…»
- «Тут классическая ловушка на границе, её проверяю отдельно.»
- «Это то же самое, что проверка идемпотентности в вашем сервисе доставки обновлений.»

**Финал:**
- «Готово. Слабые места: … Если хотите, доведу до…»
- «Тестами это покрыл бы так: …»

# Как тренироваться

Три захода до собеса, если время есть; один — если нет.

**Заход 1 — уровни 1 и 2, по таймеру.** Пять минут на задачу, вслух, без подглядывания. Цель — вернуть беглость синтаксиса.

**Заход 2 — уровень 3.** Не столько код, сколько формулировки: тест-дизайн перед кодом, `ids`, изоляция данных, уборка.

**Заход 3 — уровни 4 и 5.** Здесь важнее не дописать, а правильно уточнить и назвать риски. Если из пяти задач вы в трёх начнёте с уточняющих вопросов и в конце сами назовёте крайние случаи — этап пройден, даже если код будет не идеальным.

Обязательно **вслух и с включённой камерой на себя**. Разница между «решил в голове» и «решил, объясняя» — примерно как между чтением про плавание и плаванием.
