## Python: ООП, async/await, чистый код

По ООП это ежедневная работа, потому что вся архитектура автотестов на нём и держится. Page Object — это классы: базовый класс с общими операциями, страницы наследуются от него, повторяющиеся блоки интерфейса вынесены в компоненты и подключаются композицией. Правило разделения простое: наследование, когда страница является частным случаем базовой; композиция, когда она содержит блок. Дальше — модели данных: `dataclass` для тестовых объектов с дефолтами, Pydantic для разбора и валидации ответов API, `classmethod` как альтернативный конструктор, `property` для вычисляемых признаков. И `__repr__` в моделях — без него при падении ассерта в отчёте будет адрес объекта в памяти вместо данных.

Про async честно разграничу две вещи, которые часто смешивают. **Асинхронные системы** я тестировал много: Kafka, eventual consistency, события, которые обрабатываются не мгновенно. **`async`/`await` в самом Python** применял ограниченно: у Playwright есть асинхронный API, есть `httpx`. Но в тестовом коде обычно выбирал синхронный вариант сознательно — параллелизм дешевле и надёжнее получать процессами через `pytest-xdist` или воркерами Playwright, а асинхронный код усложняет отладку без выигрыша там, где узкое место всё равно сеть и браузер.

При этом понимаю, где async уместен: из-за GIL потоки не ускоряют вычисления, но работают на ожидании ввода-вывода — async решает ту же задачу без накладных расходов на потоки. Практически использовал, когда нужно отправить пачку параллельных запросов — например, воспроизвести гонку и проверить идемпотентность.

Насчёт чистоты кода — это часть моей зоны ответственности. Написал технический стандарт: кодстайл, иерархия селекторов, правила именования. Настроил линтеры и форматирование, чтобы стиль не обсуждался на ревью. Поставил обязательное код-ревью, потом перевёл команду на кросс-ревью. Принципы, которые защищал: в тестах нет логики (никаких `if` — на каждое условие свой тест), локаторы не дублируются, ассертов нет внутри Page Object, никаких `sleep`, имя теста читается как утверждение о поведении. Плюс типизация — она сильно помогает, когда фреймворк растёт.

## Опыт с JavaScript / TypeScript, Playwright и React

Это мой основной стек последних месяцев. На проекте в Т-Банке — личный кабинет бизнес-клиентов — строил автоматизацию с нуля на Playwright и TypeScript: до меня лежало немного legacy на Selenide, мы от него отказались и покрывали с чистого листа. Архитектура — классический Page Object плюс компонентный подход: повторяющиеся блоки интерфейса вынесены в отдельные классы, страницы их композируют. Разбиение по пакетам под юниты — посткредитование, рассрочка.

Из технической части: авторизация через `storageState`, чтобы не прогонять логин в каждом тесте; параллельный прогон на воркерах с изоляцией данных; моки нестабильных интеграций через `route`; отдельный слой API-проверок на `request` со схема-валидацией через Zod. При падении тест самодиагностируется — трейс, скриншот, запрос и ответ. Прогон в GitLab CI: быстрый набор на пуш, полный ночью с шардированием. Результат — покрытие критичных зон 80–85%, регресс с четырёх часов до сорока минут, флак задавлен.

Про React уточню честно: я его тестирую, а не разрабатываю на нём. Но специфику учитываю. Классы генерируются сборщиком и меняются при пересборке, поэтому локаторы на них вешать нельзя — договорился с разработкой о простановке `data-testid`, и это оказалось самой окупаемой договорённостью на проекте. Дальше: SPA не перезагружает страницу, поэтому ждать надо состояние или конкретный сетевой ответ, а не событие загрузки; частые ре-рендеры дают устаревшие ссылки на элементы, что закрывается автоожиданиями Playwright; в виртуализированных списках элемента может физически не быть в DOM.

Компонентное тестирование React-компонентов не вёл — это была зона разработчиков с их юнит-тестами. Моя граница начиналась на уровне собранного приложения: e2e и API.

## SQL: уровень и пример задачи

Уровень — уверенный пользовательский, в объёме, который нужен тестировщику. Свободно пишу `SELECT` с фильтрацией, `INNER` и `LEFT JOIN` по нескольким таблицам, `GROUP BY` с агрегатами и `HAVING`, подзапросы, `IN`/`EXISTS`, сортировку и лимиты; базово — оконные функции. Для подготовки данных использую точечные `INSERT` и `UPDATE`, после прогона убираю за собой. Основная СУБД — PostgreSQL, работаю через DBeaver.

Оптимизацией запросов в проде не занимаюсь, это зона разработки и DBA. Но если выборка или тест тормозят, смотрю план через `EXPLAIN ANALYZE` и понимаю, где не хватает индекса.

Типичная задача — проверка того, что не видно на интерфейсе. Например, проверял идемпотентность оформления: при повторной отправке запроса с тем же ключом в базе должна оставаться одна заявка, а не две. На UI это не воспроизводилось, дубли ловились только в данных:

```sql
SELECT idempotency_key, COUNT(*) AS cnt
FROM applications
WHERE created_at >= now() - interval '1 hour'
GROUP BY idempotency_key
HAVING COUNT(*) > 1;
```

Так поймали гонку при параллельных запросах. После этого проверку инварианта «один ключ — одна запись» зафиксировал в автотесте.

Второй регулярный сценарий — сверка того, что вернул API, с тем, что легло в таблицы, и поиск осиротевших связей: заявка есть, а графика платежей к ней нет. Это `LEFT JOIN` с фильтром по `NULL` в правой таблице.

# Инструменты

## Docker: опыт, команды, пример задачи

Docker для меня — рабочая среда прогона тестов. Тесты гоняю в контейнере, чтобы окружение было одинаковым локально и в CI: зафиксированы версия браузеров, системные зависимости и версия Playwright — это снимает класс проблем «локально зелёно, в CI красно».

```
docker build -t aqa-tests:local .
docker run --rm -v "$(pwd)/playwright-report:/tests/playwright-report" aqa-tests:local
docker run -it --rm --entrypoint bash aqa-tests:local
docker ps -a / docker images / docker logs -f <id>
docker compose up --build --abort-on-container-exit --exit-code-from tests
docker compose down -v
docker system prune -af
```

Пример задачи. Тест на оформление рассрочки стабильно падал в CI и был зелёным локально. Зашёл внутрь контейнера через `--entrypoint bash`, сверил версии и переменные окружения, проверил доступность приложения и mock-сервера по именам сервисов внутри сети compose. Оказалось, тесты стартовали раньше, чем БД принимала соединения. Починил не ретраями, а корректной готовностью зависимостей: `healthcheck` на БД (`pg_isready`) и `depends_on: condition: service_healthy`.

## Dockerfile и docker-compose для тестовых окружений

Писал и поддерживал оба.

Dockerfile для тестов — от официального образа Playwright с тегом, жёстко совпадающим с версией в `package.json`. Порядок слоёв важен ради кеша: сначала копируются только `package*.json`, затем `npm ci` строго по lock-файлу, и только потом весь код тестов. За счёт этого при правке теста образ пересобирается за секунды. Пересборка нужна только при смене окружения.

docker-compose поднимал стек из четырёх сервисов: `app` — тестируемое приложение из registry; `db` — PostgreSQL с healthcheck; `mock` — WireMock для нестабильных внешних интеграций, правила ответов подключены volume'ом; `tests` — контейнер с автотестами, `BASE_URL` и `MOCK_URL` заданы по именам сервисов, отчёты вынесены на хост через volume.

Запуск в CI — `docker compose up --build --abort-on-container-exit --exit-code-from tests`: код выхода контейнера с тестами прокидывается наружу, поэтому упавшие тесты роняют пайплайн — это и есть quality gate. Уборка — `docker compose down -v`.

## Selenium, Bitbucket, Jenkins, JMeter, Allure

**Selenium** — работал, уверенно. Разрабатывал, поддерживал и рефакторил UI-тесты на Selenium + pytest, был опыт и с Selenide. Ключевое: явные ожидания через `WebDriverWait` вместо фиксированных задержек, иерархия локаторов с приоритетом `data-testid`, Page Object как основа. На последнем проекте осознанно ушли с Selenide на Playwright — кода было немного, а встроенные автоожидания снимали основной источник флака.

**Allure** — уверенно, основной инструмент отчётности. Подключал `allure-pytest`, размечал шаги, прикладывал к падениям артефакты: скриншот, трейс, запрос и ответ. Ценю историю прогонов — она показывает, что тест нестабильный, а не «сегодня не повезло». Знаю нюанс с параллелью: Allure пишет отдельный файл на тест, поэтому нормально живёт с многопроцессным прогоном, а генерация HTML — отдельный шаг после pytest.

**Jenkins** — использовал, но основной мой CI — GitLab CI, там настраивал пайплайны сам: быстрый набор на пуш, полный прогон по расписанию с шардированием, релизные гейты. В Jenkins принципы те же — джобы, стадии, артефакты, триггеры; вход быстрый, но глубокую экспертизу заявлять не буду.

**JMeter** — базовый уровень. Составлял планы тестирования, настраивал группы потоков с разгоном, собирал отчёты по времени отклика и ошибкам. Понимаю, что смотреть надо на перцентили, а не на среднее: среднее прячет хвост, и страдает как раз тот процент пользователей, который в него попал. Но нагрузочное не было моей специализацией.

**Bitbucket** — не работал, у меня GitLab и GitHub. Это тот же git с пул-реквестами, разница в интерфейсе и в синтаксисе пайплайнов, вход занимает пару дней.

Настраивал устройство на прокси, ставил корневой сертификат Charles, чтобы видеть HTTPS в расшифрованном виде. Дальше — фильтрация по хосту, просмотр запроса и ответа целиком, проверка того, что клиент реально отправляет. Это регулярно закрывало споры «баг на фронте или на бэке».

Из более прикладного — подмена ответа для проверки поведения клиента на нестандартных данных и троттлинг соединения, чтобы посмотреть поведение на медленной сети и при обрыве.

Уровень честно: уверенный пользователь на этих сценариях. В правила переписывания трафика и тонкую настройку SSL-проксирования не углублялся.

## Системы баг-трекинга

Основной инструмент — **Jira**, ей пользовался больше всего: уверенно. Помимо базового заведения и ведения дефектов — работа с фильтрами и JQL для выборок, настройка досок и дашбордов под команду, связывание задач между собой: дефект с требованием и с тест-кейсом, чтобы прослеживалась цепочка. В Т-Банке использовалась внутренняя TMS, до этого работал с **Яндекс-трекером**, из более раннего — **Redmine** и **Bugzilla**.

По уровню: как пользователь уверенно во всех, включая настройку рабочих процессов и статусной модели под команду. Администрированием на уровне схем прав и глобальной конфигурации не занимался.

По существу инструмент здесь не главное — переключиться между ними вопрос пары дней. Важнее содержание дефекта. Стараюсь отдавать разработчику не симптом, а локализованную картину: чёткие шаги воспроизведения, ожидаемое и фактическое поведение, окружение и версия, стабильность воспроизведения, и главное — где именно ломается: запрос и ответ из devtools, фрагмент лога, при необходимости состояние в базе. Плюс артефакты — скриншот, видео, трейс.

Принципиальная позиция: дефект завожу всегда. Обсуждать можно severity, priority и попадёт ли исправление в текущий релиз — но не сам факт существования. Незаведённый баг — потерянная для команды информация.

## Общий стаж в QA и сколько из него автоматизация ⚠️

## Опыт ручного тестирования ⚠️

> ⚠️ Срок подставить свой, тот же, что и в предыдущем ответе.

Ручное тестирование для меня база, с него я начинал и оно никуда не делось: суммарно занимаюсь им около [X] лет, и на текущем проекте оно остаётся частью ежедневной работы.

Новая функциональность всегда проверяется руками. Автотест имеет смысл писать на сценарий, который устоялся — пока фича меняется каждый день, автоматизация будет переписываться быстрее, чем приносить пользу. Плюс исследовательское тестирование: там ценность как раз в том, что человек отходит от сценария. Автотест по определению проверяет только то, что в него заложили.

Что входило: разбор требований вместе с системными аналитиками ещё до разработки — часто именно там всплывают неописанные комбинации; тест-дизайн и оформление тест-кейсов в TMS; функциональная и регрессионная проверка; приёмка перед релизом. Отдельно — локализация дефектов: не «не работает», а найти, где именно ломается.

Отношение спокойное: ручное и автоматизация не конкуренты. Автоматизация снимает повторяемую рутину, а человек нужен там, где нужна голова. На проекте, где автотестов ещё нет, я в любом случае начинаю руками: сначала понять систему и разметить критичные пути, потом покрывать.

## Самостоятельная работа и консультирование младших

На текущем проекте я пришёл в точку, где спросить было не у кого — автотестов не было вообще, архитектуры не было, кодстайла не было, требования по старым фичам не описаны. Сначала ревьюил преимущественно я и быстро стал узким местом: пул-реквесты ждали меня, релизы тормозили, знание сидело в одной голове. Подтянул коллегу до второго ревьюера и перевёл команду на кросс-ревью. Пропускная способность выросла, стандарт перестал зависеть от моего наличия, а сами ревью стали учебными. Для меня это и есть критерий, что консультирование сработало — когда команда справляется без тебя.

# Методология и процессы

## Интеграционные проекты: какие типы интеграций

Уточню рамку сразу: сами интеграции разрабатывали бэкенд-разработчики — моя зона была тестировать их и покрывать автотестами. Но проект по сути весь состоял из стыков.

Типы. Синхронные REST-вызовы между микросервисами — здесь основное это контракт: проверял не только значения полей, но и структуру ответа по схеме, потому что переименованное поле может не уронить тест на конкретное значение, а систему сломает. Асинхронный обмен через Kafka — проверка, что событие ушло, что потребитель его обработал и что статус изменился; ловил по идентификаторам сообщений. Внешние источники — модули ФНС и БКИ: медленные, не всегда доступные, с ограничениями по частоте, поэтому в тестах мокировались, а реальная интеграция проверялась отдельным узким набором. Плюс внутренние сервисы персонификации.

Что из этого следует. Асинхрон означает eventual consistency: вместо задержек — опрос статуса с таймаутом, ранним выходом на терминальной ошибке и внятным сообщением о последнем значении. Ненадёжная сеть означает ретраи со стороны клиента, а значит нужна идемпотентность — проверял параллельными одинаковыми запросами с одним ключом и инвариантом «одна запись в базе». Отсюда же гонки.

Отдельно — сквозная проверка. UI-тест не заканчивается на зелёной плашке: если операция асинхронная, я подтверждаю результат там, где он реально появляется — статус через API, сообщение в очереди, запись в базе.

Из направлений, которые считаю правильными для такой архитектуры, — контрактное тестирование: когда сервисов много, поднимать всё вместе на каждую проверку дорого.

## Микросервисная архитектура: опыт и примеры

Основной пример — личный кабинет бизнес-клиентов в Т-Банке. Не монолит с одной базой, а набор сервисов: отдельные юниты под посткредитование, рассрочку, бизнес-счета, плюс слои персонификации, которые тянут данные из ФНС и БКИ. Между собой сервисы общаются и синхронно по REST, и асинхронно через Kafka. Фронт при этом один.

Что микросервисность меняет для тестировщика — три вещи. **Нет одной точки правды**: результат размазан по нескольким сервисам и базам, и зелёная плашка на экране ничего не доказывает. **Результат появляется не сразу**: проверки строятся на опросе состояния с таймаутом, а не на задержках. **Отказ одного сервиса не равен отказу системы** — и поведение при недоступности соседа само по себе требование, которое надо тестировать.

Как выстраивал тестирование. Перенёс основной объём проверок с UI на API-слой. Нестабильные внешние источники мокировались, реальная интеграция закрывалась отдельным узким набором — иначе весь регресс зависел бы от доступности ФНС. Сквозные сценарии оставил только на критичных путях: дорого поддерживать, первыми становятся флакующими. И обязательно проверка в базе и в очереди.

Конкретный случай. Тест на асинхронный сценарий падал по таймауту, при этом API отвечал корректно и на UI всё выглядело нормально. Нашёл лог потребителя Kafka, отфильтровал по идентификатору сообщения — событие доходило, но обработчик падал на валидации схемы. Дефект был не в том сервисе, который я тестировал, и на его границах не проявлялся.

Самое сложное в микросервисной архитектуре — не написать тест, а локализовать падение: понять, какой из семи сервисов сломался. Поэтому много вкладывался в диагностируемость — трейсы, логи, идентификаторы сообщений.

## BDD и Gherkin ⚠️

> ⚠️ Ответ построен на позиции «знаком, боевого проекта не вёл». Если реальный опыт с Cucumber или pytest-bdd есть — переписать.

С методологией знаком, синтаксис Gherkin знаю и использовал, но полноценного боевого проекта на Cucumber или pytest-bdd не вёл — скажу честно.

Что понимаю под BDD по сути: это не про инструмент, а про то, что поведение описывается на языке бизнеса и **до** разработки — совместно аналитиком, разработчиком и тестировщиком. Основная ценность возникает на этапе обсуждения: когда сценарий проговаривается втроём, неописанные комбинации и противоречия в требованиях всплывают до того, как написан код. Файл с фичей — побочный продукт этого разговора, а не цель.

Структуру знаю: `Feature`, `Background`, `Scenario` с `Given / When / Then`, `Scenario Outline` с таблицей `Examples`, теги для отбора наборов.

```gherkin
Функция: Оформление рассрочки

  Предыстория:
    Дано клиент авторизован в личном кабинете

  Структура сценария: лимит на сумму рассрочки
    Дано у клиента доступный лимит <лимит> рублей
    Когда он оформляет рассрочку на <сумма> рублей
    Тогда система отвечает "<результат>"

    Примеры:
      | лимит  | сумма  | результат |
      | 100000 | 99999  | одобрено  |
      | 100000 | 100000 | одобрено  |
      | 100000 | 100001 | отказано  |
```

Практически близкое делал на своём проекте, только без Gherkin-слоя: тест-кейсы в TMS писались в той же логике «предусловие → действие → ожидаемый результат», а требования разбирали с системными аналитиками до старта разработки.

И одну позицию обозначу. BDD окупается, когда Gherkin действительно читают люди со стороны бизнеса. Если сценарии пишут тестировщики для тестировщиков, получается лишний слой: step definitions приходится поддерживать, а выигрыша в понимании нет. Так что для меня это вопрос не «использовать или нет», а «есть ли у сценариев внешний читатель».

## Планирование тестов: тест-план и стратегия

**Короткая версия для скрининга:**

Разделяю два документа: стратегия — про подход и живёт долго (уровни проверок, что автоматизируем, работа с данными и средами, критерии качества релиза); тест-план — про конкретный релиз: объём, сроки, роли, риски, критерии входа и выхода.

Планирую от риска, а не от покрытия: приоритет — вероятность отказа × цена отказа. Обязательно фиксирую границы, включая пункт «что мы не тестируем и почему» — он снимает ложные ожидания. Бизнес-логику гоняю на API-слое, сквозные сценарии оставляю только на критичных путях, потому что они дороже всех в поддержке.

На практике: на проекте без автотестов стратегия была не «покрыть всё», а разметить 10–15 критичных путей, за полторы недели собрать каркас с прогоном в CI и за следующие две-три их закрыть — в пределах месяца у команды появляется рабочий гейт. Обратный случай — зрелый регресс на 4 часа: там планирование свелось к чистке по ценности, вышло 40 минут без роста дефектов в проде.

План при этом живой: если он не пересматривается по фактическим данным, это уже не планирование.

**Развёрнутая версия — что добавить, если попросят подробнее:**

Что закладываю в план. Границы объёма — пункт «что мы НЕ тестируем и почему» не менее важен, чем список проверок. Распределение по уровням: бизнес-логика на API, интерфейс там, где действительно про интерфейс, сквозные только на критичных путях. Тестовые данные и среды — кто владелец стенда, как готовятся данные, есть ли изоляция при параллельном прогоне; это чаще всего и оказывается настоящим ограничением, а не нехватка тестов. Критерии входа и выхода. Риски с планом реакции. Метрики, по которым потом видно, сработало или нет.

# Общие правила ответов на скрининге

- **Цифры одинаковые везде.** Стаж, вилка, сроки выхода — в резюме, hh, анкете и разговоре. Рекрутёры сверяют внутри одного скрининга.
- **Деньги не в мотивации.** Мотивация всегда «к чему-то»: задачи, гринфилд, ответственность, домен.
- **Честная граница вместо преувеличения.** Одна-две очерченные границы («администрированием не занимался», «Bitbucket не работал») делают анкету достовернее, чем сплошные «да, всё умею», и снимают риск провала на добore.
- **Конкретика вместо абстракций.** «4 часа → 40 минут», «10–15 критичных сценариев», «покрытие 80–85%» — цифры продают, «кратчайшее время» нет.
- **Позиция по ценностям.** Баг завожу всегда, обсуждаю severity и priority — не сдвигаться под нажимом.
