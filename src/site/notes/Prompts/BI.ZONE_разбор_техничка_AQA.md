## Общий вердикт по интервью

Одной фразой: **инженер в кандидате виден отчётливо, программист на Python — нет; и провалилась ровно та зона, про которую было три прямых предупреждения на HR-скрининге двумя днями раньше.**

Встреча распалась на две почти не связанные половины.

**Первая половина — сильная.** Рассказ об опыте, архитектура автотестового проекта, разделение API- и UI-слоёв, подготовка данных через API вместо кликов, иерархия селекторов, автовейты Playwright, Kafka, контрактное тестирование, чтение лога, разница 401/403 — здесь кандидат говорил как человек, который это делал руками. Илья дважды подтвердил вслух: «нет-нет, всё правильно, всё круто». По инженерному мышлению вопросов к кандидату нет.

**Вторая половина — провальная.** Как только разговор перешёл с «как ты это организуешь» на «напиши код на Python», уровень обрушился до джуна первого месяца. Хронология падения:

- на вопрос «что надо прописать у фикстуры, чтобы пользователь создался один раз» — не назвал `scope`; ушёл в рассуждение про хранение данных в переменной или файле, потом сказал «не прописывать `yield`» (неверно, и по смыслу обратное);
- на прямой вопрос «знаешь, что такое scope?» — назвал скопы из **Playwright/TypeScript** (worker, session) и добавил, что в Python «их штук пять, сессия, функция и, наверное, воркер». Илья поправил: «worker'а такого я не слышал, по-моему, такого нет»;
- на «для чего ещё нужен session scope» — ответил «для параллелизма», перепутав scope фикстуры с воркерами `pytest-xdist`;
- в лайвкодинге на FizzBuzz потребовались подсказки по **двоеточию после `if`**, по разнице **`=` и `==`**, по **f-строкам** и по существованию **`else`**;
- во второй задаче написал `requests.json` вместо `response.json()`, а тест не запускался, потому что pytest его не собирал.

Итого: интервьюер-питонист последние сорок минут не оценивал кандидата, а **обучал его синтаксису**. Для вакансии, где в требованиях прямым текстом стоит «тестирование на Python с использованием pytest», это центральный факт встречи.

**Отягчающее обстоятельство — не незнание, а рассинхрон со словами.** На вопрос «на Python когда последний раз что-то делал?» кандидат ответил: «на последнем проекте, в Trade Star», а в конце встречи добавил: «на Python я работал, и был у меня коммерческий опыт на проекте». После этого он не смог поставить двоеточие после `if`. Интервьюер такое считывает мгновенно, и вывод делается не «слабый Python», а «сказал больше, чем есть» — а это бьёт уже по доверию ко всему остальному рассказу, включая сильную часть.

**Что сыграло в плюс:**

- **Архитектура автотестового проекта** — пакетное разбиение, отдельные API- и UI-фикстуры, POM с компонентами, именование методов так, чтобы в теле теста было видно, где API, а где UI. Ответ зрелый и «свой».
- **Подготовка данных через API, действия — через UI.** Ключевой принцип автоматизации назван самостоятельно и правильно, с обоснованием (скорость, параллелизация, стабильность).
- **Селекторы и автовейты.** `getByRole` как приоритет, скоупинг по родителям, отказ от `sleep`, ожидание по видимости элемента — это уровень человека, который вычищал флак.
- **Kafka.** Проверки сообщений по уникальному ID, eventual consistency — прямое попадание в их домен (телеметрия и обновления инсталляций — это очереди и асинхрон).
- **HTTP-часть.** 401 vs 403 — чётко, без запинки, с правильной формулировкой.
- **Не сдался под подсказками.** В обеих задачах дошёл до рабочего результата, принимал подсказки спокойно и без обид, вслух проговаривал ход мысли. Это единственное, что удержало встречу от полного обвала.

**Что было слабее:**

- **pytest как инструмент — не знает.** Не `scope`, не жизненный цикл фикстуры, не структура сборки тестов. Это ядро вакансии.
- **Python как язык — на уровне «читал, но не писал».** Синтаксис ветвлений, f-строки, `else`, разница присваивания и сравнения. Именно то, что нельзя «вспомнить за три дня», как было обещано на встрече.
- **Метрика покрытия.** На вопрос Кати «а как вы считали 80%?» ответ был сбивчивым, с формулировкой «по формуле тестов всего и количественных тестов, которые уже написаны» — и завершился фразой «мы к этой цифре не возвращались, тимлид такую цифру нам назначает». Одной репликой обесценен главный числовой якорь легенды.
- **Атрибут `active=true/false`.** На хорошо поставленный вопрос про кастомный атрибут кандидат ответил про автовейты Playwright «под капотом» — то есть ровно про то, что в этом случае **не работает**.
- **Тема ИИ поднята самим кандидатом** и разбилась о фразу «у нас запрещено использовать сторонние модели». В компании-вендоре кибербезопасности рассказ о том, как рабочий код и подготовка тестовых данных прогоняются через внешнюю модель, — не нейтральная деталь.

**Главный вывод.** Это не «неудачный день» и не «завалили на мелочах». Это точное срабатывание риска, который был назван письменно за два дня до встречи: *«либо вы пишете `@pytest.fixture` и `@pytest.mark.parametrize` не задумываясь, либо нет»*. Не написал. Разбор ниже устроен так, чтобы (а) по каждому вопросу был готовый правильный ответ и (б) в конце был не самоупрёк, а расписанный план, после которого такой этап проходится уверенно.

## Глава 1. Презентация команды и продукта — и первый вопрос кандидата

**Что рассказала Екатерина:** команда делает внутренние переиспользуемые компоненты. Есть SSO на **Keycloak** — единая точка входа в облачные продукты. Сейчас делают **сервис лицензирования** — учёт лицензий на ПО, выданных клиентам. В планах — **сервис обновлений** для коробочных инсталляций: коробка стучится в удалённое API и получает обновления исходя из своей текущей версии, всё это должно работать в связке с лицензированием.

Стек: **Python + FastAPI**, один сервис на **Go** (полулегаси), **Java** — потому что Keycloak на Java и все плагины с кастомизациями пишутся на ней (Spring). Инфраструктура: **K8s**, старые сервисы деплоятся на физические серверы; логи — **ELK + Kibana**; метрики — **Grafana**; код — **GitLab**, оттуда же **CI/CD**. Команда: два Python-разработчика (один мультистек), DevOps, тимлид, аналитик. Ищут **фултайм QA** — сейчас есть приходящая тестировщица, но её ресурс приходится согласовывать.

Три фразы, которые важнее остальных:

> «Сразу скажу, что **покрытие автотестами у нас в команде 0%**. От кандидата ожидаем, что мы совместно выработаем флоу для старта автоматизации».

> «Тест-кейсы у нас есть **в Allure** на новый функционал, описаны довольно хорошо и объёмно приходящим тестировщиком. На старый функционал не всегда есть».

> «Процессы: **канбан-доска, никаких спринтов и оценок**, берём из статуса задачу с наивысшим приоритетом. Бэкенд в основном, поэтому непрерывный деплой. Соотношение по бэклогу — **90 на 10 в пользу бэкенда**».

**Что спросил кандидат:** правильно ли он понимает, что ожидается тестирование бэкенда — ручки, описанные в Swagger или аналоге, то, что выходит за рамки юнит-тестирования разработчиков; и что тесты будут в том числе комплексные, затрагивающие UI, а не только модульные.

**Ответ Екатерины:** UI-части будет **минимальное количество**, только то, что касается SSO. «Остальное — тебе просто не с чем будет работать».

**Оценка ответа:**

- 👍 Вопрос по делу и в правильный момент — сразу очертил предмет работы и получил ключевой факт: **UI почти нет, всё будет API**. Это меняет приоритеты подготовки целиком.
- 👎 Вопрос был единственным на этом блоке, и он был про **scope работ**, а не про **продукт**. В HR-разборе двумя днями раньше был заготовлен список доменных вопросов — про офлайн-инсталляции, идемпотентность обновлений, границу срока лицензии, дубликаты телеметрии. Ни один не прозвучал. А ведь именно там кандидат выглядел бы сильнее всего: это его темы (eventual consistency, гонки, контракты), и это самое больное место их продукта.
- 👎 «Юнит-тестирование» в вопросе прозвучало в кандидатском значении (нижний уровень пирамиды), а у бэкендеров это слово означает строго тесты разработчика. Позже пришлось объясняться: «юнит-тестирование имею в виду не как у разработчиков, а по пирамиде». Мелочь, но с питонистами лучше сразу говорить их словами.

**Идеальный ответ (вместо одного вопроса — три, за то же время):**

> Правильно понимаю, что основная работа — API-слой поверх того, что описано в Swagger, а UI минимальный и только вокруг SSO?
>
> Тогда два вопроса по продукту, чтобы понимать, где будут главные риски.
>
> Первый — про обновления: как на тестовом контуре эмулируются инсталляции клиентов? Есть стенд с несколькими версиями продуктов? Меня интересует, чем проверять обратную совместимость — сервис новый, а инсталляции у клиентов старые, и это классическое место, где всё ломается.

**Почему так лучше:** три вопроса заняли бы столько же времени, сколько один, но показали бы, что кандидат уже думает об **их** системе. Для команды, где тестировщика не было никогда, это сигнал «человек начнёт приносить пользу с первой недели» — самый ценный сигнал, который вообще можно послать на такой вакансии.

## Глава 2. Рассказ о последнем месте работы

**Вопрос:** «Расскажи про последнее место работы: что было за команда, что за продукт, какие процессы».

**Что ответил:** T-банк, подразделение T-бизнес, на проекте ~8 месяцев. Юниты — рассрочка, T-mani, посткредитование. Покрытия не было вообще, покрывали с нуля; немного было на Selenide — отказались, потому что юниты активно развивались. В команде три AQA, ручных тестировщиков нет. Работали не по спринтам, а по фокусам; тест-кейсы заполняли **параллельно** с написанием автотестов, чтобы не дозаполнять по памяти.

Python я знаю на уровне чтения и правок, писал на нём на предыдущем проекте, но не в том объёме. # Тема крупным планом: покрытие тестами — как считается и зачем нужно

*Вынесено в отдельную главу по двум причинам. Первая: именно на этой метрике встреча дала первый сбой — ответ на вопрос Кати «а как вы считали 80%?» развалился на три захода и закончился фразой «тимлид нам такую цифру назначает». Вторая: этот вопрос задают почти на каждом собеседовании, и он всегда идёт следом за любой названной цифрой. Цифру без методики лучше не называть вообще.*

## Первое, что надо сделать, — уточнить, о каком покрытии речь

Под «покрытием» в AQA понимают минимум четыре разные метрики, и это первая развилка. Если вас спрашивают про покрытие, правильная реакция — не начинать отвечать, а уточнить: **покрытие кода или покрытие требований?** Путать их — типичная ошибка, и опытный интервьюер задаёт вопрос именно затем, чтобы посмотреть, различаете ли вы их.

## 1. Покрытие требований (requirements coverage)

Самая ходовая метрика в QA, потому что не требует доступа к коду.

```
Покрытие = (требований, на которые есть хотя бы один тест / всего требований) × 100%
```

Считается по **матрице трассируемости (RTM)** — таблице «требование ↔ тест-кейсы». 40 требований, тесты есть на 34 → 85%.

Здесь же живёт вопрос «а как понять, что тестов достаточно»: одного теста на требование мало. Зрелые команды считают покрытие не самих требований, а их **условий** — по классам эквивалентности и граничным значениям. Одно требование «лицензия действует до даты X» — это минимум четыре условия: до даты, ровно в дату, после даты, дата в другом часовом поясе.

## 2. Покрытие автоматизацией (automation coverage)

Именно это чаще всего имеют в виду, когда в контексте AQA говорят «у нас покрытие 60%»:

```
Покрытие = (автоматизированных тест-кейсов / всего тест-кейсов в наборе) × 100%
```

**Метрика лукавая.** 200 автоматизированных смоук-кейсов из 1000 дадут 20%, хотя закрывать они могут все критичные сценарии. Поэтому её режут по приоритетам: «критичных P1 автоматизировано 95%, по всему набору — 40%». Именно так и надо было отвечать Кате: назвать две цифры вместо одной.

## 3. Покрытие кода (code coverage)

Считается инструментом, который инструментирует код и смотрит, какие строки исполнились во время прогона. В Python это `coverage.py` и плагин `pytest-cov`, в JS — istanbul/nyc.

| Метрика | Что считает | Формула |
|---|---|---|
| Line / Statement | исполненные строки | исполнено / всего строк |
| Branch (decision) | обе ветки каждого `if` | пройдено ветвлений / всего |
| Condition | каждое подусловие в составном `if` | истина и ложь по каждому операнду |
| Function / Method | вызванные функции | вызвано / всего |
| Path | все маршруты по функции | практически не считают — комбинаторный взрыв |

**Ключевой момент для собеседования — разница между line и branch:**

```python
def check(status):
    if status == 200:
        return "ok"
    return "fail"
```

Один тест со `status=200` не выполнит `return "fail"` — покрытие строк 75%. Но по **ветвям** это 50%: ветка «условие ложно» не пройдена вообще. Branch coverage строже и честнее, за это его и спрашивают.

**Отдельная тонкость именно для AQA:** e2e-тесты обычно **не измеряют** code coverage, потому что код выполняется в другом процессе или вообще на другой машине. Чтобы получить цифру, приложение нужно собрать в инструментированном виде и снять покрытие после прогона. Поэтому code coverage — метрика юнит- и интеграционного уровня, а автотесты уровня UI/API меряют покрытием функциональности. Это ровно тот ответ, которого не хватило: «мы считали не code coverage, он для E2E почти не имеет смысла».

## 4. Покрытие API и точек входа

Для вакансии, где 90% работы — API поверх Swagger, это **самая осмысленная цифра**, и её стоило назвать самому:

```
Покрытие = (протестированных эндпоинтов / всего эндпоинтов в спецификации) × 100%
```

Считается по OpenAPI-схеме, причём честно считать не эндпоинты, а тройки **«эндпоинт + метод + код ответа»**. Разница принципиальная: если считать по эндпоинтам, покрытие выглядит красиво, а негативные сценарии не покрыты вовсе.

Пример на их продукте. Сервис лицензирования, условно 8 эндпоинтов. Покрыты `GET /licenses`, `GET /licenses/{id}`, `POST /licenses` — по эндпоинтам это 37%, звучит нормально. Но в разрезе кодов ответа картина другая: 200 покрыты, а 400 на невалидный payload, 401 без токена, 403 с чужой ролью, 404 на несуществующий id, 409 на дубликат — не покрыты ни разу. Реальное покрытие по тройкам — около 10%. **Вот в этом и польза метрики: она показывает дыры, а не оценивает вас.**

## Как считают на практике (Python)

```bash
pip install pytest-cov

pytest --cov=. --cov-report=term-missing --cov-branch
```

- `--cov-branch` включает ветви вместо одних строк;
- `--cov-report=term-missing` печатает номера непокрытых строк;
- `--cov-report=html` даёт кликабельный отчёт в `htmlcov/`.

Порог в CI:

```bash
pytest --cov=. --cov-fail-under=80
```

Исключения из подсчёта — комментарием `# pragma: no cover` или секцией `[tool.coverage.run] omit = ...`: для генерируемого кода, обвязки и `if __name__ == "__main__"`.

## Что говорить про «сколько нужно»

Разумный ответ, который засчитывается на любом уровне:

> 100% покрытия не означает отсутствия багов — оно означает лишь, что код **исполнился**, а не что результат **проверен**. Тест без единого ассерта даст те же 100%.
>
> Метрика хорошо работает в одну сторону: **низкое покрытие достоверно говорит о дырах, высокое ничего не гарантирует.**
>
> Плюс закон Гудхарта: как только покрытие становится KPI, команда начинает писать тесты ради строк. Поэтому рядом с покрытием я всегда держу вторую цифру — время прогона регресса и долю флака. Одна цифра без другой врёт.
>
> Практический ориентир: 70–80% по ветвям на бизнес-логику, 100% на критичные модули (расчёты, платежи, авторизация, проверка лицензии), и осознанные исключения для генерируемого кода.

## Готовые ответы на типовые формулировки вопроса

**«Как вы считали покрытие?»**
Назвать метрику, знаменатель и вторую цифру. «Считали покрытие тест-кейсов автоматизацией: доля автоматизированных от общего числа в TMS, отдельно — срез по критическому пути. Code coverage не считали, для E2E он не показателен. Рядом всегда смотрели время регресса и долю флака».

**«У вас 80% — это много или мало?»**
«Смотря от чего. По критическому пути 80–85% — это рабочая цифра, по всему набору она была ниже, и это нормально: часть кейсов автоматизировать дороже, чем прогнать руками раз в квартал».

**«Чем line coverage отличается от branch?»**
Пример с `if` выше, дословно. Это самый частый уточняющий вопрос по теме.

**«Можно ли доверять 100% покрытию?»**
«Нет. Покрытие говорит, что код исполнился, а не что результат проверен — тест без ассертов даёт 100%».

**«Как бы вы считали покрытие у нас?»** *(лучший ответ под их продукт)*
«По OpenAPI, в разрезе метод + код ответа. Сразу будет видно, что позитивные сценарии закрыты, а 4xx нет — это первое, что я бы покрывал. Плюс отдельно матрица версий: сервис новый, инсталляции у клиентов старые, и совместимость версий — это тоже покрытие, только не строк, а сочетаний».

## Шпаргалка одной таблицей

| Метрика | Формула | Когда применяют | Чем плоха |
|---|---|---|---|
| Требования | тесты есть / всего требований | ручное QA, RTM | один тест на требование ≠ покрыто |
| Автоматизация | автоматизировано / всего кейсов | AQA, отчёты руководству | зависит от качества набора кейсов |
| Строки (line) | исполнено / всего строк | юнит-тесты | не видит непройденные ветки |
| Ветви (branch) | пройдено / всего ветвлений | юнит + интеграция | не работает для E2E |
| Эндпоинты | покрыто / всего в OpenAPI | API-автоматизация | без разреза по кодам ответа завышает |

## Глава 6. Один тест на три роли: как подготовить данные

**Вопрос Ильи:** «Ты говорил про ролевую модель. Допустим, у нас на проекте тоже есть роли, тебе нужно подготавливать данные и использовать их в тесте. Один и тот же тест надо прогонять с тремя разными ролями. Как бы это у тебя выглядело?»

**Что ответил:** классический подход — функция-декоратор `pytest.mark.parametrize`: в ней описываются бизнес-роли, статусы, все места, которые расходятся; если параметров несколько, они перемножаются — условно 5 на 4 даст 20 прогонов. Фикстуры складывались бы в `conftest.py` либо в отдельный пакет фикстур.

**Оценка ответа:**

- 👍 **Первый по-настоящему правильный технический ответ.** Названо ровно то, что спрашивали: `parametrize`, декоратор, `conftest.py`.
- 👍 Про перемножение параметров — верно и по делу: сложение нескольких декораторов `parametrize` даёт декартово произведение. Это уже деталь для тех, кто пользовался.
- 👎 Названо «функция-декоратор» — мелкая, но заметная неточность: `parametrize` это маркер, а `fixture` — декоратор. Питонист услышит.
- 👎 Ответ остановился на полпути: сказано **чем** параметризовать, но не сказано **что именно** параметризуется в случае ролей. А там есть развилка, которая отличает джуна от мидла: параметризовать сам тест или параметризовать фикстуру.

**Идеальный ответ:**

> Здесь два слоя. Сам перебор ролей — это `@pytest.mark.parametrize` над тестом: список ролей, и pytest разворачивает один тест в три с читаемыми именами.
>
> ```python
> @pytest.mark.parametrize("role", ["admin", "operator", "viewer"])
> def test_licenses_visible(api_client, role):
>     ...
> ```
>
> Но роль — это ещё и подготовка данных, поэтому чаще правильнее параметризовать не тест, а **фикстуру**, через косвенную параметризацию:
>
> ```python
> @pytest.fixture
> def user(request, users_api):
>     user = users_api.create(role=request.param)
>     yield user
>     users_api.delete(user.id)
>
> @pytest.mark.parametrize("user", ["admin", "operator", "viewer"], indirect=True)
> def test_licenses_visible(user, api_client):
>     ...
> ```
>
> Тогда тест не знает, как создаётся пользователь, а фикстура не знает, какие роли перебираются — и то и другое переиспользуется отдельно.
>
> Если ролей много и не все комбинации валидны — беру не декартово произведение, а список кортежей: `parametrize("role, expected_status", [("admin", 200), ("viewer", 403)])`. И обязательно `ids=`, чтобы в отчёте было `test_licenses[viewer-403]`, а не `test_licenses[1]`.
>
> Сами фикстуры — в `conftest.py`: корневой на общие, и отдельные `conftest.py` в `tests/api` и `tests/ui`, чтобы браузер не поднимался при прогоне только API.

**🔧 Что стоит выучить дословно.** Три формы `parametrize`, которые закрывают 90% задач:

```python
@pytest.mark.parametrize("value", [1, 2, 3])                       # один параметр
@pytest.mark.parametrize("role, code", [("admin", 200), ("guest", 403)])   # пара
@pytest.mark.parametrize("role", ["admin", "guest"], ids=["админ", "гость"])  # имена
```

И два способа комбинировать: **два декоратора** над одним тестом дают перемножение, **список кортежей** — только перечисленные комбинации.

## Глава 7. Что такое фикстура и чем она отличается от функции

**Вопрос:** «А фикстура вообще что это такое, чем это от функции отличается?»

**Что ответил:** фикстура — это функция, которая воссоздаёт окружение, предусловие для теста, и которая сама по себе тестом не является. Пример: заходим через точку авторизации, переходим на нужный URI — скажем, в корзину, делаем несколько переходов, и только тогда начинается тест. Фикстура называлась бы «зайти пользователем с VIP-статусом, перейти в корзину», задавалась бы через декоратор `pytest.fixture`. На уточнение «чем отличается от обычной функции» — «к ней можно обратиться и совершить все действия, не прописывая в тесте: подписали в тесте `logged_in_user`, и все предшествующие действия совершились под капотом».

**Оценка ответа:**

- 👍 Смысл передан верно: предусловие, не тест, декоратор назван правильно.
- 👍 Пример живой и конкретный — это хорошо, абстрактных определений интервьюеры не любят.
- 👎 **Главное отличие не названо.** Отличие фикстуры от функции не в том, что «действия совершаются под капотом» — так работает и обычная функция, которую вызвали. Отличие в **механизме внедрения и жизненном цикле**: pytest сам находит фикстуру по имени аргумента, сам разрешает её зависимости, кэширует результат в пределах scope и выполняет teardown. Ничего из этого не прозвучало.
- 👎 Ответ подвёл к следующему вопросу неудачно: раз кандидат описал фикстуру как «функцию, которая делает действия», следующий вопрос про повторное создание пользователя стал для него ловушкой.

**Идеальный ответ:**

> Технически фикстура — это функция с декоратором `@pytest.fixture`, но отличается она от обычной функции не телом, а тем, как её вызывают и сколько она живёт.
>
> **Первое — инверсия зависимостей.** Обычную функцию тест вызывает сам. Фикстуру он просто объявляет в аргументах — pytest находит её по имени, сам выстраивает цепочку зависимостей, если фикстура зависит от других фикстур, и подставляет результат. Тест не знает, откуда взялись данные.
>
> **Второе — жизненный цикл.** У фикстуры есть setup и teardown: код до `yield` выполняется перед тестом, код после — гарантированно после, даже если тест упал. Обычная функция так не умеет, ей нужен `try/finally`.
>
> **Третье — кэширование по scope.** Результат кэшируется в пределах `function`, `class`, `module`, `package` или `session`. Именно это отличает фикстуру от «просто хелпера»: вызвать её десять раз в пределах одного scope — значит выполнить один раз.
>
> **Четвёртое — видимость.** Фикстуры из `conftest.py` доступны всем тестам в каталоге и ниже, без импортов, и иерархия conftest'ов позволяет переопределять их на уровне подпапки.

**🔧 Инженерная расшивка.** На этот вопрос есть эталонная формула из трёх слов: **внедрение по имени, жизненный цикл с teardown, кэширование по scope**. Кто называет все три — знает pytest. Кто говорит «это подготовка данных перед тестом» — читал про pytest.

## Глава 8. Один пользователь на весь прогон — «какую вещь надо прописать?» 🔴🔴

**Вопрос Ильи** (он вёл к ответу почти минуту, максимально прозрачно): «Если у меня много тестов, и я для всех хочу использовать одного и того же подготовленного пользователя… Фикстура создаёт пользователя, возвращает объект `User`, в teardown удаляет из базы. Если мы не пропишем **некоторую штуку**, она после каждого теста будет выполнять teardown и в каждом новом тесте заново подготавливать и удалять. Но если мы какую-то вещь пропишем у этой фикстуры, то она выполнится один раз и будет действовать, пока все тесты не закончат выполнение».

**Что ответил:** «Нужно было бы… это уже вопрос, где мы будем хранить сведения об этом пользователе — или в переменной, или лежал бы пакет-файл, к которому мы обращались бы, то есть подтянуть переменную с этим пользователем для этой фикстуры и использовать фикстуру с параметризацией на этого пользователя». Илья: «Сейчас плохо понял» — и переформулировал вопрос ещё раз. Ответ со второй попытки: «Не прописывать `yield`, например, то есть всё, что после `yield`, оно вычищается в JMS, память, таким образом».

**Оценка ответа:** 🔴🔴 **Ключевой провал встречи.**

- 👎 **Вопрос был максимально подведённым.** Интервьюер прямым текстом описал поведение по умолчанию и попросил назвать одно слово. Слово — `scope`. Не названо ни с первой, ни со второй попытки.
- 👎 **Первый ответ — не туда.** Хранение данных в переменной или в файле — это ответ на вопрос «как расшарить данные между процессами», а не «как продлить жизнь фикстуры». Кандидат решал задачу, которой не было. Забавно и обидно: это правильный ответ на **другой** вопрос — про `pytest-xdist`, который всплыл бы двумя шагами позже.
- 👎 **Второй ответ хуже первого.** «Не прописывать `yield`» — неверно фактически: без `yield` фикстура просто не будет иметь teardown, но пересоздаваться при `scope="function"` она всё равно будет на каждом тесте. Плюс «вычищается в JMS» — это оговорка из Java-мира (JVM/GC), и в разговоре с питонистом она звучит особенно случайно.
- 👍 Единственный плюс: кандидат честно уточнял и не пытался блефовать. Илья это увидел и сам вывел на слово «scope».

**Идеальный ответ (два предложения):**

> Это параметр `scope` у декоратора. По умолчанию `scope="function"`, поэтому setup и teardown крутятся вокруг каждого теста. Ставим `@pytest.fixture(scope="session")` — pytest выполнит тело один раз при первом обратившемся тесте, закэширует результат и отдаст всем остальным тот же объект, а код после `yield` выполнит один раз в самом конце прогона.
>
> ```python
> @pytest.fixture(scope="session")
> def test_user(users_api):
>     user = users_api.create(name="test", role="admin")
>     yield user
>     users_api.delete(user.id)
> ```

**И сразу — три вещи, которые надо сказать самому, не дожидаясь вопроса:**

> **Первое — где лежит.** `scope` управляет временем жизни, но не видимостью. Чтобы фикстуру видели все тесты, она должна быть в `conftest.py`.
>
> **Второе — ScopeMismatch.** Session-фикстура не может зависеть от function-фикстуры: pytest упадёт ещё до тестов. Широкая фикстура живёт дольше узкой и не может держать на неё ссылку. Значит, `users_api` здесь тоже обязана быть session-scoped.
>
> **Третье — изоляция, и это главный минус.** Общий пользователь на весь прогон делает тесты зависимыми: один сменил ему пароль или оставил товар в корзине — следующий падает, причём в зависимости от порядка запуска. Компромисс, который я использую: тяжёлое создание — в session-фикстуре, а приведение состояния в чистое — в function-фикстуре поверх неё.
>
> ```python
> @pytest.fixture
> def clean_user(test_user, users_api):
>     users_api.reset_state(test_user.id)
>     return test_user
> ```
>
> **И четвёртое, если у вас параллельный запуск.** Под `pytest-xdist` каждый воркер — отдельный процесс со своей сессией, то есть пользователь создастся столько раз, сколько воркеров. Штатный рецепт из документации pytest: воркеры синхронизируются через `FileLock` на общем временном каталоге, первый создаёт пользователя и пишет его в json, остальные читают готовый.

**🔧 Почему это стоило именно столько.** Вопрос про `scope` — это не «вопрос на знание», это **фильтр**. Он занимает у интервьюера двадцать секунд и делит кандидатов на тех, кто писал тесты на pytest, и тех, кто про них читал. Провалить его на вакансии «Python + pytest» — значит закрыть тему компетенции одним ответом. Всё, что кандидат говорил дальше про архитектуру, Илья уже слушал через фильтр «а он это правда делал?».

## Глава 9. Что такое scope и какие они бывают в pytest 🔴

**Вопрос:** «Ну ладно, давай так. Знаешь, что такое скоп у фикстуры?»

**Что ответил:** «Это там, где у нас хранятся переменные для теста — скажем, сессия, браузер, воркеры в Playwright. В связке TypeScript плюс Playwright скопов всего два: worker и session». Илья уточнил: «Это скоп, который pytest… а в Python не знаешь как?» Ответ: «Не, это как в TypeScript, а именно в Python я знаю, что их побольше, штук пять: скоп на сессию, на функцию и… на воркер, скорее всего». Илья: «Вот worker'а такого я не слышал, по-моему, такого нет».

**Оценка ответа:** 🔴

- 👎 **Определение неверное.** Scope — это не «где хранятся переменные», а **время жизни и область кэширования** фикстуры: как часто она пересоздаётся.
- 👎 **Ответ из другого фреймворка.** Кандидат честно сказал, что говорит про Playwright/TS, но в вакансии на Python это читается как «в нужном инструменте не знаю».
- 👎 **Догадка вслух с ошибкой.** «Штук пять» — верно (`function`, `class`, `module`, `package`, `session`), но названы две из пяти плюс несуществующий `worker`. Догадываться в лайвкодинг-формате допустимо, но лучше честно сказать «точно помню function и session, остальные подсмотрю» — это выглядит лучше, чем изобретённый скоп.
- 👍 Кандидат сразу признал границу («в TypeScript так, в Python помню хуже») — это лучше блефа.

**Идеальный ответ:**

> Scope — это время жизни фикстуры: как часто pytest её пересоздаёт и в каких пределах кэширует результат. Их пять, от узкого к широкому:
>
> | scope | Пересоздаётся |
> |---|---|
> | `function` (по умолчанию) | на каждый тест |
> | `class` | на каждый класс с тестами |
> | `module` | на каждый файл |
> | `package` | на каждый пакет тестов |
> | `session` | один раз за прогон |
>
> Правило простое: чем дороже ресурс, тем шире scope, но тем хуже изоляция. Браузер — `session`, потому что поднимать его на каждый тест дорого. Контекст браузера — `function`, потому что нужны чистые куки на каждый кейс. Токен авторизации — `session`. Тестовые данные — `function`, если тест их меняет.
>
> В Playwright для TypeScript похожая идея реализована через `test` и `worker` фикстуры — но это другой фреймворк, в pytest воркеров нет, параллель там даёт отдельный плагин `pytest-xdist`.

**🔧 Что выучить.** Пять значений `scope` — это то, что надо знать как таблицу умножения. Плюс два следствия: **ScopeMismatch** (широкая не может зависеть от узкой) и **ленивость** (фикстура создаётся при первом обращении, а не в начале прогона).

## Глава 10. Для чего ещё нужен `scope="session"` 🔴

**Вопрос:** «Если мы пропишем `scope="session"` — чем он будет отличаться от `function`?» И следом: «Для каких вещей, кроме подготовки пользователя, может пригодиться такой скоп? Для чего приходилось использовать?»

**Что ответил:** на первый — «в сессии будут храниться фикстуры, которые активны в этой сессии, то есть на весь автотест»; на уточнение «а что значит активно?» — «фикстуры не очистятся, пока не закончится прогон этой части автотестов». На второй — «для параллелизма: параллелизм это подход, при котором мы можем разбить по потокам наши тесты и прогонять одновременно… если мы означаем скоп session, мы можем работать с этой сессией как с потоком, это аналог работы с воркером в Playwright плюс TypeScript».

**Оценка ответа:** 🔴

- 👍 Первая часть — по сути верна, хоть и коряво: «не очистятся до конца прогона» это правильная интуиция.
- 👎 Вторая часть — **концептуальная ошибка**. `scope="session"` не имеет отношения к параллелизму. Более того, при параллельном запуске через `pytest-xdist` session-фикстура работает **против** ожиданий: у каждого воркера своя сессия, и «одна на всех» превращается в «одна на каждого из восьми». Кандидат назвал ровно ту область, где session-scope создаёт проблему, как область, где он помогает.
- 👎 Ответ снова уехал в Playwright-терминологию. Третий раз за десять минут — интервьюер уже точно понял, что боевой инструмент другой.
- 👎 Не назван ни один типовой кейс, а их четыре штуки и они очевидные.

**Идеальный ответ:**

> Отличие от `function` в частоте пересоздания: `function` — заново на каждый тест, `session` — один раз за весь прогон, и все тесты получают из кэша один и тот же объект.
>
> Использую в четырёх типовых случаях:
>
> 1. **Дорогие ресурсы.** Запуск браузера, коннект к базе, поднятие docker-контейнера с зависимостью. Секунды на старте, умноженные на количество тестов, — это самая большая экономия времени прогона.
> 2. **Авторизация.** Токен или storage state получаем один раз и переиспользуем: не логинимся заново перед каждым тестом. В Playwright это `storage_state`, в API-тестах — сессия `requests` с заголовком.
> 3. **Конфигурация.** Чтение `.env`, базовые URL, клиент API — то, что неизменно в пределах прогона.
> 4. **Общие тестовые данные,** которые тесты только читают: справочники, каталог продуктов, заранее заведённая лицензия.
>
> Чего я в session **не** кладу — изменяемое состояние, которое тесты правят: это ломает изоляцию и делает падения зависимыми от порядка.
>
> И отдельная оговорка: к параллельному запуску scope отношения не имеет. Параллель в pytest — это `pytest-xdist` и ключ `-n`, и каждый воркер там отдельный процесс со своей сессией. То есть session-фикстура выполнится в каждом воркере, и если внутри неё создаётся общий ресурс, воркеров надо синхронизировать через файловую блокировку.

## Глава 11. Лайвкодинг, задача 1: FizzBuzz в фирменной обёртке 🔴🔴🔴

**Задача Ильи:** «Давай просто скрипт, без классов и функций. Выводим в консоль с новой строки каждое число от 1 до 100 включительно. Если число кратно 2 — выводим `bi`. Кратно 7 — `zone`. Кратно 2 и 7 одновременно — `bizone`. Если ни одно правило не подходит — выводим само число».

То есть классический FizzBuzz, переодетый в название компании. Задача-разминка, её обычно дают на 3–5 минут, чтобы снять напряжение и посмотреть, как человек думает вслух.

**Как это прошло.** Заняло **примерно 13 минут** (13:00 → 13:13) и потребовало серии подсказок. Хронология:

| Что произошло | Реплика интервьюера |
|---|---|
| Начал с `for i in range(1, 101)` — верно | — |
| Написал условие с делением, задумался про остаток | «Получится, в смысле, остаток?» |
| Не поставил двоеточия после `if` | «После второй и четвёртой строчки, после условий, в конце поставить двоеточие» |
| Поставил точку с запятой | «А на пятой точку с запятой не надо ставить, наоборот» |
| Написал `=` вместо `==` | «Одно равно — это операция у нас присваивания» |
| Второй раз то же самое | «Тут всё равно ещё моментик: опять присваивание операторов» |
| Захотел вывести число вместе со словом, не знал синтаксис | «Ты здесь букву F ставишь, F-строка, форматинг… и фигурные скобочки» |
| Не хватало ветки «иначе» | «Есть `if`, есть `elif`, а вот есть ещё один в Питоне, называется `else`» |
| 28 попало в ветку двойки вместо `bizone` | «Нам нужно, чтобы при i = 28 мы попали не в блок с двойкой, а в третий блок» |

**Оценка:** 🔴🔴🔴

- 👎 **Пять подсказок по базовому синтаксису.** Двоеточие, `==`, точка с запятой, f-строка, `else` — это не «подзабыл детали», это язык, на котором человек не писал. Причём подсказки были не наводящие, а прямые: интервьюер диктовал.
- 👎 **Точка с запятой и `=` вместо `==`** — характерные следы TypeScript. Само по себе объяснимо и даже нормально при переходе, **если** об этом предупредить заранее (см. главу 2). Не предупредил — и это читалось как незнание, а не как переключение контекста.
- 👎 **Ошибка с порядком условий — единственная содержательная**, и она была бы простительна в любой другой ситуации. Классическая ловушка FizzBuzz: самое узкое условие должно проверяться первым, иначе кратное 14 «съедается» веткой двойки. Илья сформулировал это отлично: «ты поднял условие выше — это такая воронка более узкая». Но на фоне пяти синтаксических подсказок эта ошибка уже не читалась как «задумался о логике».
- 👎 **Не проверил результат сам.** Проверку сделал только после того, как Илья предложил «давай попробуем потестить». Для тестировщика это плохой сигнал: первым порывом человека, который тестирует за деньги, должно быть «сейчас прогоню и посмотрю на 14 и 28».
- 👍 **Держался спокойно.** Не паниковал, не оправдывался, проговаривал мысли вслух, подсказки принимал без обиды. Дошёл до рабочего решения. Это единственное, что здесь сработало в плюс, и это не пустяк — многие в такой ситуации закрываются.
- 👍 **Сам заметил дефект вывода:** «28 должен делиться ещё на 7, он наложился из-за того, что делится на 2». Диагностику провёл верно, хоть и с подсказкой по исправлению.

**Эталонное решение (то, что должно писаться за 90 секунд, не задумываясь):**

```python
for i in range(1, 101):
    if i % 2 == 0 and i % 7 == 0:
        print("bizone")
    elif i % 2 == 0:
        print("bi")
    elif i % 7 == 0:
        print("zone")
    else:
        print(i)
```

**Как это надо было проговаривать вслух** (проговаривание — половина оценки на лайвкодинге):

> Иду циклом `range(1, 101)` — верхняя граница не включается, поэтому 101, чтобы сотня попала.
>
> Кратность проверяю остатком: `i % 2 == 0`.
>
> Порядок условий важен: комбинированное условие ставлю **первым**, иначе число 14 попадёт в ветку двойки и до третьего правила не дойдёт. Правило от узкого к широкому.
>
> Последняя ветка — `else`, само число.
>
> Проверю на контрольных точках: 1 должна дать `1`, 2 → `bi`, 7 → `zone`, 14 → `bizone`, 28 → `bizone`, 49 → `zone`.

**Вариант с накоплением строки** — стоит знать, потому что часто спрашивают «а как ещё?»:

```python
for i in range(1, 101):
    word = ""
    if i % 2 == 0:
        word += "bi"
    if i % 7 == 0:
        word += "zone"
    print(word or i)
```

Здесь порядок условий уже не важен, комбинация собирается сама, а `word or i` печатает число, если строка пустая. Показать оба варианта и объяснить, чем второй лучше при добавлении третьего правила, — это ответ уровня «уверенный мидл».

**🔧 Что на самом деле проверяет FizzBuzz.** Никого не интересует, умеет ли кандидат считать остатки. Проверяются четыре вещи: (1) свободен ли синтаксис — то есть не тратится ли внимание на язык вместо задачи; (2) понимает ли человек порядок ветвлений; (3) проверяет ли себя на граничных значениях **до** того, как ему об этом скажут; (4) как ведёт себя, когда что-то не сходится. Кандидат прошёл только по четвёртому пункту.

## Глава 12. Лайвкодинг, задача 2: тест на ручку `/ip` 🔴

**Задача:** Илья дал ссылку на публичный Swagger. Ручка `/ip` возвращает JSON с IP-адресом и сообщением. «Хотим написать на неё тестик. Опять же, без классов, в формате скрипта. Дёргаем запрос, получаем ответ, что-то из него проверяем — статус-код, IP».

**Как это прошло.** Заметно лучше первой задачи, но с двумя заминками:

1. **`requests.json` вместо `response.json()`.** Кандидат обратился к методу у модуля, а не у объекта ответа. IDE подчеркнула, Илья дал наводящий вопрос: «Что такое `requests.json`? Из чего она его должна преобразовать?» — и затем прямо: «Он говорит, что в модуле `requests` нет никакого `json`». После этого кандидат исправил.
2. **Тест не запускался.** PyCharm не собирал файл — конфигурация запуска считала его pytest-файлом, а тестов не находила. Потеряли около трёх минут, пока Илья не предложил перенести код в scratch-файл и запустить как обычный скрипт. Здесь вины кандидата почти нет — это среда, — но он и не диагностировал причину сам («не подхватил», «пустой набор»).

Дальше всё пошло нормально: получили JSON, обратились к нему как к словарю (Илья подсказал: «дата — это как словарик»), вытащили `ip`, захардкодили ожидаемое значение, обернули в `assert`. И финальный, самый правильный шаг встречи — **Илья предложил специально сломать ассерт**, поменяв один символ в IP, чтобы убедиться, что проверка вообще работает. Кандидат сразу понял смысл: «Сломалось. Да».

**Оценка:** 🔴 с оговорками

- 👍 Общая канва верная: импорт, запрос, `assert` на статус-код, десериализация, проверка значения. Слово «десериализовали» прозвучало от кандидата — терминология своя.
- 👍 Понял и одобрил идею проверить сам ассерт на сломанном ожидании. Это признак тестировщика.
- 👎 `requests.json` — ошибка не «синтаксическая», а **модельная**: она означает, что человек не держит в голове разницу между модулем, функцией и объектом ответа. Для API-автоматизатора на Python это базовый уровень.
- 👎 Не диагностировал проблему с запуском. Тестировщик, который не может понять, почему pytest не видит его тест, будет тратить на это время каждый день — а причин ровно три, и они известны.
- 👎 Не предложил ни одной дополнительной проверки. Ручка отдаёт IP и сообщение — там сразу просятся: формат IP по регексу или `ipaddress`, наличие обязательных ключей, `Content-Type`, время ответа. Илья явно оставлял место («что ты захочешь проверить»), кандидат ограничился минимумом, который сам же интервьюер и назвал.

**Эталонное решение:**

```python
import re
import requests

BASE_URL = "https://api.example.com"


def test_ip_returns_client_address():
    response = requests.get(f"{BASE_URL}/ip", timeout=10)

    assert response.status_code == 200
    assert response.headers["Content-Type"].startswith("application/json")

    data = response.json()

    assert "ip" in data
    assert re.fullmatch(r"(\d{1,3}\.){3}\d{1,3}", data["ip"])
    assert data["ip"] == "195.133.83.1"
```

**Что стоило сказать вслух после того, как тест позеленел:**

> Здесь я захардкодил конкретный IP, и это осознанный компромисс для демонстрации: в реальном проекте так делать нельзя — тест сломается при запуске с другой машины или из CI. Правильнее проверять **контракт**, а не значение: что поле `ip` присутствует, что оно строка и что оно похоже на IP-адрес. А если нужен именно точный адрес — брать его из конфига окружения, а не из тела теста.
>
> И раз речь про контракт: в проекте я бы не писал такие проверки руками, а описал модель на Pydantic и валидировал ей весь ответ — тогда падение будет говорить «поле пропало» или «тип изменился», а не «assert False».
>
> ```python
> from pydantic import BaseModel, IPvAnyAddress
>
> class IpResponse(BaseModel):
>     ip: IPvAnyAddress
>     message: str
>
> def test_ip_contract():
>     response = requests.get(f"{BASE_URL}/ip", timeout=10)
>     assert response.status_code == 200
>     IpResponse.model_validate(response.json())
> ```

**🔧 Почему pytest не видит тест — три причины, которые надо знать наизусть:**

1. **Имя файла** не начинается с `test_` и не заканчивается на `_test.py`.
2. **Имя функции** не начинается с `test_` (или класс не начинается с `Test`, или у класса есть `__init__`).
3. **Запускается не pytest**, а обычный скрипт — тогда функция просто определяется и не вызывается. Ровно это и произошло: Илья сказал «ты написал функцию, а вызова её нет — он не знает, что это тест».

Плюс частая четвёртая: `testpaths` или `python_files` переопределены в `pytest.ini`, и файл не попадает под маску. Диагностика в одну команду: `pytest --collect-only -q`.

## Глава 14. Zod, Pact, Pydantic — что это такое

**Вопрос:** «А что такое вот Zod и Pact? Это что такое?»

**Что ответил:** Zod — инструмент для контрактного тестирования: проверяем, соответствуют ли приходящие JSON-объекты спецификации, как они прописаны в Swagger. Для Python это было бы по аналогии — Pydantic. Позже, отвечая на другой вопрос, добавил точное сравнение: «Если в Zod какое-то поле было бы опциональное, мы бы закрыли его вопросиком, а здесь обозначили бы `Optional`. Подходы одни и те же, разный синтаксис».

**Оценка ответа:**

- 👍 По сути верно и сформулировано компактно. Сравнение Zod ↔ Pydantic через опциональные поля — хорошая деталь, она показывает, что человек писал схемы руками, а не слышал название.
- 👍 Правильно связал с Swagger как источником истины.
- 👎 **Zod — это не «инструмент для контрактного тестирования».** Zod и Pydantic — библиотеки **валидации схем**. Контрактное тестирование в узком смысле — это Pact: проверка совместимости между потребителем и поставщиком с брокером контрактов. Кандидат сам назвал Pact отдельно, но термин применил к обоим, и получилась путаница в понятиях.
- 👎 Про Pact не сказано ничего конкретного, кроме «для версионирования» — а на продукте, где сервис общается с инсталляциями разных версий, это самая интересная тема, и её можно было развернуть.

**Идеальный ответ:**

> Это два разных уровня, их часто путают.
>
> **Zod и Pydantic — валидация схемы.** Описываешь ожидаемую структуру ответа как модель, прогоняешь через неё JSON: не то поле, не тот тип, пропало обязательное — падаем сразу и с понятным сообщением, а не через десять строк на `KeyError`. Это проверка «сервис отдал то, что обещал в Swagger». Zod в TypeScript, Pydantic в Python — разница синтаксическая: опциональное поле в Zod это `.optional()`, в Pydantic — `Optional[str] = None`.
>
> **Pact — контрактное тестирование в строгом смысле.** Здесь проверяется не форма одного ответа, а **совместимость двух сторон**: потребитель описывает, что ему нужно от поставщика, контракт публикуется в брокер, и поставщик на своей стороне прогоняет верификацию. Смысл в том, что поставщик узнаёт о поломке совместимости до релиза, а не когда клиент упал в проде.
>
> И вот под ваш продукт это ложится прямо: у вас сервис обновлений разговаривает с инсталляциями разных версий, которые обновляются не одновременно. Классическая ситуация для потребительских контрактов — сервис новый, коробка у клиента старая. Проверять это схемой одного ответа мало, нужна матрица версий.

## Глава 15. Тест на удаление товара: где API, где UI

**Вопрос Ильи:** «Представим, у нас тест на удаление товара из корзины. Должна быть подготовка данных — положили товар в корзину; потом через UI хотим зайти в интерфейс, нажать кнопку, убрать товар, подтвердить. Как это будет выглядеть — когда мы API дёргаем, когда с UI взаимодействуем?»

**Что ответил:** то, что нужно проверять через UI, принципиально дёргаем через UI — в этом суть: если тестируем кнопки, мы их нажимаем в браузере. А то, что можно ускорить, — делаем по API, чтобы распараллелить тесты и сократить время прогонов. Методы называем так, чтобы было видно, что это API: например, `add_to_cart_one_item`. Смешивать не надо, нужно помнить о цели теста. Плюс, отвечая раньше на смежный вопрос, добавил: если нужно положить в корзину 200 товаров, это делается циклом по API, а не двумястами кликами, и всё это лежит в отдельном классе `Cart` с методами — тест остаётся читаемым.

**Реакция интервьюера:** «Нет-нет, всё правильно, всё правильно, всё круто».

**Оценка ответа:**

- 👍 **Лучший содержательный ответ встречи.** Назван главный принцип автоматизации: **подготовка — через API, проверяемое действие — через UI**. С обоснованием: скорость, параллелизация, стабильность.
- 👍 Отдельно ценно про **именование**: чтобы в теле теста было видно, где API, а где UI. Это уже забота о читаемости чужими глазами — признак человека, который проходил код-ревью.
- 👍 Пример с 200 товарами — конкретный и убедительный.
- 👎 Не назван **самый сильный аргумент** в пользу такой схемы: подготовка через UI делает тест хрупким по чужой вине. Если сломается страница добавления товара, упадут все тесты удаления — и по отчёту будет непонятно, что именно сломалось. Подготовка через API даёт **точную локализацию отказа**: падает только то, что действительно проверялось.
- 👎 Не проговорена обратная сторона — что при подготовке через API мы **не проверяем** путь добавления, и на него нужен отдельный UI-тест. Иначе можно всё «оптимизировать» до состояния, когда UI не тестируется вовсе.

**Идеальный ответ:**

> Правило простое: **через UI делаем только то, что и есть предмет теста; всё остальное — через API.**
>
> Для теста на удаление это:
>
> 1. **Setup через API.** Фикстура создаёт пользователя и кладёт товар в корзину одним запросом. Быстро, стабильно, не зависит от вёрстки.
> 2. **Действие через UI.** Открываем корзину, жмём «удалить», подтверждаем в модалке. Это и есть то, ради чего тест написан.
> 3. **Проверка на двух уровнях.** На UI — что товара в списке нет и счётчик обнулился. И следом по API — что корзина действительно пуста на бэкенде. Второе важно: интерфейс может убрать элемент оптимистично, а запрос — упасть.
> 4. **Teardown через API.** Чистим за собой корзину и пользователя.
>
> Главный аргумент за такую схему — не только скорость. Это **локализация отказа**: если подготовку делать кликами, то поломка страницы добавления уронит все тесты удаления, и отчёт будет врать о причине. При подготовке через API падает ровно то, что действительно сломано.
>
> Обратную сторону тоже назову: раз мы обошли добавление через API, значит на него нужен отдельный UI-тест. Иначе однажды окажется, что кнопка «в корзину» не покрыта вообще.

## Глава 16. Код-стайл: иерархия селекторов в Playwright

**Вопрос Кати:** «А каким ты код-стайл видишь? Какие правила тебе нужно описать?» Илья добавил: «Давай, я как раз больше UI занимаюсь, мне интересно».

**Что ответил:** если Playwright — «раздолье по сравнению с Selenium»: код лаконичнее, есть автовейты. Основная работа в код-стайле — селекторы и их приоритизация. Первым делом всё, что можно, выделяем через `getByRole`. То, что не кликается или спрятано в модальных окнах и мешает нажатию, — берём через скоупинг по родителям в ветке DOM-дерева.

**Оценка ответа:**

- 👍 **Отвечал уверенно и предметно** — видно, что это его территория. После проваленного pytest-блока этот ответ заметно выправил впечатление.
- 👍 `getByRole` как приоритет — правильный и «книжный» ответ, ровно то, что рекомендует документация Playwright.
- 👍 Скоупинг по родителям вместо индексов — признак человека, который боролся с флаком.
- 👎 **Иерархия названа не полностью.** Прозвучали первый и последний пункты, а середина — `data-testid`, `getByLabel`, `getByText` — пропущена. При этом в прошлых разборах `data-testid` был одним из главных якорей легенды (кандидат «продавил внедрение data-testid у фронтенда»). Здесь он не прозвучал вообще.
- 👎 Код-стайл сведён к селекторам. А спрашивали шире: это ещё и структура папок, именование тестов и методов, что можно и что нельзя в page object, где живут ассерты, длина теста, обязательность ожиданий, запрет на `sleep`, требования к атомарности.
- 👎 Ничего не сказано про **Python-специфику** код-стайла, хотя проект будет питоновский: PEP 8, `black`, `ruff`, `isort`, аннотации типов, pre-commit хуки. Для команды, где автотестов нет вообще, «я принесу линтер и pre-commit» — очень весомый аргумент.

**Идеальный ответ:**

> Код-стайл я бы разложил на четыре части.
>
> **1. Иерархия селекторов** — самое важное, потому что отсюда растёт весь флак. Порядок такой:
> `getByRole` с именем → `data-testid` → `getByLabel` / `getByPlaceholder` → `getByText` → CSS. Никаких XPath, никаких индексов вроде `nth(3)`, никакой привязки к тексту, который меняет продакт. Если элемент неоднозначен — не индекс, а **скоупинг по родителю**: сначала находим карточку или модалку, потом ищем внутри неё.
> Отдельным пунктом — договорённость с фронтендом о `data-testid` на ключевых элементах. В T-банке я это продавливал, и точечные правки локаторов упали с нескольких в неделю до единичных.
>
> **2. Структура и слои.** Page object содержит локаторы и действия, ассертов в нём нет. Повторяющиеся блоки — сайдбары, модалки, таблицы — выносятся в компоненты. Тест не обращается к локаторам напрямую.
>
> **3. Ожидания.** `sleep` запрещён как класс. Ждём состояние, а не время: `expect(locator).to_be_visible()`, а не `time.sleep(2)`. Явные таймауты — только там, где это осознанно.
>
> **4. Питоновская часть.** PEP 8, форматирование `black`, линт `ruff`, сортировка импортов, аннотации типов в page object и в API-клиенте, всё это в pre-commit хуках, чтобы стиль проверялся до ревью, а не на ревью. Для команды, которая начинает с нуля, это стоит настроить в первую же неделю: потом договориться будет дороже.
>
> И правило поверх всего: документация пишется до того, как в проект зайдёт второй человек. У вас сейчас QA один, но приходящая тестировщица уже есть, а дальше команда вырастет.

## Глава 17. Автовейты, accessibility tree и кнопка с атрибутом `active` 🟠

**Вопрос Ильи (часть первая):** «На что Playwright вообще завязывается, когда пытается понять, кликабелен элемент или нет?»

**Что ответил:** на accessibility tree — в отличие от Selenium, работает по дереву доступности, по ролям; в DevTools это видно; поэтому документация советует делать селекторы на `getByRole`.

**Вопрос (часть вторая, и он был главным):** «А если у сущности в дереве какой-то баттон, и то, что он активен или неактивен, обозначается через атрибут `active=true` / `active=false`? Как мы Playwright объясним, что именно так надо разделять кликабельное от некликабельного? Тут автовейт нам поможет или нет?»

**Что ответил:** можно сделать ассершен непосредственно на этот элемент — кликабельный он или нет: сначала выделить, потом проверка. Можно вешать проверки на видимость и кликабельность и только потом пропускать действие, чтобы тест сломался в этом месте. И следом: «Это автовейтом, кстати, делается в Playwright под капотом. Playwright под капотом дожидается видимости и кликабельности элемента, дополнительных проверок, как в Selenium, писать не нужно».

**Оценка ответа:** 🟠

- 👍 Первая часть — верно. Playwright действительно опирается на роли и accessibility tree, и `getByRole` действительно рекомендован документацией.
- 👍 Направление во второй части нащупано правильно: «сделать явную проверку перед действием» — это и есть ответ.
- 👎 **Но вывод сделан ровно противоположный.** Финальная фраза «это автовейт делает под капотом, дополнительных проверок писать не нужно» — неверна именно для того случая, про который спрашивали. Playwright понимает **стандартные** признаки: `disabled`, `aria-disabled`, `pointer-events`, перекрытие другим элементом. **Кастомный атрибут `active="false"` для него — просто атрибут**, кнопка остаётся с точки зрения фреймворка кликабельной, и клик пройдёт.
- 👎 Кандидат сначала дал правильную мысль, потом сам её перечеркнул. Похоже, сработал заготовленный тезис «в Playwright всё под капотом» — и он выстрелил не в ту сторону. Это типичная ловушка: интервьюер спрашивает про исключение, а отвечают правилом.

**Идеальный ответ:**

> Автовейт здесь **не поможет**, и это важный нюанс. Playwright перед действием проверяет actionability по стандартным признакам: элемент виден, стабилен (не анимируется), принимает события и enabled. Но «enabled» он определяет по HTML — атрибут `disabled` или `aria-disabled` на нативном контроле. Ваш `active="false"` для него ничего не значит: это произвольный атрибут, кнопка будет считаться кликабельной, и клик пройдёт по неактивной кнопке. Тест позеленеет там, где должен упасть — а это худший вид дефекта в автоматизации.
>
> Решать можно на трёх уровнях, по убыванию правильности.
>
> **Первое, самое правильное — договориться с фронтендом.** Попросить вешать `disabled` или хотя бы `aria-disabled="true"` в дополнение к своему атрибуту. Это чинит не только тесты, но и доступность: скринридер тоже не понимает `active="false"`. Такой ответ ценят, потому что он про качество продукта, а не про костыль в тестах.
>
> **Второе — явное ожидание перед действием.** Раз фреймворк не знает нашей семантики, мы объясняем её сами:
>
> ```python
> expect(button).to_have_attribute("active", "true")
> button.click()
> ```
>
> `expect` тоже перепроверяет условие до таймаута, так что это не `sleep`, а честное ожидание состояния.
>
> **Третье — инкапсулировать в page object,** чтобы правило не размазалось по тестам:
>
> ```python
> class ProductCard:
>     def click_when_active(self):
>         expect(self.button).to_have_attribute("active", "true")
>         self.button.click()
> ```
>
> Тогда в тестах никто не сможет случайно кликнуть в обход проверки, а если фронт когда-нибудь перейдёт на `disabled`, правка будет в одном месте.
>
> И для негативных сценариев зеркальная проверка: `expect(button).to_have_attribute("active", "false")` — убедиться, что кнопка действительно заблокирована, когда должна быть.

**🔧 Почему этот вопрос был лучшим на встрече.** Илья спросил не «знаешь ли ты, что такое автовейт», а «понимаешь ли ты его **границы**». Разница между «слышал про фичу» и «эксплуатировал её и знает, где она ломается» — как раз здесь. Это стандартный приём хорошего интервьюера, и к нему надо быть готовым: на любой вопрос «а автовейт/ретрай/фреймворк это сам сделает?» правильная реакция — сначала подумать «а точно ли этот случай попадает в стандартный механизм».

## Глава 18. Kafka и проверка бизнес-логики

**Контекст:** Илья описал, чего ждут от API-тестов: «нам нужно всю бизнес-логику проверять — что она правильно создалась, что в разных местах создалось. Плюс у нас реально где-то Kafka есть, тоже проверять, что это ушло. У нас не очень много методов, которые просто возвращают простой ответ, — там именно бизнес-логика на постах, и в некоторых местах она весьма сложная».

**Что ответил:** на текущем проекте работают с Kafka: делают проверки по сообщениям, которые завязаны на события. Фронтенд инициирует событие, есть модули БКИ и ФНС, которые персонифицируют страницу в зависимости от бизнес-ролей и статусов клиентов, и часть проверок в E2E делается на Kafka: используется библиотека KafkaJS, она по API взаимодействует с Kafka, и вешаются проверки, что сообщение с нужным уникальным ID или с нужным содержимым появилось.

**Оценка ответа:**

- 👍 **Прямое попадание в их стек.** Kafka у них есть, асинхрон есть, и опыт кандидата ложится один в один.
- 👍 Проверка **по уникальному ID сообщения** — правильная и зрелая техника. Наивный подход «прочитать последнее сообщение из топика» разваливается при параллельных прогонах, и кандидат этой ошибки не сделал.
- 👎 Не проговорена механика **ожидания**: сообщение появляется не мгновенно, значит нужен поллинг с таймаутом, и это самое частое место флака в асинхронных проверках. Слово «eventual consistency» звучало раньше, но здесь его стоило повторить и раскрыть.
- 👎 Не сказано про офсеты и группы консьюмеров — как именно тест читает топик, не мешая другим. У кандидата есть отдельный конспект по Kafka; на встрече он не пригодился.
- 👎 Не связал с их доменом, хотя связь напрашивалась: телеметрия с инсталляций и уведомления об обновлениях — это ровно очереди, и там живут дубликаты, потеря части сообщений и нарушение порядка доставки.

**Идеальный ответ:**

> С Kafka работал на текущем проекте: часть E2E-сценариев завершается не проверкой на UI, а проверкой сообщения в топике.
>
> Механика такая. Перед действием фиксирую момент — офсет или временную метку. Выполняю действие. Дальше **поллинг с таймаутом**: читаю сообщения и ищу своё по уникальному идентификатору, который сам же передал в запросе. Не «последнее сообщение в топике» — при параллельных прогонах это чужое сообщение. Найдено — валидирую payload схемой. Не найдено за таймаут — падаем с внятным сообщением: «событие X не появилось за N секунд».
>
> Ключевое, что здесь надо понимать: это асинхрон, и любая жёсткая пауза даёт либо флак, либо потерю времени. Поэтому только ожидание с ретраями.
>
> На Python это `kafka-python` или `confluent-kafka` вместо KafkaJS, с отдельной consumer group для тестов, чтобы не сдвигать офсеты рабочим консьюмерам.
>
> И под ваш продукт: телеметрия с инсталляций и рассылка обновлений — это как раз очереди, и я бы сразу закладывал тесты на три классические беды асинхрона: **дубликат** сообщения (обработчик должен быть идемпотентным), **потеря** части данных и **нарушение порядка** доставки. Плюс сценарий «инсталляция была офлайн в момент выкатки» — что произойдёт, когда она вернётся.

- 👍 Гипотезы про протухшие креды и разлогин — практичные, из реального опыта.
- 👎 **403 нашлась только с подсказкой.** Первый заход дал «пятисотая, ошибка на сервере» — то есть кандидат прочитал верхнюю строку и остановился. Разбор лога — это работа снизу вверх и по всей длине, а не по первой заметной строке.
- 👎 Не назван **главный вывод для тестировщика**: если внутренний сервис получил 403 от зависимости и вернул наружу 500 — это **дефект обработки ошибок**. Корректное поведение — вернуть 403 (или 401) с внятным телом, а не маскировать чужой отказ доступа под внутреннюю ошибку. Это баг, и его надо заводить.
- 👎 Не прозвучало, как связь **доказывается**: по времени, по trace-id, по последовательности вызовов. «Я думаю, первопричина в этом» — это гипотеза, а тестировщика ценят за то, что он умеет её подтвердить.

**Идеальный ответ:**

> Вижу две ошибки. Первая — 403 Forbidden на запрос к ресурсу: сервер понял, кто мы, но доступ запрещён. Вторая — 500 в методе `RunTasks`.
>
> Гипотеза: это одна цепочка. Сервис пошёл за данными в зависимость, получил 403, не обработал его и упал с необработанным исключением — наружу ушло 500.
>
> Проверил бы это тремя способами: по времени — 403 должен предшествовать 500 с разницей в миллисекунды; по trace-id или correlation-id, если он в логах есть — это самый надёжный признак; и по стектрейсу пятисотки — там должно быть видно, что исключение пришло из клиента к внешнему сервису, а не из бизнес-логики.
>
> И вывод, который для меня как тестировщика важнее самой причины: **здесь два дефекта, а не один.**
>
> Первый — почему нет доступа: протухший токен, недостаточная роль, неверный скоуп, сервисная учётка без прав.
>
> Второй — **сервис неправильно обрабатывает отказ зависимости.** Ответ 500 на чужой 403 — это маскировка: клиент видит «у вас всё сломалось» вместо «у вас нет прав», не может ничего исправить, а поддержка идёт разбирать несуществующую аварию. Правильное поведение — пробросить осмысленный код и тело ошибки. Этот баг я бы завёл отдельно, даже если доступ починят.

## Глава 20. Разница между 401 и 403

**Вопрос:** «Есть 403, а есть 401. Какая между ними разница?»

**Что ответил:** «401 — что ты вообще не авторизован, сервер говорит, что нужно предъявить свою авторизацию в принципе. А 403 — что ты авторизован, но твои права доступа не позволяют тебе прийти сюда».

**Оценка ответа:**

- 👍 **Чётко, коротко, правильно.** Единственный ответ за встречу, который не потребовал ни одного уточняющего вопроса. Ровно то, что хотели услышать.
- 👍 Формулировка «предъявить авторизацию» близка к канонической: 401 означает отсутствие или невалидность аутентификационных данных.
- 👎 Придраться можно только к одному, и это совсем тонко: 401 в стандарте называется `Unauthorized`, но по смыслу это **Unauthenticated** — «не аутентифицирован», а 403 — как раз про авторизацию. Знать эту путаницу в названиях полезно, потому что её любят спрашивать на следующем уровне.

**Идеальный ответ (расширение на всякий случай):**

> 401 — «я не знаю, кто ты»: токена нет, он невалиден или истёк. Правильная реакция клиента — пройти аутентификацию заново; по стандарту сервер должен отдать заголовок `WWW-Authenticate` с тем, как именно.
>
> 403 — «я знаю, кто ты, и тебе сюда нельзя»: аутентификация прошла, но прав на ресурс нет. Повторный логин не поможет, нужны другие права.
>
> Терминологический курьёз: в стандарте 401 называется `Unauthorized`, хотя по смыслу это «не аутентифицирован», а «не авторизован» — это как раз 403.
>
> И практическая деталь для тестирования безопасности: иногда вместо 403 намеренно отдают **404**, чтобы не подтверждать существование ресурса пользователю без прав. Это осознанное решение, и его стоит уточнять у аналитика, а не считать багом.

# Анатомия провала: почему лайвкодинг сложился именно так

Отдельная глава, потому что без неё разбор превращается в перечень ошибок, а нужен вывод.

**Предупреждение было. Письменное, за два дня.** В разборе HR-скрининга от 24 августа глава 15 называлась «Главная дыра встречи: Python/pytest не закрыт 🔴» и содержала дословно: *«На лайвкодинге не получится говорить абстрактно: там надо написать код на Python, и либо вы пишете `@pytest.fixture` и `@pytest.mark.parametrize` не задумываясь, либо нет»*. Чек-лист начинался с двух красных пунктов: pytest-синтаксис до автоматизма и Python-минимум. Ни один не был выполнен в объёме, достаточном хотя бы для FizzBuzz.

**Три сигнала от рекрутёра были проигнорированы ещё раньше:** «важно тестирование на Python с использованием pytest», «после опыта тестирования на pytest важно умение автоматизировать UI», «тест-дизайн точно будет, pytest точно будет, тестирование на Python будут спрашивать». Реакция была — «понял».

**Почему так вышло — три причины, и ни одна не про способности.**

**1. Иллюзия переносимости.** Кандидат искренне считает — и говорил это вслух на встрече, — что «подходы одни и те же, разный синтаксис», что достаточно «за дня три сделать перенос в голове». Это верно для **архитектуры** и неверно для **письма**. Понимать код и писать код — разные навыки, они тренируются по-отдельности, и второй не появляется от чтения. Двоеточие после `if` не вспоминается, оно набивается пальцами.

**2. Подготовка шла в сторону силы, а не слабости.** Судя по файлам подготовки, время вкладывалось в Kafka, Docker, 2PC, контрактное тестирование, тест-дизайн — темы, где кандидат и так силён и где приятно готовиться. Слабое место требовало скучной механической работы: сесть и написать двадцать тестов на pytest руками. Это классическая ловушка подготовки — учить то, что уже знаешь, потому что это даёт ощущение прогресса.

**3. Не была поставлена честная рамка.** Это единственная ошибка, которая **ничего не стоила бы** и полностью изменила бы восприятие. Одна фраза в начале — «боевой стек последних двух лет TypeScript, Python знаю, но пишу на нём редко, синтаксис буду подглядывать» — превратила бы каждую последующую запинку из «не знает» в «предупреждал». Более того, интервьюер после такой рамки обычно **сам** снижает планку по синтаксису и смотрит на логику. Илья это фактически и попытался сделать, дважды предложив перейти на TypeScript — кандидат отказался и остался в Python. Решение смелое, но без рамки оно сыграло против него.

**Что оказалось хуже самого незнания.** Последовательность реплик выглядела так: «на Python работал, был коммерческий опыт» → через двадцать минут не поставил двоеточие после `if`. Между этими двумя фактами интервьюер обязан выбрать интерпретацию, и по умолчанию он выберет не «человек забыл», а «человек преувеличил». Дальше срабатывает эффект переноса: если преувеличил здесь, то, может, и 80% покрытия — не его цифра (тем более что на вопрос про неё ответ был мутный), и 300 E2E-сценариев тоже. Так одна незакрытая слабость обесценивает сильную часть, которая была настоящей.

# Приложение 1. Эталонный FizzBuzz и его вариации

Выучить до состояния «пишется без раздумий». Проверено запуском.

**Вариант 1 — через ветвления (самый ожидаемый):**

```python
for i in range(1, 101):
    if i % 2 == 0 and i % 7 == 0:
        print("bizone")
    elif i % 2 == 0:
        print("bi")
    elif i % 7 == 0:
        print("zone")
    else:
        print(i)
```

Ключевое правило: **самое узкое условие — первым**. Иначе 14 и 28 уйдут в ветку двойки.

**Вариант 2 — через накопление строки (масштабируется лучше):**

```python
for i in range(1, 101):
    word = ""
    if i % 2 == 0:
        word += "bi"
    if i % 7 == 0:
        word += "zone"
    print(word or i)
```

Порядок условий здесь не важен, а добавление третьего правила — это ещё три строки, а не переписывание всей лесенки. `word or i` печатает число, когда строка пустая.

**Вариант 3 — если попросят с числом рядом:**

```python
for i in range(1, 101):
    if i % 2 == 0 and i % 7 == 0:
        print(f"{i} bizone")
    elif i % 2 == 0:
        print(f"{i} bi")
    elif i % 7 == 0:
        print(f"{i} zone")
    else:
        print(i)
```

**Контрольные точки для самопроверки** (называть вслух до запуска): 1 → `1`, 2 → `bi`, 7 → `zone`, 14 → `bizone`, 28 → `bizone`, 49 → `zone`, 98 → `bizone`, 100 → `bi`.

**Синтаксис, на котором были подсказки — выписать и не забывать:**

| Что | Python | TypeScript |
|---|---|---|
| Конец строки | ничего | `;` |
| Блок | `:` и отступ | `{ }` |
| Сравнение | `==` | `===` |
| Присваивание | `=` | `=` |
| Иначе-если | `elif` | `else if` |
| Интерполяция | `f"{i} bi"` | `` `${i} bi` `` |
| Остаток | `%` | `%` |
| Цикл по диапазону | `for i in range(1, 101):` | `for (let i = 1; i <= 100; i++)` |
| Логическое И | `and` | `&&` |
| Отрицание | `not` | `!` |

# Приложение 2. Шпаргалка по `scope` фикстур

То, на чём встреча сломалась. Знать наизусть.

```python
@pytest.fixture(scope="session")   # один раз за прогон
@pytest.fixture(scope="package")   # на каждый пакет тестов
@pytest.fixture(scope="module")    # на каждый файл
@pytest.fixture(scope="class")     # на каждый класс
@pytest.fixture                    # по умолчанию function — на каждый тест
```

**Жизненный цикл:**

```python
@pytest.fixture(scope="session")
def test_user(users_api):
    user = users_api.create(role="admin")   # setup — до yield
    yield user                              # отдаём тесту, ждём
    users_api.delete(user.id)               # teardown — после последнего теста
```

Код после `yield` выполняется **даже если тест упал** — это `try/finally`, оформленный синтаксисом генератора.

**Что куда класть:**

| Ресурс | scope | Почему |
|---|---|---|
| Браузер | `session` | дорого поднимать |
| Контекст браузера / страница | `function` | нужна изоляция куки и состояния |
| Токен авторизации | `session` | не логиниться на каждый тест |
| Конфиг, API-клиент | `session` | неизменны в прогоне |
| Справочные данные (только чтение) | `session` / `module` | не меняются |
| Тестовые данные, которые тест правит | `function` | иначе тесты зависят от порядка |

**Пять фактов, которые спросят следом:**

1. **ScopeMismatch** — широкая фикстура не может зависеть от узкой; pytest упадёт до тестов.
2. **Видимость ≠ время жизни** — за видимость отвечает `conftest.py`, за время жизни `scope`.
3. **Ленивость** — фикстура выполняется при первом обращении, а не в начале прогона.
4. **`autouse=True`** — применяется ко всем тестам в области видимости без объявления в аргументах.
5. **`pytest-xdist`** — каждый воркер отдельный процесс со своей сессией; для общего ресурса нужна синхронизация через `FileLock` на `tmp_path_factory.getbasetemp().parent`.

Инженерная часть переносится один в один — если по ходу будет что-то, где мне нужна секунда на вспомнить, я скажу прямо.

Почему это работает:

- **Снимает главный риск интерпретации.** Запинка после такой фразы читается как «предупреждал», без неё — как «преувеличил в резюме». Факты те же, вывод противоположный.
- **Переключает интервьюера на логику.** Многие после такой рамки сознательно перестают ловить на синтаксисе и начинают смотреть на подход — то есть на вашу сильную сторону.
- **Стоит десять секунд** и не требует ничего, кроме решимости её произнести.

**Таблица соответствий, которую полезно держать в голове и озвучивать** — она превращает «не знаю Python» в «знаю то же самое другими словами»:

| TypeScript + Playwright | Python + pytest |
|---|---|
| Page Object (класс) | Page Object (класс) — один в один |
| фикстуры Playwright `test.extend` | `@pytest.fixture` в `conftest.py` |
| `beforeEach` / `afterEach` | фикстура `function`-scope с `yield` |
| `beforeAll` / `afterAll` | фикстура `session`/`module`-scope |
| data-driven через массив + `forEach` | `@pytest.mark.parametrize` |
| `test.describe` | класс `TestSomething` |
| `test.skip` / `test.fixme` | `@pytest.mark.skip` / `xfail` |
| `expect(locator).toBeVisible()` | `expect(locator).to_be_visible()` |
| `.not.toBeVisible()` | `.not_to_be_visible()` |
| Axios / `request` | `requests` |
| Zod | Pydantic |
| KafkaJS | `kafka-python` / `confluent-kafka` |
| `playwright.config.ts` | `pytest.ini` + `conftest.py` |
| `npx playwright test --grep` | `pytest -k` / `-m` |
| воркеры Playwright | `pytest-xdist -n` |

**Главный вывод файла.** Разрыв между тем, что вы умеете как инженер, и тем, что вы можете показать на Python, — единственная причина этого исхода. Он закрывается не пониманием, а часами за клавиатурой: две недели по часу в день, и такой этап проходится спокойно. Всё остальное — архитектура, домен, асинхрон, чтение логов, поведение под давлением — у вас уже есть, и это подтвердил их же разработчик вслух.
