# A. pytest — самые вероятные вопросы

Это ядро этапа. Здесь надо отвечать без пауз.

### A1. «Что такое фикстура и зачем она нужна?»

> Фикстура — это подготовка состояния для теста и его уборка после. Тест не должен сам создавать себе окружение: он должен получить готовое. В pytest фикстура объявляется декоратором и запрашивается тестом по имени аргумента — это инъекция зависимости, а не глобальные переменные.
>
> Всё, что до `yield`, — setup; всё, что после, — teardown, и он выполнится даже если тест упал.

```python
import pytest

@pytest.fixture
def api_client():
    client = ApiClient(base_url=settings.BASE_URL)
    client.login(settings.USER, settings.PASSWORD)
    yield client                # тест работает здесь
    client.logout()             # выполнится даже при падении теста

def test_license_is_active(api_client):
    resp = api_client.get("/licenses/42")
    assert resp.status_code == 200
    assert resp.json()["status"] == "active"
```

### A2. «Какие бывают scope у фикстур?»

Пять: `function` (по умолчанию), `class`, `module`, `package`, `session`.

> Правило простое: скоуп выбирается по цене создания и по риску связности. Дорогое и неизменяемое — `session`: браузер, соединение с БД, токен. Всё, что тест меняет, — `function`, иначе тесты начнут влиять друг на друга и порядок запуска станет значимым, а это худший вид флака.

```python
@pytest.fixture(scope="session")
def browser():
    with sync_playwright() as p:
        browser = p.chromium.launch()
        yield browser
        browser.close()

@pytest.fixture(scope="function")
def page(browser):
    context = browser.new_context()   # чистое состояние на каждый тест
    page = context.new_page()
    yield page
    context.close()
```

**Вероятный добор:** «а если session-фикстура, а тесты бегут в несколько процессов через xdist?» → Каждый воркер — отдельный процесс, поэтому session-фикстура отработает **в каждом воркере**. Если внутри создаётся общий ресурс (запись в БД, файл), будет конфликт — нужен либо изолированный ресурс на воркер, либо блокировка.

### A3. «Что такое conftest.py?»

> Файл, куда выносятся фикстуры и хуки, общие для тестов в этой директории и всех вложенных. Импортировать его не надо — pytest подхватывает автоматически. Иерархия работает: корневой `conftest.py` для всего проекта, вложенный — для своего каталога, ближний переопределяет дальний.
>
> Практически: в корневом держу конфигурацию сред, клиентов, авторизацию; в `tests/ui/conftest.py` — браузерные фикстуры; в `tests/api/conftest.py` — HTTP-клиент.

### A4. «Как параметризовать тест?»

```python
@pytest.mark.parametrize(
    "days_left, expected_status",
    [
        (30, "active"),
        (1, "active"),
        (0, "expired"),      # граница
        (-1, "expired"),
    ],
    ids=["month", "last_day", "expiry_day", "after_expiry"],
)
def test_license_status(days_left, expected_status):
    assert license_status(days_left) == expected_status
```

> `ids` даю всегда — иначе в отчёте будет `test_license_status[0-active]`, и при падении непонятно, какой кейс упал.

**Вероятный добор:** «а если два декоратора parametrize?» → Получается декартово произведение: 3 значения × 2 значения = 6 тестов. Удобно для матриц «версия продукта × тип лицензии», но легко получить взрыв количества — тогда лучше явный список кортежей.

**Ещё добор:** «чем parametrize отличается от цикла внутри теста?» → Цикл — это один тест: упал первый кейс, остальные не проверились, и в отчёте одна строка. Parametrize — N независимых тестов, каждый со своим результатом. Для диагностики это принципиально.

### A5. «Что такое маркеры и зачем?»

```python
# pytest.ini
[pytest]
markers =
    smoke: критичные сценарии, гоняем на каждый пуш
    regress: полный набор, по расписанию
    slow: долгие тесты
```

```python
@pytest.mark.smoke
def test_login(): ...
```

Запуск: `pytest -m smoke`, `pytest -m "regress and not slow"`.

> Маркеры — это то, как строится гейт. Быстрый набор на пуш, полный ночью. Регистрирую их в `pytest.ini`, иначе pytest ругается на неизвестный маркер, и опечатка `@pytest.mark.smok` тихо создаст новый маркер вместо ошибки.

Плюс встроенные: `@pytest.mark.skip(reason=...)`, `@pytest.mark.skipif(sys.platform == "win32", reason=...)`, `@pytest.mark.xfail` — известный баг, тест ожидаемо красный, но не ломает прогон.

**Важная позиция, которую могут проверить:** `xfail` — для известного заведённого дефекта; `skip` — когда сценарий неприменим в этой среде. Использовать их, чтобы прятать нестабильные тесты, — нельзя, это скрытие проблемы.

### A6. «Как проверить, что код бросает исключение?»

```python
def test_invalid_license_key_raises():
    with pytest.raises(ValidationError) as exc_info:
        parse_license_key("not-a-key")
    assert "invalid format" in str(exc_info.value)
```

> Проверяю не только факт исключения, но и его содержание — иначе тест пройдёт на любой ошибке, в том числе на опечатке в коде теста.

### A7. «Какие встроенные фикстуры знаешь?»

- `tmp_path` — временная директория на тест, сама убирается.
- `monkeypatch` — подменить переменную окружения, атрибут, функцию на время теста.
- `caplog` — перехват логов, проверить, что нужное записалось.
- `capsys` — перехват stdout/stderr.
- `request` — метаданные о тесте, доступ к параметрам фикстуры.

```python
def test_uses_staging_url(monkeypatch):
    monkeypatch.setenv("BASE_URL", "https://staging.example.com")
    assert build_client().base_url == "https://staging.example.com"
```

### A8. «Как запускаешь тесты?»

```bash

pytest -x                            # остановиться на первом падении
```

# B. Python для автоматизатора

Спрашивать будут не язык целиком, а то, что реально всплывает в тестах.

**Точно надо уметь без запинки:**

```python
# comprehension'ы
active = [i for i in installations if i["status"] == "active"]
by_id = {i["id"]: i for i in installations}

# распаковка
first, *rest = versions
a, b = b, a

# f-строки
f"/api/v1/installations/{inst_id}/licenses"

# работа с JSON
import json
data = json.loads(raw)
payload = json.dumps({"version": "2.1.0"})

# классы для POM
class BasePage:
    def __init__(self, page):
        self.page = page

class LoginPage(BasePage):
    def login(self, user, password): ...
```

**Вопросы, которые любят задавать:**

- **«Изменяемые и неизменяемые типы?»** → Неизменяемые: `int`, `str`, `tuple`, `frozenset`. Изменяемые: `list`, `dict`, `set`. Практическое следствие для тестов — **мутабельный аргумент по умолчанию**:

```python
def add_tag(tags=[]):     # ❌ список создаётся ОДИН раз при определении функции
    tags.append("x")
    return tags

def add_tag(tags=None):   # ✅
    tags = tags or []
```

Это классическая ловушка, её любят на собесах.

- **«Разница между `is` и `==`?»** → `==` сравнивает значения, `is` — идентичность объекта. В ассертах почти всегда `==`; `is` уместен для `None`, `True`, `False`.

- **«Что такое декоратор?»** → Функция, которая оборачивает другую функцию, не меняя её код. Весь pytest на них построен — `@pytest.fixture`, `@pytest.mark.parametrize`. Уметь прочитать и объяснить достаточно; писать свой на собесе просят редко, но простой ретрай-декоратор стоит уметь набросать (см. блок G).

- **«Контекстный менеджер?»** → `with` — гарантирует освобождение ресурса. `with open(...)`, `with pytest.raises(...)`, `with sync_playwright()`.

- **«Как работать с API?»**

```python
import requests

resp = requests.get(url, headers={"Authorization": f"Bearer {token}"}, timeout=10)
resp.raise_for_status()
data = resp.json()
```

`requests.Session()` — когда нужны общие заголовки и переиспользование соединения.

# C. Тест-дизайн

Назван прямым текстом, значит будет обязательно. Отвечать **не определением из учебника, а применением к их продукту**.

### C1. Классы эквивалентности и граничные значения

> Эквивалентность — разбиваю входные данные на группы, где система ведёт себя одинаково, и беру по одному представителю из каждой. Границы — проверяю ровно на краях групп, потому что именно там живут ошибки на единицу.
>
> На вашем продукте: срок действия лицензии. Классы — активная, истекает сегодня, истекла, отозвана, отсутствует. Границы — последняя секунда перед истечением, момент истечения, первая секунда после. Отдельно — часовой пояс: истечение считается по UTC или по локали инсталляции? Это классический источник расхождения на сутки.

### C2. Таблица решений

> Когда результат зависит от комбинации нескольких условий, я строю таблицу: условия по строкам, комбинации по столбцам, ожидаемый результат внизу. Она сразу показывает, какие комбинации не описаны в требованиях.
>
> Пример для вас: применять ли обновление? Условия — лицензия активна, версия совместима, инсталляция онлайн, есть свободное место. Восемь-шестнадцать комбинаций, и часть из них наверняка в требованиях не расписана — вот это и есть находка на этапе анализа, ещё до кода.

### C3. Тестирование состояний и переходов

Это **ваш главный козырь на их домене** — доставка обновления по сути конечный автомат:

```
pending → downloading → downloaded → applying → applied
              ↓              ↓           ↓
           failed         failed      failed → rolled_back
```

> Проверяю не только счастливый путь, но и запрещённые переходы: можно ли из `failed` попасть в `applied` минуя `applying`; что происходит при обрыве связи в каждом состоянии; идемпотентен ли повтор — если команда «применить обновление» пришла дважды, применилось один раз или два.

### C4. Попарное тестирование (pairwise)

> Когда параметров много, полный перебор невозможен: пять параметров по четыре значения — это 1024 комбинации. Pairwise покрывает все пары значений примерно двумя десятками комбинаций, исходя из того, что большинство дефектов вызывается взаимодействием двух факторов, а не пяти.
>
> У вас это прямо просится: версия продукта × ОС инсталляции × тип лицензии × канал обновления.

### C5. Приоритизация: с чего начинать покрытие

> Не «покрыть всё», а по риску: вероятность отказа × цена отказа. Сначала critical path — то, что ломает продукт для клиента. Для вашего сервиса это, скорее всего, три вещи: инсталляция не получила обновление, лицензия неверно определена как истёкшая, телеметрия потеряна или задублирована. Дальше happy path остальных сценариев, потом расширение по impact-анализу.

### C6. Что ещё могут спросить

- **Smoke vs регресс:** smoke — узкий набор «система вообще работает», минуты, на каждый пуш; регресс — широкий, ловит деградацию, по расписанию.
- **Impact-анализ:** от изменения строю карту затронутых областей — какие модули, какие интеграции, какие сценарии, — и гоняю целевой регресс вместо полного.
- **Позитивные и негативные тесты:** негативных обычно больше, и они важнее — счастливый путь разработчик проверит сам.
- **Как оценить достаточность покрытия:** не процентом строк, а покрытием рисков и критичных путей. Покрытие кода — вспомогательная метрика, 90% покрытых строк с плохими ассертами хуже, чем 40% с хорошими.

# D. UI-автоматизация

### D1. «Как строишь Page Object?»

```python
class BasePage:
    def __init__(self, page):
        self.page = page

    def open(self, path=""):
        self.page.goto(f"{settings.BASE_URL}{path}")


class InstallationsPage(BasePage):
    SEARCH = "[data-testid='installations-search']"
    ROW = "[data-testid='installation-row']"
    STATUS = "[data-testid='installation-status']"

    def search(self, query):
        self.page.fill(self.SEARCH, query)
        self.page.press(self.SEARCH, "Enter")
        return self

    def status_of(self, name):
        row = self.page.locator(self.ROW, has_text=name)
        return row.locator(self.STATUS).inner_text()
```

> Правило: в Page Object — только взаимодействие со страницей и получение данных. **Ассертов внутри Page Object нет** — они в тесте, иначе страница начинает знать про ожидания и её нельзя переиспользовать.

### D2. «Какие локаторы предпочитаешь и почему?»

> Иерархия: `data-testid` → роль и доступное имя → текст → CSS → XPath в последнюю очередь.
>
> `data-testid` я договариваюсь ставить с разработкой — это дешевле, чем ловить падения после каждого рефакторинга вёрстки. XPath по абсолютному пути — худший вариант: ломается от любой вставки div. Локаторы по видимому тексту рискуют при локализации.

Это ровно тот аргумент, который зашёл на первом этапе в СБС, — он работает.

### D3. «Как борешься с флаком?»

Сильная позиция — и её любят проверять:

> Флак — это не «тест плохой», это сигнал. Сначала я классифицирую причину:
>
> **Ожидания.** Никаких `sleep`. Ждать надо состояние, а не время: элемент видим, запрос завершён, спиннер исчез. В Playwright автоожидание встроено, в Selenium — явные ожидания через `WebDriverWait` с `expected_conditions`.
>
> **Данные.** Тесты делят одну учётку или одну запись — начинают мешать друг другу при параллели. Лечится изоляцией: свои данные на тест, создание через API, уборка после.
>
> **Среда.** Тест стартовал раньше, чем поднялась зависимость. Лечится healthcheck'ом и ожиданием готовности, а не ретраем.
>
> **Само приложение.** Иногда флак — настоящий баг: гонка, которая воспроизводится в одном случае из двадцати. Это самый ценный флак, и его нельзя гасить ретраями.
>
> Ретраи я допускаю только как временную меру с обязательной пометкой и разбором — иначе они превращают красный прогон в зелёный и скрывают деградацию.

### D4. «Playwright или Selenium?»

> В Python оба живые. Playwright даёт автоожидания, изоляцию через контексты, трассировку с записью действий — на новом проекте я бы выбрал его. Selenium — если в компании уже есть экспертиза и инфраструктура селениум-грида: тогда стоимость перехода выше выгоды.
>
> На моём прошлом проекте мы отказались от небольшого legacy на Selenide в пользу Playwright, потому что кода было мало, а автоожидания снимали основной источник флака.

**Не переобещать:** если спросят про `pytest-playwright` конкретно — сказать честно, что боевой код писали на TS-версии, а Python-биндинг знаете как API: те же `page`, `locator`, `expect`, встроенная фикстура `page`.

### D5. «Как проверять то, что не видно на UI?»

> UI-тест не должен заканчиваться на «увидел зелёную плашку». Если операция асинхронная, я проверяю результат там, где он реально появляется: статус через API, запись в БД, сообщение в очереди. UI подтверждает, что пользователю показали правду, а не что операция прошла.

# E. API, интеграции, асинхрон

### E1. Схема-валидация

> Проверять только значения полей недостаточно: если бэкенд переименует поле или сменит тип, тест на конкретное значение может остаться зелёным. Поэтому валидирую ответ по схеме — в Python это Pydantic.

```python
from pydantic import BaseModel
from datetime import datetime

class License(BaseModel):
    id: int
    status: str
    expires_at: datetime
    product: str

def test_license_schema(api_client):
    resp = api_client.get("/licenses/42")
    License.model_validate(resp.json())   # упадёт при любом расхождении контракта
```

### E2. Контрактное тестирование

> Когда сервис общается со многими продуктами, интеграционные тесты «всё вместе» дорогие и медленные. Контрактные проверяют, что потребитель и поставщик договорились о формате: потребитель описывает ожидаемый контракт, поставщик проверяется против него. Инструмент — Pact.
>
> Для вашего Security Cloud это прямо в точку: один сервис, много продуктов-потребителей разных версий. Контракты дешевле, чем поднимать всю линейку.

### E3. Идемпотентность

> Операция идемпотентна, если повтор не меняет результат. В сервисе доставки обновлений это критично: сеть ненадёжна, клиент ретраит, и «применить обновление» не должно примениться дважды.
>
> Проверяю так: отправляю два одинаковых запроса с одним ключом идемпотентности, затем проверяю инвариант — одна запись в БД, один переход состояния, статус финальный один и тот же.

### E4. Race condition

> Гонка — когда результат зависит от порядка выполнения параллельных операций, и хотя бы один порядок даёт неверный итог.
>
> Воспроизвожу в тесте так: параллельные запросы к одному ресурсу плюс инверсия порядка ответов в моке, чтобы принудительно получить «неудобный» порядок. Проверяю не выдачу, а инвариант: один ключ — одна запись, счётчик не разъехался, статус не откатился назад.

*(Это тема, на которой вы просели на финале Сбера. Формулировка выше — рабочая, проговорить вслух.)*

### E5. Eventual consistency

> В распределённой системе после записи данные появляются не мгновенно. Поэтому в тестах — не `sleep`, а polling с таймаутом: опрашиваю статус до достижения ожидаемого или до истечения бюджета времени, и падаю с внятным сообщением, если не дождался.

```python
def wait_for(condition, timeout=30, interval=1):
    deadline = time.monotonic() + timeout
    while time.monotonic() < deadline:
        result = condition()
        if result:
            return result
        time.sleep(interval)
    raise AssertionError(f"Условие не выполнилось за {timeout}с")
```

# F. Домен: обновления, телеметрия, лицензии

Это то, что отличает «кандидата с pytest» от «инженера, который уже думает про их систему». Если вы назовёте эти острые места сами — этап сделан наполовину.

### F1. Доставка обновлений

Что может пойти не так и как проверять:

| Риск | Как проверяю |
|---|---|
| Инсталляция офлайн в момент выкатки | догоняющая доставка при возвращении в сеть; обновление не потерялось |
| Обрыв на середине загрузки | докачка или чистый повтор; нет полуприменённого состояния |
| Обновление применено дважды | идемпотентность по ключу; один переход состояния |
| Несовместимая версия | обновление отклонено с внятной ошибкой, а не применено «частично» |
| Откат | после `failed` система возвращается в рабочее состояние, а не зависает |
| Массовая выкатка | сотни инсталляций одновременно — очередь не переполняется, порядок не критичен |
| Старая инсталляция, новый сервис | обратная совместимость протокола |

### F2. Лицензии

Богатейший источник граничных кейсов — и именно тут стоит показать тест-дизайн:

- Момент истечения: последняя секунда, ровно ноль, первая секунда после.
- **Часовой пояс:** истечение по UTC или по локальному времени инсталляции? Расхождение на сутки — классика.
- Лицензия отозвана, пока инсталляция работает — когда узнает и что делает.
- Оффлайн-проверка: инсталляция не может достучаться до сервиса — грейс-период или немедленная блокировка? **Это отличный вопрос им**, и он показывает, что вы думаете про поведение системы при отказе.
- Продление в момент истечения — гонка между проверкой и обновлением срока.
- Лицензия на N инсталляций: попытка активировать N+1.

### F3. Телеметрия и статистика

- Потеря части данных при обрыве — переотправка, дедупликация по идентификатору события.
- Дубликаты: одно событие пришло дважды — счётчики не должны удвоиться.
- Порядок доставки: события пришли не в том порядке, что произошли.
- Часы инсталляции разошлись с сервером — по какому времени агрегируем.
- Объём: рост числа инсталляций, разрастание хранилища.

### F4. Кейс-вопрос, который вам почти наверняка дадут

Формат «вопросы близко к боевым задачам» обычно означает что-то вроде: **«Мы раскатываем сервис на новый продукт. Как ты это будешь тестировать?»**

Каркас ответа, чтобы не поплыть, как было на задаче ДМС в Сбере:

1. **Уточняю контекст.** Что именно интегрируется: только доставка обновлений или ещё телеметрия и лицензии? Какая версия протокола у продукта? Есть ли стенд с этим продуктом?
2. **Определяю риски по цене отказа.** Самое дорогое — инсталляция клиента получила битое обновление или потеряла лицензию. Это и есть критичные пути.
3. **Раскладываю по уровням.** Контрактные проверки между сервисом и продуктом — дёшево и ловит большинство расхождений. Интеграционные на стенде с реальной инсталляцией — узкий набор, только критичные пути. UI — что оператор видит корректный статус.
4. **Проверяю не только счастливый путь.** Офлайн, обрыв, повтор, несовместимая версия, откат.
5. **Называю, чем закончится.** Набор в CI, который гоняется перед раскаткой на следующий продукт, и гейт: не прошли — не раскатываем.

**Главное отличие от провала на ДМС:** сначала уточняющие вопросы и структура, потом детали. Не начинать с перечисления тест-кейсов.

# G. Лайвкодинг — 6 типовых задач с решениями

**Что говорить вслух, пока пишете:** «беру по одному представителю на класс эквивалентности, отдельно граничные — пустая строка и None, ids чтобы падение читалось».

### G2. Фикстура с подготовкой и уборкой данных

```python
@pytest.fixture
```

**Комментарий вслух:** «данные создаю через API, а не через UI — быстрее и не зависит от вёрстки; уборка в teardown, чтобы тесты можно было гонять параллельно и повторно».

### G3. Найди ошибки в тесте

Классическая задача «вот код, что не так». Что искать:

```python
def test_update():
```

### G4. Работа со структурами данных

**Задача:** из списка инсталляций собрать словарь «продукт → количество активных».

```python
def count_active_by_product(installations):
    result = {}
    for inst in installations:
        if inst["status"] != "active":
            continue
        result[inst["product"]] = result.get(inst["product"], 0) + 1
    return result
```

Вариант через стандартную библиотеку, если попросят короче:

```python
from collections import Counter

def count_active_by_product(installations):
    return Counter(i["product"] for i in installations if i["status"] == "active")
```

### G5. Ожидание асинхронного результата

**Задача:** обновление применяется асинхронно, напиши проверку.

```python
def test_update_is_applied(api_client, installation):
    api_client.post(f"/installations/{installation['id']}/updates", json={"version": "2.1.0"})

    status = wait_for(
        lambda: api_client.get(f"/installations/{installation['id']}").json()["update_status"],
        expected="applied",
        timeout=60,
    )
    assert status == "applied"


def wait_for(getter, expected, timeout=30, interval=2):
    deadline = time.monotonic() + timeout
    last = None
    while time.monotonic() < deadline:
        last = getter()
        if last == expected:
            return last
        time.sleep(interval)
    raise AssertionError(f"Ожидали '{expected}', последнее значение '{last}' за {timeout}с")
```

**Что подчеркнуть:** в сообщении об ошибке есть последнее фактическое значение — иначе при падении непонятно, застряло на `downloading` или вообще не стартовало.

### G6. Простой декоратор (если спросят)

```python
import functools, time

def retry(times=3, delay=1):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(times):
                try:
                    return func(*args, **kwargs)
                except AssertionError:
                    if attempt == times - 1:
                        raise
                    time.sleep(delay)
        return wrapper
    return decorator
```

И сразу добавить позицию: «в тестах я такое не применяю — ретрай прячет флак. Это уместно для нестабильной инфраструктуры, не для проверок».

# H. Процесс, CI, флак

- **«Как встроишь тесты в CI?»** → На пуш — линт и smoke, минуты. Полный набор по расписанию ночью, с параллелизмом и сборкой общего отчёта. Гейт: упавшие тесты роняют пайплайн, мержа нет. Артефакты — трейсы, скриншоты, логи — прикладываются к прогону, чтобы падение диагностировалось без локального воспроизведения.
- **«Что делать, если тестов нет, а надо начать?»** → Критичные пути, 10–15 сценариев. Неделя-полторы на каркас, две-три недели на покрытие критичных путей. В пределах месяца у команды есть работающий гейт. Дальше расширение по impact-анализу.
- **«Как понять, что автоматизация приносит пользу?»** → Время приёмки перед релизом, количество дефектов, доехавших до прода, доля падений, оказавшихся настоящими багами. Не количество тестов.
- **«Разработчик просит не заводить баг»** → Завожу всегда. Обсуждать можно severity и priority, сроки, попадёт ли в этот релиз — но не факт существования дефекта. Незаведённый баг — это потерянная информация для всей команды.

# S. Домен безопасности: вопросы, ответы, что доизучить

Отдельная глава, потому что это ИБ-вендор, и разговор почти наверняка свернёт в безопасность. Здесь важно не изображать пентестера, а показать **тестировщика, который понимает риски своей системы и умеет проверять их функционально**.

## S.0. Рамка — как позиционироваться

Скажите один раз, если тема зайдёт глубоко:

> «Я не AppSec-инженер и не пентестер — не буду делать вид. Мой уровень: понимаю модель угроз системы, умею превратить требование безопасности в проверяемый тест-кейс и знаю, где в таком продукте живут типовые дыры. Пентест и анализ кода — это отдельная роль, я с ней работаю рядом, а не вместо неё.»

**Почему это выигрывает:** в ИБ-компании люди мгновенно чувствуют, когда кандидат жонглирует терминами. Честная граница плюс предметное рассуждение внутри неё ценится намного выше, чем попытка звучать экспертом.

---

## S.1. Аутентификация и авторизация

**Вопрос: «Чем отличается аутентификация от авторизации?»**

> Аутентификация — кто ты (проверка личности). Авторизация — что тебе можно (проверка прав). Тестируются они по-разному: первая — сценариями входа, вторая — матрицей «роль × действие × объект».

**Вопрос: «Как тестируешь авторизацию?»**

> Строю матрицу доступа: роли по строкам, действия по столбцам, в ячейках — разрешено или запрещено. Дальше автоматизирую негативную часть, она важнее позитивной: под каждой ролью пытаюсь сделать то, что ей не положено, и жду 403, а не 200 и не 500.
>
> Отдельно — **проверка на уровне API, а не UI**. Скрытая в интерфейсе кнопка ничего не значит: запрос можно отправить напрямую. Поэтому тест на права всегда идёт в обход UI.

**Ключевой класс дефектов, который надо назвать самому — IDOR / BOLA**

> Broken Object Level Authorization — когда сервер проверяет, что ты залогинен, но не проверяет, что объект твой. Классика: меняю `/installations/42` на `/installations/43` и получаю чужую инсталляцию.
>
> Для вашего продукта это риск номер один: сервис общий для всех клиентов, и изоляция арендаторов — то, на чём его надо ломать в первую очередь. Проверяю так: два клиента, у каждого свои инсталляции и лицензии; под токеном первого перебираю идентификаторы второго — по всем эндпоинтам, включая те, что кажутся безобидными: статистика, логи, статусы обновлений.

**Что доизучить:** JWT (структура header/payload/signature, срок жизни, refresh, что подпись проверяется на сервере, а payload не секретен), OAuth2/OIDC на уровне ролей и потоков, mTLS (взаимная аутентификация — вероятна в связке «сервис ↔ инсталляция»), RBAC против ABAC, API-ключи и их ротация.

**Тест-кейсы на токены, которые стоит перечислить:**

- истёкший токен → 401;
- токен другого клиента → 403 на чужие объекты;
- токен с изменённым payload и старой подписью → отвергнут;
- отсутствующий заголовок `Authorization` → 401, а не 500;
- отозванный токен продолжает работать до истечения — это вопрос к архитектуре, а не баг по умолчанию, но его надо задать;
- права понижены во время активной сессии — когда применится.

---

## S.2. Целостность обновлений — сердце их продукта

Это самая релевантная тема: сервис доставляет обновления на инсталляции клиентов. Подмена обновления = компрометация всех клиентов сразу. Именно так работают supply chain-атаки.

**Что должно проверяться:**

| Риск | Проверка |
|---|---|
| Подмена пакета в пути | цифровая подпись пакета проверяется перед применением; битый/подменённый — отклонён |
| Несовпадение хеша | контрольная сумма (SHA-256) сверяется после загрузки |
| Откат на уязвимую версию | downgrade-атака: попытка подсунуть старую версию с известной уязвимостью должна отклоняться |
| Просроченный/отозванный сертификат подписи | обновление не применяется, инсталляция сообщает внятную причину |
| Replay: повтор старого валидного пакета | защита по версии/nonce/времени |
| Path traversal при распаковке | архив с путями вида `../../etc/passwd` не должен вылезти за пределы каталога (zip slip) |
| Частичное применение | обрыв на середине не оставляет систему в полурабочем состоянии; есть откат |

**Как это произнести:**

> Для сервиса доставки обновлений главный риск не функциональный, а целостности: если можно подменить пакет, скомпрометированы все инсталляции разом. Поэтому я бы проверял цепочку доверия целиком — подпись, хеш, срок действия сертификата, отзыв, — и отдельно негативные сценарии: битый пакет, чужая подпись, старая версия, обрыв на середине.

**Что доизучить:** асимметричная подпись в двух предложениях (приватный ключ подписывает, публичный проверяет), хеш-функции и зачем SHA-256 против MD5, что такое цепочка сертификатов и отзыв (CRL/OCSP), понятие supply chain attack на примере — этого достаточно для AQA-уровня.

## S.3. Многотенантность и изоляция данных

> Сервис общий для всех продуктов и, вероятно, для многих клиентов. Значит основной класс дефектов — утечка между арендаторами: телеметрия одного клиента видна другому, лицензия применилась не к той инсталляции, статистика агрегировалась по всем.
>
> Тестирую всегда минимум двумя клиентами. Один клиент — принципиально нетестируемая конфигурация: с ним изоляция не проверяется вообще.

**Кейсы:** список сущностей под клиентом A не содержит объектов клиента B; прямой запрос по id чужого объекта; поиск и фильтры не протекают; агрегаты и счётчики считаются в границах клиента; экспорт/выгрузка; сообщения об ошибках не раскрывают существование чужих объектов (`404` вместо `403` там, где сам факт существования — уже утечка).

## S.4. Секреты и чувствительные данные

**Вопрос: «Как хранишь креды для тестов?»** — почти наверняка спросят в ИБ-компании.

> Никогда в репозитории. Тестовые учётки и токены — в переменных окружения, в CI — в защищённых переменных или в vault. В коде только имена переменных. В логах и отчётах секреты маскируются: Allure с приложенным заголовком `Authorization` — это утечка, особенно если отчёты публикуются.
>
> Отдельно — что тестовые данные не должны содержать реальных персональных данных. Для ИБ-вендора это ещё и вопрос комплаенса.

**Что проверять в самом продукте:** секреты не попадают в логи и телеметрию; ключи лицензий маскируются в интерфейсе и выгрузках; сообщения об ошибках не раскрывают внутренние пути, версии и стектрейсы; заголовки ответов не выдают версию сервера.

**Что доизучить:** практики работы с секретами в GitLab CI (masked/protected variables), базово Vault, secret scanning в пайплайне.

## S.5. Транспорт и сеть

> TLS для всего трафика, включая внутренний между сервисом и инсталляциями. Что проверяю: соединение по HTTP отклоняется или редиректится, самоподписанный сертификат не принимается по умолчанию, истёкший сертификат приводит к отказу, а не к тихому продолжению.
>
> Отдельный вопрос — **ротация сертификатов**: инсталляции живут годами, сертификаты — нет. Что происходит с инсталляцией, у которой сертификат протух, — она отваливается молча или сообщает.

**Что доизучить:** TLS-рукопожатие на пальцах, mTLS, certificate pinning и его цена при ротации, HSTS, зачем нужны заголовки безопасности (`Content-Security-Policy`, `X-Content-Type-Options`, `Strict-Transport-Security`) — для UI-части это может всплыть.

## S.6. Отказоустойчивость с точки зрения безопасности

**Вопрос, который стоит задать им самому** — он показывает уровень:

> «Что делает инсталляция, если сервис лицензирования недоступен: fail-open — продолжает работать, или fail-close — блокируется? И есть ли грейс-период?»

> Это архитектурный компромисс между доступностью и безопасностью, и он должен быть осознанным решением, а не побочным эффектом. Для средства защиты fail-close может означать, что клиент остался без защиты; fail-open — что лицензионный контроль обходится отключением сети. Что бы ни выбрали, это тестируемое поведение: обрыв связи, длительный оффлайн, возврат в сеть.

## S.7. Типовые уязвимости — минимум, который надо знать

Не углубляться, но уметь назвать и сказать, как проверяется:

| Класс | Суть | Как проверяю |
|---|---|---|
| **BOLA / IDOR** | доступ к чужому объекту по id | перебор id под чужим токеном |
| **Broken authentication** | слабая или обходимая аутентификация | истёкший/поддельный/отсутствующий токен |
| **Injection** (SQL, command) | недоверенный ввод попадает в запрос или команду | спецсимволы в полях, кавычки, `;`, шаблоны |
| **Path traversal** | выход за пределы каталога | `../` в именах файлов и путях распаковки |
| **SSRF** | сервис ходит по URL, который задал пользователь | подстановка внутренних адресов |
| **Mass assignment** | клиент передаёт поле, которое менять не должен | добавить `"role": "admin"` в payload |
| **Rate limiting / DoS** | нет ограничения частоты | шквал запросов, крупные payload |
| **Раскрытие информации** | стектрейсы, версии, внутренние пути в ответах | негативные сценарии и 500-е |

> Формулировка вслух: «Я не провожу пентест, но эти классы держу в голове при проектировании негативных тестов. Часть из них — обычные функциональные проверки, просто со злым умыслом: тот же mass assignment ловится тестом на то, что сервер игнорирует лишние поля.»

**Что доизучить:** OWASP Top 10 и, важнее для их продукта, **OWASP API Security Top 10** — прочитать список и уметь назвать три-четыре пункта с примером.

## S.8. Безопасность в процессе и в CI

**Вопрос: «Как безопасность встраивается в пайплайн?»**

> Три вещи, которые обычно есть: **SCA** — проверка зависимостей на известные уязвимости, **SAST** — статический анализ кода, **secret scanning** — поиск случайно закоммиченных ключей. Динамический анализ (**DAST**) — реже и на отдельном стенде.
>
> Моя зона как автотестировщика — не запускать сканеры, а следить, чтобы их результаты были гейтом, а не отчётом, который никто не читает, и чтобы найденное превращалось в задачи. Плюс мои собственные негативные тесты на права и изоляцию — они закрывают то, что сканер не увидит, потому что это логика, а не паттерн в коде.

**Про свои же зависимости:** тестовый проект — тоже код, и его зависимости тоже могут содержать уязвимости. Упомянуть, что это учитываете, — небольшой, но заметный плюс в ИБ-компании.

**Что доизучить:** что такое CVE и CVSS в двух словах; чем SAST отличается от DAST и SCA; как это выглядит в GitLab CI (там встроенные шаблоны сканирования).

## P1. DTO и модели данных

### A1. «Что такое DTO и зачем он в автотестах?»

> DTO — объект, который переносит данные между слоями и ничего не делает сам: без бизнес-логики, только поля. В автотестах он решает три задачи.
>
> **Первая — читаемость.** Вместо `resp.json()["data"]["license"]["expires_at"]` пишется `license.expires_at`. Опечатка в строковом ключе ловится только в рантайме, а в атрибуте — сразу подсветит IDE.
>
> **Вторая — валидация контракта.** Если бэкенд переименовал поле или сменил тип, разбор в модель падает сразу и с внятным сообщением, а не через десять строк на непонятном `KeyError`.
>
> **Третья — тестовые данные.** DTO с дефолтами превращается в фабрику: создаю объект, переопределяя только то, что важно для конкретного теста.

### A2. «Чем сделаешь DTO: dict, dataclass, NamedTuple, TypedDict или Pydantic?»

Это любимый вопрос, потому что показывает, понимает ли человек разницу между подсказкой типов и реальной проверкой.

| | Валидация в рантайме | Изменяемый | Когда беру |
|---|---|---|---|
| `dict` | нет | да | быстрый разбор, одноразово |
| `TypedDict` | **нет**, только подсказка для линтера | да | типизировать существующие словари, не меняя код |
| `NamedTuple` | нет | нет | маленький неизменяемый набор полей, можно как ключ словаря |
| `@dataclass` | нет (типы не проверяются!) | да, если не `frozen` | внутренние модели тестов, фабрики данных |
| **Pydantic** | **да** | да | **разбор ответов API — основной выбор** |

> Ключевое, что надо сказать вслух: **`dataclass` и `TypedDict` типы не проверяют.** Аннотация `expires_at: datetime` в датаклассе не помешает положить туда строку — это подсказка для человека и линтера, а не рантайм-контроль. Поэтому для валидации ответов от сервиса я беру Pydantic: он реально приводит и проверяет типы и падает на расхождении контракта.

### A3. Pydantic — как выглядит на практике

```python
from pydantic import BaseModel, Field, field_validator
from datetime import datetime
from enum import Enum


class LicenseStatus(str, Enum):
    ACTIVE = "active"
    EXPIRED = "expired"
    REVOKED = "revoked"


class License(BaseModel):
    id: int
    key: str = Field(min_length=19, max_length=19)
    status: LicenseStatus
    expires_at: datetime
    seats: int = Field(ge=1)
    product: str

    @field_validator("key")
    @classmethod
    def key_format(cls, v: str) -> str:
        if v != v.upper():
            raise ValueError("ключ должен быть в верхнем регистре")
        return v


# разбор ответа
license = License.model_validate(resp.json())
assert license.status is LicenseStatus.ACTIVE

# обратно в словарь для отправки
payload = license.model_dump(mode="json")
```

**Что здесь стоит проговорить:**

- `Enum` для статусов вместо строк — опечатка `"activ"` не пройдёт, а сравнение читается.
- `Field(ge=1)` — ограничения прямо в модели, не в ассертах.
- `model_validate` падает при любом расхождении контракта: лишнее поле не страшно, а отсутствующее или не того типа — сразу.
- `model_dump(mode="json")` — сериализация с приведением `datetime` к строке.

**Могут доспросить:** «а если бэкенд добавит новое поле?» → По умолчанию Pydantic лишние поля игнорирует. Если нужно ловить расширение контракта — `model_config = ConfigDict(extra="forbid")`. В тестах это обоюдоострая штука: строгий режим ловит незадокументированные изменения, но и ломает тесты при безобидном расширении API. Обычно строго — в контрактных тестах, мягко — в функциональных.

### A4. dataclass — для тестовых данных

```python
from dataclasses import dataclass, field, asdict


@dataclass
class InstallationData:
    name: str = "test-installation"
    product: str = "security-cloud"
    version: str = "1.0.0"
    tags: list[str] = field(default_factory=list)   # ❗ не tags: list = []
    online: bool = True


# в тесте переопределяю только значимое
inst = InstallationData(version="2.1.0", online=False)
payload = asdict(inst)
```

**Три вещи, которые здесь проверяют:**

1. **`field(default_factory=list)`.** Если написать `tags: list = []`, список создастся один раз при определении класса и будет общим для всех экземпляров — классическая ловушка мутабельного дефолта.
2. **`frozen=True`** делает объект неизменяемым и хешируемым — можно класть в `set` или использовать как ключ словаря.
3. **Дефолты** — это и есть «фабрика тестовых данных»: тест указывает только то, что важно для него, остальное берётся из осмысленных умолчаний. Это резко повышает читаемость: видно, что именно в этом тесте существенно.

### A5. «Как строишь тестовые данные для сложных объектов?»

> Тремя способами, по возрастанию сложности объекта.
>
> **Дефолты в датаклассе** — когда объект простой. Тест меняет одно-два поля.
>
> **Фабричные функции** — когда нужны осмысленные пресеты: `expired_license()`, `installation_offline()`. Название несёт смысл, и в тесте читается сценарий, а не набор полей.
>
> **Builder** — когда полей много и комбинаций много: `LicenseBuilder().expired().with_seats(5).build()`.
>
> Плюс `Faker` для значений, которые должны быть уникальными и правдоподобными — имена, email, адреса. Уникальность важна при параллельном прогоне: захардкоженное имя приводит к конфликтам между воркерами.

```python
def expired_license(**overrides):
    defaults = dict(
        status="expired",
        expires_at=datetime.now(timezone.utc) - timedelta(days=1),
        seats=1,
    )
    return License(**{**defaults, **overrides})
```

## P2. Структуры данных

### B1. «Чем отличаются list, tuple, set, dict?»

| | Упорядочен | Изменяем | Дубликаты | Поиск `in` |
|---|---|---|---|---|
| `list` | да | да | да | **O(n)** |
| `tuple` | да | нет | да | O(n) |
| `set` | нет* | да | нет | **O(1)** в среднем |
| `dict` | да (порядок вставки) | да | ключи уникальны | **O(1)** в среднем |

\* у `set` нет гарантий порядка; у `dict` порядок вставки гарантирован начиная с Python 3.7.

> Практическое следствие для тестов: если проверяю вхождение в большой набор — перевожу в `set`. Проверка `id in list_of_10000` линейная, `id in set_of_10000` — константная. На выборках из API это разница между секундами и миллисекундами.

### B2. «Сложность основных операций»

| Операция | list | dict / set |
|---|---|---|
| доступ по индексу / ключу | O(1) | O(1) |
| `append` / добавление | O(1) амортизированно | O(1) |
| `insert(0, x)` | O(n) | — |
| `in` | O(n) | O(1) |
| удаление по значению | O(n) | O(1) |

**Могут доспросить:** «а если надо часто добавлять в начало?» → `collections.deque` — двусторонняя очередь, `appendleft` за O(1).

### B3. «Что может быть ключом словаря?»

> Только хешируемый объект — то есть неизменяемый: `str`, `int`, `tuple` (если все элементы внутри тоже хешируемы), `frozenset`, `Enum`. Список или словарь ключом быть не могут: если объект изменится, его хеш перестанет соответствовать месту в таблице.

```python
by_key = {("security-cloud", "2.1.0"): installation}   # ✅ tuple как составной ключ
by_key = {["a", "b"]: 1}                               # ❌ TypeError: unhashable type
```

**Могут доспросить:** «а свой класс?» → По умолчанию хешируется по идентичности объекта. Если переопределили `__eq__`, надо переопределить и `__hash__` — иначе объект станет нехешируемым. `@dataclass(frozen=True)` делает это автоматически.

### B4. «Полезное из collections»

```python
from collections import Counter, defaultdict, deque, namedtuple

Counter(i["product"] for i in installations)        # подсчёт: продукт → сколько
Counter(...).most_common(3)                          # топ-3

d = defaultdict(list)                                # словарь со значением по умолчанию
for inst in installations:
    d[inst["product"]].append(inst["name"])          # без проверки на наличие ключа

deque(maxlen=100)                                    # очередь фиксированной длины
```

`Counter` и `defaultdict` — то, что чаще всего выручает на лайвкодинге, когда просят сгруппировать или посчитать.

### B5. «Копирование: в чём разница между поверхностным и глубоким?»

```python
import copy

original = {"name": "inst", "tags": ["prod", "critical"]}

shallow = copy.copy(original)      # или original.copy() / dict(original)
shallow["tags"].append("new")      # ❗ изменит и original — вложенный список тот же объект

deep = copy.deepcopy(original)
deep["tags"].append("new")         # original не тронут
```

> Для тестов это важно, когда есть общий шаблон данных: если базовый payload копировать поверхностно и менять вложенные поля, тесты начнут влиять друг на друга. Либо `deepcopy`, либо неизменяемые дефолты и построение нового объекта.

### B6. «Список или генератор?»

```python
active = [i for i in installations if i["online"]]         # список: весь в памяти
active = (i for i in installations if i["online"])         # генератор: лениво, один проход
```

> Генератор экономит память и хорош для потоковой обработки, но по нему можно пройти **только один раз**. В тестах это ловушка: прошли генератор в ассерте, потом хотите его же посчитать — получаете пусто. Поэтому в тестовом коде я обычно беру список: данных немного, а предсказуемость важнее.

### B7. «Как отсортировать список словарей?»

```python
sorted(installations, key=lambda i: i["name"])
sorted(installations, key=lambda i: (i["product"], -i["seats"]))    # по двум ключам
sorted(installations, key=itemgetter("created_at"), reverse=True)
```

`sorted` возвращает новый список, `list.sort()` меняет на месте и возвращает `None` — на этом ловят: `x = my_list.sort()` даёт `None`.

### B8. «Множества — где применяешь в тестах?»

```python
expected = {"prod", "staging", "dev"}
actual = {e["name"] for e in resp.json()}

assert actual == expected
assert expected - actual == set()          # чего не хватает
assert actual - expected == set()          # что лишнее
```

> Сравнение списков падает с нечитаемым выводом, если отличается только порядок. Множества дают внятную диагностику: разность сразу показывает, чего не хватает и что появилось лишнего. Но только там, где порядок действительно не важен и дубликаты не значимы.

## P3. Язык: то, что всплывает в тестах

### C1. Мутабельный аргумент по умолчанию

```python
def add_tag(tag, tags=[]):     # ❌ список один на все вызовы
    tags.append(tag)
    return tags

def add_tag(tag, tags=None):   # ✅
    tags = list(tags or [])
    tags.append(tag)
    return tags
```

Самая частая «ловушка на понимание» в питон-собесах. Причина: значения по умолчанию вычисляются один раз при определении функции, а не при каждом вызове.

### C2. `is` против `==`

> `==` сравнивает значения, `is` — что это один и тот же объект в памяти. В ассертах почти всегда `==`. `is` — только для `None`, `True`, `False` и для членов `Enum`.

```python
assert resp.json()["status"] == "active"     # ✅
assert value is None                          # ✅
assert count is 5                             # ❌ работает случайно, из-за кеша малых чисел
```

### C3. Исключения

```python
try:
    resp = requests.get(url, timeout=10)
    resp.raise_for_status()
except requests.Timeout:
    ...                       # конкретное исключение
except requests.HTTPError as e:
    ...
except Exception:             # ❌ так в тестах не надо — проглотит и падение ассерта
    ...
finally:
    session.close()           # выполнится всегда
```

> Голый `except:` или `except Exception:` в тестовом коде — плохая практика: он проглатывает в том числе `AssertionError`, и тест становится всегда зелёным. Ловлю только то, что действительно ожидаю обработать.

### C4. Контекстные менеджеры

```python
with open("data.json") as f:          # файл закроется даже при исключении
    data = json.load(f)

with pytest.raises(ValueError):
    parse_key("bad")

# свой
from contextlib import contextmanager

@contextmanager
def temporary_license(api, **kwargs):
    lic = api.create_license(**kwargs)
    try:
        yield lic
    finally:
        api.delete_license(lic.id)
```

### C5. Декораторы

> Функция, которая оборачивает другую функцию, не меняя её код. Весь pytest на них построен. Уметь прочитать обязательно; написать простой — желательно.

```python
import functools

def log_step(name):
    def decorator(func):
        @functools.wraps(func)         # сохраняет __name__ и docstring
        def wrapper(*args, **kwargs):
            print(f"--- {name}")
            return func(*args, **kwargs)
        return wrapper
    return decorator
```

`functools.wraps` — деталь, которую любят спрашивать: без неё обёрнутая функция теряет имя, и pytest с отчётами начинают показывать `wrapper` вместо реального имени теста.

### C6. `*args` и `**kwargs`

```python
def create_installation(name, **overrides):
    payload = {"name": name, "product": "security-cloud", "online": True}
    payload.update(overrides)          # тест переопределяет только нужное
    return api.post("/installations", json=payload)

create_installation("inst-1", online=False, version="2.1.0")
```

Это основной приём для фабрик тестовых данных — стоит показать именно в таком виде.

### C7. Распаковка и объединение

```python
merged = {**defaults, **overrides}       # правое побеждает
combined = [*base_tags, *extra_tags]
first, *rest = versions
a, b = b, a
```

### C8. Работа с JSON

```python
import json

data = json.loads(raw_string)                       # строка → объект
raw = json.dumps(data, ensure_ascii=False, indent=2)  # объект → строка

with open("expected.json", encoding="utf-8") as f:
    expected = json.load(f)                          # файл → объект
```

`loads`/`dumps` — со строкой, `load`/`dump` — с файлом. Буква `s` = string. На этом иногда ловят.

### C9. Регулярные выражения

```python
import re

re.fullmatch(r"[A-Z0-9]{4}(-[A-Z0-9]{4}){3}", key)   # ключ целиком
re.search(r"version=(\d+\.\d+\.\d+)", log)            # найти где угодно
m = re.search(r"id=(?P<id>\d+)", text)
m.group("id")
```

`match` — с начала строки, `search` — где угодно, `fullmatch` — вся строка целиком. Для валидации формата почти всегда нужен `fullmatch`, а не `match` — типичная ошибка.

### C10. GIL и параллельность

> GIL не даёт нескольким потокам одновременно выполнять питоновский байткод. Для тестов это значит: потоки не ускорят вычисления, но **отлично работают на ожидании ввода-вывода** — HTTP-запросы, чтение файлов. Поэтому параллельная отправка запросов через `ThreadPoolExecutor` даёт реальный выигрыш, а pytest-xdist использует **процессы**, а не потоки — именно чтобы обойти GIL.

```python
from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(max_workers=10) as pool:
    results = list(pool.map(lambda i: api.get(f"/installations/{i}"), ids))
```

Это же — способ воспроизвести гонку: параллельные одинаковые запросы и проверка инварианта.

## P4. ООП под Page Object

### D1. «Наследование или композиция?»

> В Page Object обычно и то и другое. Наследование — от `BasePage`, где живут общие операции: открыть, дождаться загрузки, доступ к драйверу. Композиция — для повторяющихся кусков интерфейса: шапка, боковое меню, модалка. Компонент — отдельный класс, страница держит его как поле.
>
> Правило: наследование — когда «страница **является** частным случаем базовой», композиция — когда «страница **содержит** этот блок». Таблица не является страницей, поэтому она поле, а не родитель.

```python
class BasePage:
    def __init__(self, page):
        self.page = page
        self.header = HeaderComponent(page)      # композиция


class InstallationsPage(BasePage):               # наследование
    def open(self):
        self.page.goto(f"{BASE_URL}/installations")
        return self
```

### D2. «`classmethod`, `staticmethod`, `property`?»

```python
class License:
    def __init__(self, expires_at):
        self.expires_at = expires_at

    @property
    def is_expired(self):                        # обращение как к полю: lic.is_expired
        return self.expires_at < datetime.now(timezone.utc)

    @classmethod
    def from_api(cls, payload):                  # альтернативный конструктор
        return cls(expires_at=parse(payload["expires_at"]))

    @staticmethod
    def format_key(raw):                         # утилита, не нужен ни self, ни cls
        return raw.upper().replace(" ", "-")
```

### D3. «Зачем `__repr__` в тестовых моделях?»

> Прямая практическая польза: при падении ассерта pytest печатает объекты, и без `__repr__` вы увидите `<License object at 0x7f...>`, что бесполезно. С `__repr__` — `License(id=42, status='expired')`, и причина падения видна сразу, без перезапуска с отладчиком.

У `@dataclass` и Pydantic `__repr__` генерируется автоматически — ещё один аргумент в их пользу против голых словарей.

### D4. «`__eq__` и `__hash__`»

> Если переопределяете `__eq__`, надо думать и про `__hash__`: объект с собственным `__eq__` без `__hash__` становится нехешируемым и не ляжет в `set`. Контракт простой: равные объекты обязаны иметь равный хеш. `@dataclass(frozen=True)` делает оба корректно.

## P5. Даты, время, часовые пояса

Для их продукта — лицензии с датами истечения — это не абстракция, а прямая зона багов.

```python
from datetime import datetime, timezone, timedelta

datetime.now()                       # ❌ naive — без часового пояса
datetime.now(timezone.utc)           # ✅ aware

# парсинг ISO 8601
datetime.fromisoformat("2026-08-25T15:30:00+00:00")

# сравнение naive и aware бросит TypeError — частая ошибка
```

**Что сказать на вопрос про тестирование лицензий:**

> Первое, что уточняю: истечение считается по UTC или по локальному времени инсталляции. Это самый частый источник расхождения на сутки, особенно когда сервер в UTC, а инсталляция в UTC+10.
>
> В тестах даты никогда не хардкожу — вычисляю относительно текущего момента: `now + 1 день`, `now - 1 секунда`. Хардкод `2026-01-01` протухает и превращается в тест, который однажды сам покраснеет.
>
> И проверяю ровно три точки: последняя секунда до истечения, момент истечения, первая секунда после. Плюс переход через полночь и через границу часового пояса.

## P6. Практические задачи с решениями

#### F1. Сгруппировать по ключу

**Задача:** из списка инсталляций получить словарь «продукт → список имён».

```python
from collections import defaultdict

def group_by_product(installations):
    result = defaultdict(list)
    for inst in installations:
        result[inst["product"]].append(inst["name"])
    return dict(result)
```

#### F2. Найти дубликаты

**Задача:** телеметрия прислала события, найти повторяющиеся id.

```python
from collections import Counter

def find_duplicates(events):
    counts = Counter(e["id"] for e in events)
    return [event_id for event_id, n in counts.items() if n > 1]
```

**Что сказать:** «это ровно та проверка, которая нужна для дедупликации телеметрии — событие пришло дважды, счётчики не должны удвоиться».

#### F3. Сравнить два набора и показать разницу

```python
def diff_installations(expected, actual):
    exp = {i["id"] for i in expected}
    act = {i["id"] for i in actual}
    return {
        "missing": sorted(exp - act),
        "unexpected": sorted(act - exp),
    }
```

#### F4. Плоский разбор вложенного JSON

**Задача:** достать все версии продуктов из вложенной структуры.

```python
def collect_versions(payload):
    return {
        product["name"]: product["version"]
        for installation in payload["installations"]
        for product in installation.get("products", [])
    }
```

`.get("products", [])` вместо `["products"]` — защита от отсутствующего ключа. На собесе это заметят как аккуратность.

#### F5. DTO + разбор ответа + тест

```python
from pydantic import BaseModel
from datetime import datetime


class Installation(BaseModel):
    id: int
    name: str
    product: str
    version: str
    online: bool
    last_seen: datetime


def test_installation_contract(api_client):
```

**Что подчеркнуть вслух:** «разделяю две проверки — контракт отдельно, бизнес-логика отдельно. Если сломался контракт, я это вижу как ошибку валидации, а не как непонятное падение ассерта».

```python
IGNORED = {"id", "created_at", "updated_at", "trace_id"}

def normalize(payload, ignored=IGNORED):
```

## P7. Быстрый прогон: 30 коротких вопросов

Проверьте себя — на каждый должен быть ответ в одно-два предложения.

**DTO и модели**

1. Чем `dataclass` отличается от Pydantic-модели? → Датакласс типы **не проверяет** в рантайме, Pydantic проверяет и приводит.
2. Что делает `field(default_factory=list)`? → Создаёт новый список на каждый экземпляр вместо общего.
3. Зачем `frozen=True`? → Неизменяемость плюс хешируемость, можно в `set` и как ключ.
4. Чем `TypedDict` отличается от `NamedTuple`? → Первый — это словарь с подсказками типов, второй — неизменяемый кортеж с именами полей.
5. Как в Pydantic запретить лишние поля? → `model_config = ConfigDict(extra="forbid")`.
6. Зачем `Enum` для статусов? → Опечатка ловится сразу, значения в одном месте, сравнение читается.
7. Как сериализовать модель обратно в JSON? → `model_dump(mode="json")`.

**Структуры данных**

8. Сложность `in` для списка и для множества? → O(n) и O(1) в среднем.
9. Что может быть ключом словаря? → Хешируемое, то есть неизменяемое.
10. Гарантируется ли порядок в `dict`? → Да, порядок вставки, с Python 3.7.
11. Разница `copy` и `deepcopy`? → Поверхностная копия делит вложенные объекты, глубокая — нет.
12. `sorted` и `list.sort()`? → Первая возвращает новый список, вторая меняет на месте и возвращает `None`.
13. Когда `deque` вместо `list`? → Когда часто добавляем и удаляем с начала.
14. Что вернёт `Counter(...).most_common(3)`? → Три самых частых элемента с количествами.
15. Чем генератор отличается от списка? → Ленивый, экономит память, проходится один раз.
16. Как найти, чего не хватает в ответе? → Разностью множеств: `expected - actual`.

**Язык**

17. Почему `def f(x=[])` — плохо? → Дефолт вычисляется один раз, список общий для всех вызовов.
18. `is` или `==` для сравнения строк? → `==`.
19. Чем плох `except Exception` в тесте? → Проглотит и `AssertionError`, тест станет всегда зелёным.
20. Что делает `functools.wraps`? → Сохраняет имя и метаданные обёрнутой функции.
21. `json.load` и `json.loads`? → Файл и строка; `s` = string.
22. `re.match`, `search`, `fullmatch`? → С начала, где угодно, вся строка целиком.
23. Что такое GIL и как он влияет на тесты? → Мешает параллелить вычисления в потоках, не мешает ждать ввод-вывод; xdist поэтому на процессах.
24. Как сделать словарь из двух с приоритетом второго? → `{**a, **b}`.
25. Зачем `with`? → Гарантированное освобождение ресурса даже при исключении.

**ООП и практика**

26. Наследование или композиция для компонентов страницы? → Композиция: страница содержит компонент, а не является им.
27. Зачем `__repr__` в модели? → Читаемая диагностика при падении ассерта.
28. Что будет, если переопределить `__eq__` без `__hash__`? → Объект станет нехешируемым.
29. `classmethod` против `staticmethod`? → Первый получает класс и годится для альтернативных конструкторов, второй — просто утилита в неймспейсе класса.
30. Почему нельзя хардкодить даты в тестах? → Протухают; считать относительно текущего момента.

Не угадывать. Формула:

# Q. pytest CLI: все ключи по буквам

Разбор командной строки pytest по буквам: откуда взялся ключ, что он делает, как читается мнемонически и когда применяется в реальном прогоне. Отдельно — синтаксис выражений в `-k` и `-m`, параллель через xdist, коды выхода и вынос параметров в конфиг.

> Часть ключей — не самого pytest, а плагинов. Это важно на собесе: `-n` появляется только с `pytest-xdist`, `--alluredir` — с `allure-pytest`. Если сказать «стандартный ключ pytest» про `-n`, это заметят.

---


### 1. Разбор пяти команд из шпаргалки

#### `pytest -m smoke -n auto`

| Часть | Расшифровка |
|---|---|
| `-m` | **m**arker — отбор по маркерам. Запустить только те тесты, что помечены `@pytest.mark.smoke` |
| `smoke` | имя маркера (может быть выражением, см. раздел 2) |
| `-n` | **n**umber of processes — количество параллельных процессов. **Ключ плагина `pytest-xdist`** |
| `auto` | вместо числа — «столько процессов, сколько логических ядер у машины» |

Читается: «прогнать только smoke-набор, распараллелив по числу ядер».

#### `pytest -k "license and not expired"`

| Часть | Расшифровка |
|---|---|
| `-k` | **k**eyword — отбор по подстроке в имени теста, класса или файла |
| `"license and not expired"` | выражение: имя содержит `license`, но не содержит `expired` |

Важно: `-k` работает **по именам**, а не по маркерам. `test_license_expired_returns_error` под это выражение не попадёт, а `test_license_active` — попадёт.

#### `pytest --lf`

| Часть | Расшифровка |
|---|---|
| `--lf` | **l**ast **f**ailed — запустить только те тесты, что упали в прошлый прогон |

Читает кеш из `.pytest_cache`. Основной рабочий режим при починке: чинишь → `--lf` → снова, пока не станет зелёным, вместо прогона всего набора.

Родственники: `--ff` (**f**ailed **f**irst — упавшие первыми, потом остальные) и `--nf` (**n**ew **f**irst — новые файлы первыми).

#### `pytest -x`

| Часть | Расшифровка |
|---|---|
| `-x` | e**x**it on first failure — остановиться на первом падении |

Полная форма — `--exitfirst`. Обобщение: `--maxfail=3` — остановиться после трёх падений.

Смысл: если развалилась среда, нет смысла гонять 400 тестов, чтобы получить 400 одинаковых красных.

#### `pytest -vv --alluredir=allure-results`

| Часть | Расшифровка |
|---|---|
| `-v` | **v**erbose — подробный вывод: имя каждого теста и его результат отдельной строкой вместо точек |
| `-vv` | ещё подробнее: не обрезает длинные значения в ассертах и в параметрах |
| `--alluredir` | **allure dir**ectory — куда складывать сырые результаты для Allure. **Ключ плагина `allure-pytest`** |

Без `-v` вывод компактный: `....F..s.` — точка это пройденный тест, `F` — упавший, `s` — пропущенный, `E` — ошибка, `x` — xfail.

### 2. Отбор тестов: `-k` и `-m`

Два разных механизма, их часто путают — и это ровно тот вопрос, который могут задать.

| | `-k` | `-m` |
|---|---|---|
| По чему отбирает | **по именам** (тест, класс, модуль) | **по маркерам** `@pytest.mark.*` |
| Откуда берётся | подстрока в идентификаторе | явная разметка в коде |
| Мнемоника | **k**eyword | **m**arker |

#### Синтаксис выражений (общий для обоих)

Поддерживаются `and`, `or`, `not` и скобки:

```bash
pytest -k "license"                          # имя содержит license
pytest -k "license or update"                # любое из двух
pytest -k "license and not expired"          # первое есть, второго нет
pytest -k "(license or update) and not slow"
pytest -k "TestLicense and active"           # класс + имя метода
pytest -k "not test_slow_import"             # исключить один тест
```

```bash
pytest -m smoke                              # только smoke
pytest -m "regress and not slow"             # регресс без долгих
pytest -m "smoke or critical"
pytest -m "not ui"                           # всё, кроме UI
```

Подстрока в `-k` регистронезависима и ищется в полном идентификаторе — то есть `-k api` зацепит и файл `test_api.py`, и класс `TestApiClient`, и метод `test_check_api_version`.

#### Маркеры: объявление и строгость

```ini
# pytest.ini
[pytest]
markers =
    smoke: критичные сценарии, гоняем на каждый пуш
    regress: полный набор, по расписанию
    ui: тесты через браузер
    slow: дольше 30 секунд
addopts = --strict-markers
```

`--strict-markers` — незарегистрированный маркер становится **ошибкой**, а не предупреждением. Без него опечатка `@pytest.mark.smok` тихо создаёт новый маркер, тест выпадает из `-m smoke`, и никто этого не замечает. На собесе это хороший показатель зрелости — упомянуть стоит.

#### Точечный запуск без выражений

```bash
pytest tests/api/test_licenses.py                          # один файл
pytest tests/api/test_licenses.py::test_expired            # один тест
pytest tests/api/test_licenses.py::TestLicense::test_active  # метод класса
pytest "tests/test_x.py::test_status[expiry_day]"          # один параметр из parametrize
pytest tests/api/                                          # каталог
```

Последняя форма — то, ради чего в `parametrize` задаются `ids`: можно перезапустить ровно упавший кейс.

### 3. Полная таблица ключей

#### Отбор и объём прогона

| Ключ | Полная форма | Расшифровка буквы | Что делает |
|---|---|---|---|
| `-k EXPR` | — | **k**eyword | отбор по имени |
| `-m EXPR` | — | **m**arker | отбор по маркерам |
| `-x` | `--exitfirst` | e**x**it | остановиться на первом падении |
| — | `--maxfail=N` | — | остановиться после N падений |
| — | `--deselect PATH` | — | исключить конкретный тест/файл |
| — | `--ignore=PATH` | — | не собирать этот путь вовсе |
| — | `--collect-only` / `--co` | **co**llect | показать, что было бы запущено, но не запускать |

`--co` — очень полезная привычка: перед долгим прогоном посмотреть, что вообще попало в выборку. Особенно после правки `-k`.

#### Вывод

| Ключ | Полная форма | Расшифровка | Что делает |
|---|---|---|---|
| `-v` | `--verbose` | **v**erbose | по строке на тест |
| `-vv` | — | — | не обрезать длинные значения |
| `-q` | `--quiet` | **q**uiet | компактнее обычного; `-qq` ещё компактнее |
| `-s` | `--capture=no` | **s**how output | не перехватывать `print` и stdout |
| `-l` | `--showlocals` | **l**ocals | показать локальные переменные в трейсбеке |
| `-r CHARS` | — | **r**eport | сводка в конце по типам результатов |
| — | `--tb=STYLE` | **t**race**b**ack | формат трейсбека |
| — | `--durations=N` | — | N самых долгих тестов |

**Буквы для `-r`:**

| Буква | Что показывает |
|---|---|
| `f` | failed |
| `E` | error |
| `s` | skipped |
| `x` | xfailed — ожидаемо упал |
| `X` | xpassed — ожидали падения, а он прошёл |
| `p` | passed |
| `P` | passed с выводом |
| `a` | всё, кроме passed |
| `A` | вообще всё |
| `N` | ничего |

Практично: `-ra` в CI — короткая сводка всех проблем в конце лога, не листая вверх.

#### Конфигурация

| Ключ | Что делает |
|---|---|
| `-c FILE` | взять конкретный конфиг вместо найденного автоматически |
| `-o KEY=VALUE` / `--override-ini` | переопределить одну опцию ini прямо из командной строки |
| `-p NAME` | подключить плагин |
| `-p no:NAME` | **отключить** плагин, например `-p no:cacheprovider` |
| `--rootdir=PATH` | явно задать корень проекта |
| `-W FILTER` | как обрабатывать предупреждения, например `-W error::DeprecationWarning` |

### 4. Параллельный запуск: pytest-xdist

Ставится отдельно: `pip install pytest-xdist`.

| Ключ | Значение |
|---|---|
| `-n 4` | четыре процесса |
| `-n auto` | по числу логических ядер |
| `-n logical` | то же, явно про логические ядра |
| `--dist load` | по умолчанию: тесты раздаются воркерам по мере освобождения |
| `--dist loadscope` | тесты одного класса/модуля идут на один воркер |
| `--dist loadfile` | тесты одного файла — на один воркер |
| `--dist loadgroup` | группировка по метке `@pytest.mark.xdist_group` |
| `--dist no` | без распределения |
| `--max-worker-restart=N` | сколько раз перезапускать упавший воркер |

**Что здесь важно понимать (и что спросят):**

Каждый воркер — **отдельный процесс**. Из этого следует три вещи:

1. Фикстуры со `scope="session"` выполнятся **в каждом воркере**, а не один раз на прогон. Если внутри создаётся общий ресурс — запись в БД, файл, пользователь — будет конфликт.
2. Тесты, зависящие от порядка или делящие состояние, при параллели начнут падать. Это не «xdist сломал тесты» — это он вскрыл существующую связность.
3. `--dist loadscope` — компромисс, когда изолировать данные полностью дорого: тесты одного класса гарантированно идут подряд на одном воркере.

Формулировка для собеса:

> Параллель — это не ключ `-n`, это свойство тестов. Если данные изолированы и нет общего состояния, `-n auto` просто ускоряет прогон. Если нет — параллель вскроет связность, и чинить надо изоляцию, а не откатываться в один поток.

### 5. Управление выводом и трейсбеком

#### `--tb` — формат трейсбека

| Значение | Что даёт |
|---|---|
| `--tb=auto` | по умолчанию: длинный для первого и последнего падения, короткий для остальных |
| `--tb=long` | полный трейсбек для всех |
| `--tb=short` | одна строка на кадр стека — самый практичный в CI |
| `--tb=line` | одна строка на всё падение |
| `--tb=native` | стандартный питоновский формат |
| `--tb=no` | без трейсбека вообще |

В CI обычно `--tb=short`: лог остаётся читаемым, а детали смотрятся в артефактах.

#### `-s` — почему он нужен

По умолчанию pytest перехватывает вывод и показывает его только у упавших тестов. `-s` отключает перехват — всё летит в консоль сразу. Нужен, когда отлаживаешь `print`-ами или когда библиотека пишет что-то важное в stdout.

Полная форма — `--capture=no`. Есть ещё `--capture=sys` и `--capture=fd` — разные уровни перехвата.

### 6. Кеш прошлого прогона

pytest хранит результаты в каталоге `.pytest_cache`.

| Ключ | Расшифровка | Что делает |
|---|---|---|
| `--lf` | **l**ast **f**ailed | только упавшие в прошлый раз |
| `--ff` | **f**ailed **f**irst | упавшие первыми, потом все остальные |
| `--nf` | **n**ew **f**irst | новые файлы первыми |
| `--cache-clear` | — | очистить кеш перед прогоном |
| `--lfnf=all\|none` | last failed — no failures | что делать, если падений не было: гнать всё или ничего |

Рабочий цикл при починке: `pytest` → упало пять → правка → `pytest --lf` → упало два → правка → `pytest --lf` → зелено → полный прогон для проверки.

В CI `--lf` не используют: там каждый прогон должен быть полным и независимым от кеша.

### 7. Отладка

| Ключ | Что делает |
|---|---|
| `--pdb` | при падении бросить в интерактивный отладчик прямо в точке ошибки |
| `--trace` | войти в отладчик в начале каждого теста |
| `--setup-show` | показать порядок создания и разрушения фикстур |
| `--setup-plan` | показать план фикстур, ничего не выполняя |
| `-l` | локальные переменные в трейсбеке |

`--setup-show` — лучший инструмент, когда непонятно, почему фикстура не отработала или отработала не в том порядке. На собесе упомянуть уместно: показывает, что вы понимаете, как устроен жизненный цикл фикстур, а не просто пишете декораторы.

### 8. Отчёты

| Ключ | Плагин | Что делает |
|---|---|---|
| `--alluredir=DIR` | `allure-pytest` | сырые результаты для Allure |
| `--clean-alluredir` | `allure-pytest` | очистить каталог перед прогоном |
| `--junitxml=FILE` | встроен | отчёт в формате JUnit XML — понимают GitLab CI, Jenkins, TeamCity |
| `--html=FILE` | `pytest-html` | самодостаточный HTML-отчёт |
| `--cov=PKG --cov-report=html` | `pytest-cov` | покрытие кода |

Генерация HTML из Allure — отдельный шаг, уже вне pytest:

```bash
pytest --alluredir=allure-results --clean-alluredir
allure generate allure-results -o allure-report --clean
```

### 9. Коды выхода

Это то, на чём держится гейт в CI: пайплайн смотрит на код возврата.

| Код | Значение |
|---|---|
| `0` | все тесты прошли |
| `1` | часть тестов упала |
| `2` | прогон прерван пользователем |
| `3` | внутренняя ошибка |
| `4` | ошибка в аргументах командной строки |
| `5` | **не собрано ни одного теста** |

Пятый — самый коварный. Опечатались в `-k` или `-m`, тестов не нашлось, прогон «не упал» — а покрытия не было. Поэтому в CI полезно явно ловить код 5 и считать его ошибкой:

```yaml
script:
  - pytest -m smoke --tb=short -ra
  - if [ $? -eq 5 ]; then echo "Не собрано ни одного теста"; exit 1; fi
```

### 10. Вынос параметров в конфиг

Всё, что вы гоняете постоянно, не надо каждый раз писать руками — это выносится в `addopts`.

```ini
# pytest.ini
[pytest]
testpaths = tests
python_files = test_*.py
python_classes = Test*
python_functions = test_*

addopts =
    -ra
    --strict-markers
    --tb=short
    --alluredir=allure-results

markers =
    smoke: критичные сценарии
    regress: полный набор
    ui: браузерные тесты
    slow: дольше 30 секунд
```

Теперь `pytest -m smoke` уже включает в себя сводку, строгие маркеры, короткий трейсбек и allure-каталог.

То же самое можно держать в `pyproject.toml`:

```toml
[tool.pytest.ini_options]
addopts = "-ra --strict-markers --tb=short"
testpaths = ["tests"]
markers = ["smoke: критичные сценарии", "regress: полный набор"]
```

Разовое переопределение без правки файла:

```bash
pytest -o addopts="" -k license      # отключить addopts на один запуск
```

### 11. Готовые команды под задачи

```bash
# Быстрый гейт на пуш: smoke, параллельно, падаем на первой ошибке
pytest -m smoke -n auto -x --tb=short -ra

# Ночной полный регресс с отчётом
pytest -m "regress and not slow" -n auto --alluredir=allure-results --clean-alluredir -ra

# Починка: только то, что упало
pytest --lf -vv -l

# Отладка одного теста с выводом print
pytest tests/api/test_licenses.py::test_expired -s -vv --tb=long

# Один параметр из parametrize
pytest "tests/api/test_licenses.py::test_status[expiry_day]" -vv

# Посмотреть выборку, ничего не запуская
pytest -m "smoke and not ui" --co -q

# Найти самые медленные тесты
pytest --durations=10

# Разобраться с порядком фикстур
pytest tests/api/test_licenses.py --setup-show

# Прогон без параллели, если подозрение на связность тестов
pytest -m regress -p no:randomly --tb=short
```

# J. Шпаргалка на один экран

**Перед звонком проговорить вслух:**

- Рамку про стек (блок 0) — один раз, в начале.
- Фикстура, scope, conftest, parametrize, маркеры — определения без пауз.
- Три критичных пути их продукта: обновление не доехало, лицензия неверно определена, телеметрия потеряна/задублирована.
- Три риска безопасности: доступ к чужой инсталляции по id, подмена обновления, утечка между клиентами.
- «Завожу баг всегда, обсуждаю severity» — не сдвигаться под нажимом.
- «Я не пентестер, но риск умею превратить в тест-кейс» — рамка по безопасности, один раз.

**Держать под рукой (второй экран, не читать с него в камеру):**

```python
@pytest.fixture(scope="function")          # function class module package session
def x():
    setup(); yield value; teardown()

@pytest.mark.parametrize("a,b", [(1,2)], ids=["case"])
@pytest.mark.smoke
with pytest.raises(ValueError) as e: ...
pytest -m smoke -n auto -k "name" --lf -x
```

**Правила поведения:**

- Отвечать структурой: сначала принцип в одну фразу, потом пример. Не начинать с разгона («это комплексный вопрос, на самом деле…»).
- На задаче — **сначала уточняющие вопросы**, потом решение. Молчаливое ныряние в детали было ошибкой на ДМС.
- Не знаете — сказать «не сталкивался, но рассуждаю так…» и рассуждать. Это оценивается выше, чем угадывание.
- Цифры вместо абстракций: «4 часа → 40 минут», «10–15 критичных сценариев», «месяц до рабочего гейта».
- Короткие предложения. Убрать «в этом есть моя осведомлённость», «глаз наточен», «вайб».
