# Глава 1. Основы Docker

## 1.1. Проблема классического сервера

Возьмём обычный сервер (или ваш ноутбук). Снизу вверх:

- **железо** (CPU, память, диск);
- **операционная система** (Linux/Windows);
- **программы**, которые вы ставите поверх ОС.

Проблема в **зависимостях**. Каждая программа использует библиотеки нужных версий. Пока приложения не пересекаются — всё хорошо. Но как только двум приложениям нужны **разные версии** одной и той же библиотеки — начинаются «танцы с бубном»: конфликт версий, «у меня на машине работает, а на сервере нет», хрупкая настройка окружения.

## 1.2. Идея Docker: изоляция в контейнере

Docker решает это через **контейнеры**. Поверх ОС ставится программа **Docker**, а каждое приложение упаковывается в свой **контейнер** — «капсулу», внутри которой лежит и само приложение, **и все нужные ему библиотеки и зависимости** именно тех версий, что ему нужны.

Ключевой эффект: приложение внутри контейнера **не обращается к библиотекам операционной системы** — у него всё своё. Поэтому:

- контейнеры **независимы** друг от друга (у каждого свои версии зависимостей — конфликтов нет);
- приложение работает **стабильно и одинаково** везде, где есть Docker;
- под каждую программу — свой контейнер, они не мешают друг другу.

```
Классический сервер            Сервер с Docker
──────────────────            ──────────────────
   [ Приложения ]              [конт.A][конт.B][конт.C]  ← у каждого свои
   [     ОС     ]              [        Docker        ]     библиотеки
   [   Железо   ]              [          ОС          ]
                               [        Железо        ]
```

## 1.3. Docker vs виртуальные машины (важное отличие)

Оба дают изоляцию, но по-разному:

|                   | Виртуальная машина                   | Docker-контейнер            |
| ----------------- | ------------------------------------ | --------------------------- |
| Что изолирует     | целую **гостевую ОС** со своим ядром | процесс + его зависимости   |
| Ядро ОС           | своё в каждой ВМ                     | **общее ядро хоста**        |
| Вес               | гигабайты, медленный старт           | мегабайты, старт за секунды |
| Накладные расходы | высокие (гипервизор)                 | минимальные                 |

ВМ виртуализирует **железо** и тащит полноценную ОС в каждой машине. Контейнер же **шарит ядро хоста** и упаковывает только приложение с зависимостями — поэтому он лёгкий и быстрый.

## 1.4. Почему Docker «работает только на Linux»

Docker опирается на возможности **ядра Linux** (namespaces, cgroups). Поэтому:

- на **Linux** контейнеры запускаются нативно поверх ядра хоста;
- на **Windows/macOS** Docker поднимает под капотом **лёгкую виртуальную Linux-машину**, и контейнеры работают уже в ней. Ставится это автоматически (Docker Desktop / WSL2) — вам ничего вручную делать не нужно, но «промежуточный Linux» там всегда есть.

Вывод: по сути Docker — это про Linux; на других ОС он живёт через тонкую Linux-прослойку.

**Мини-итог главы 1.** Docker упаковывает приложение вместе с зависимостями в изолированную капсулу-контейнер, что убирает конфликты версий и даёт «работает одинаково везде». В отличие от ВМ, контейнеры лёгкие, потому что делят ядро хоста.

# Глава 2. Установка Docker

## 2.1. Linux

На Linux Docker ставится нативно. Общая схема (Ubuntu/Debian) — через официальный репозиторий:

```bash
# быстрый способ (официальный скрипт)
curl -fsSL https://get.docker.com | sh

# проверка
docker --version
docker run hello-world     # тестовый контейнер: если вывелось приветствие — всё ок
```

Чтобы запускать `docker` без `sudo`, добавьте пользователя в группу docker (и перезайдите в сессию):

```bash
sudo usermod -aG docker $USER
```

## 2.2. Windows / macOS

Ставится **Docker Desktop** — графическое приложение, которое само поднимает Linux-прослойку (на Windows — через WSL2). Скачивается с сайта docker.com, устанавливается «далее-далее», после запуска в трее появляется значок кита. Проверка — та же:

```bash
docker --version
docker run hello-world
```

**Мини-итог главы 2.** На Linux — нативно, на Windows/macOS — через Docker Desktop, который сам создаёт Linux-виртуалку. Проверка установки — `docker run hello-world`.

# Глава 3. Образы и контейнеры

Два центральных понятия, которые нельзя путать.

- **Образ (image)** — неизменяемый «слепок»/шаблон: файловая система + приложение + зависимости + инструкция запуска. Как ISO-образ, из которого ставят систему. Образ **только для чтения**.
- **Контейнер (container)** — **запущенный экземпляр образа**. Из одного образа можно поднять сколько угодно контейнеров. Контейнер добавляет поверх образа тонкий **записываемый слой**.

Аналогия: образ — это класс, контейнер — объект этого класса.

## 3.1. Docker Hub и теги

Образы берутся из **реестра** — по умолчанию это **Docker Hub** (публичный каталог). Когда вы пишете `docker run nginx`, Docker:

1. ищет образ `nginx` локально;
2. если нет — **скачивает** (pull) его с Docker Hub;
3. создаёт из него контейнер и запускает.

**Тег** — версия образа, указывается через двоеточие: `nginx:1.27`, `ubuntu:22.04`, `mysql:5.7`. Если тег не указан — берётся **`latest`** (последняя стабильная).

```bash
docker run ubuntu          # = ubuntu:latest
docker run ubuntu:20.04    # конкретная версия
```

> Правило: в проде **всегда фиксируйте тег** (`ubuntu:22.04`), а не `latest` — иначе завтра образ обновится и поведение изменится.

**Мини-итог главы 3.** Образ — шаблон (read-only), контейнер — его запущенный экземпляр. Образы тянутся из Docker Hub, версия задаётся тегом; без тега — `latest`.

# Глава 4. Основные команды

Здесь — рабочий минимум на каждый день. Разберём на образах `ubuntu` и `nginx`.

## 4.1. Запуск контейнера: `docker run`

Общая форма:

```
docker run [опции] ОБРАЗ[:тег] [команда] [аргументы]
```

Примеры:

```bash
docker run ubuntu:20.04 echo "hello"     # запустить, выполнить команду и выйти
docker run -it ubuntu:20.04 bash         # интерактивный терминал внутри контейнера
docker run -d nginx                      # запустить в фоне (detached)
```

**Ключевые опции `run`:**

| Опция | Что делает |
|---|---|
| `-d` (`--detach`) | запустить в **фоне**, вернуть управление терминалу |
| `-it` | **интерактивный** режим + терминал (`-i` держит STDIN, `-t` даёт TTY) — чтобы «зайти внутрь» |
| `--rm` | **удалить** контейнер автоматически после остановки (не копить мусор) |
| `--name ИМЯ` | дать контейнеру **имя** (иначе Docker придумает случайное) |
| `-p ХОСТ:КОНТ` | проброс порта (глава 5) |
| `-e ПЕРЕМ=знач` | переменная окружения (глава 6) |
| `-v ...` | монтирование данных (глава 7) |

Имя удобно тем, что дальше можно управлять контейнером по нему, а не по ID:

```bash
docker run -d --name web nginx
docker stop web
docker start web
```

## 4.2. Список контейнеров: `docker ps`

```bash
docker ps          # только РАБОТАЮЩИЕ контейнеры
docker ps -a       # ВСЕ контейнеры, включая остановленные
```

В выводе: `CONTAINER ID`, `IMAGE`, `COMMAND`, `STATUS`, `PORTS`, `NAMES`.

## 4.3. Логи: `docker logs`

```bash
docker logs web        # показать логи контейнера
docker logs -f web     # follow: живой поток логов (как tail -f)
```

Незаменимо, когда ищете ошибку или следите за процессом в реальном времени.

## 4.4. Зайти внутрь работающего контейнера: `docker exec`

```bash
docker exec -it web bash     # открыть shell внутри контейнера web
```

Важно: внутри минимальных образов (nginx и т.п.) **нет многих привычных команд** — контейнеры делают минимальными, только необходимое для работы приложения. Иногда вместо `bash` есть только `sh`.

> ⚠️ Файлы, созданные внутри контейнера «руками», **теряются при его удалении** — контейнер эфемерен. Чтобы данные жили дольше — тома (глава 7).

## 4.5. Мониторинг ресурсов: `docker stats`

```bash
docker stats            # живая таблица: CPU %, память, сеть, диск по контейнерам
docker stats web        # по одному контейнеру
```

## 4.6. Полная информация: `docker inspect`

```bash
docker inspect web      # весь JSON о контейнере: порты, тома, сеть, как собран
```

Полезно, когда пришли на незнакомый сервер и надо понять, как настроен контейнер.

## 4.7. Остановка, запуск, удаление

```bash
docker stop web         # мягко остановить
docker start web        # запустить снова
docker rm web           # удалить контейнер (сначала остановить, либо docker rm -f web)
docker images           # список локальных образов
docker rmi nginx        # удалить образ
```

## 4.8. Массовая уборка: `docker system prune`

```bash
docker system prune              # удалить всё неиспользуемое (остановленные конт., висячие образы, сети)
docker system prune --volumes    # плюс неиспользуемые тома (данные!) — с осторожностью
```

> ⚠️ `--volumes` удаляет данные томов безвозвратно. Перед этим убедитесь, что там нет нужного.

**Мини-итог главы 4.** `run` (+`-d/-it/--rm/--name`) запускает; `ps/ps -a` показывает; `logs -f` следит; `exec -it` заходит внутрь; `stats`/`inspect` диагностируют; `stop/start/rm/rmi` управляют; `system prune` убирает мусор.

**Практика.** Запустите `nginx` в фоне с именем `web`, посмотрите `docker ps`, гляньте `docker logs web`, зайдите внутрь `docker exec -it web sh`, выйдите, остановите и удалите.

# Глава 5. Проброс портов (port mapping)

## 5.1. Зачем

Docker-контейнер по умолчанию **изолирован по сети** — порт, открытый внутри контейнера, снаружи недоступен. Если внутри контейнера работает веб-сервер nginx на порту **80**, извне к нему **не подключиться напрямую**: порт открыт только внутри контейнера.

Чтобы дать доступ снаружи, порт контейнера нужно **пробросить** на порт хоста опцией `-p`:

```
-p ПОРТ_ХОСТА:ПОРТ_КОНТЕЙНЕРА
```

## 5.2. Примеры

```bash
docker run -d --name web -p 80:80 nginx
```

Здесь `80:80` означает: запросы на порт **80 сервера** пробрасываются в порт **80 контейнера**. Теперь по IP/домену сервера на порту 80 открывается nginx.

Если на одном сервере нужно несколько nginx (все слушают 80 внутри), снаружи их разводят по **разным портам хоста**:

```bash
docker run -d --name web1 -p 8080:80 nginx
docker run -d --name web2 -p 8081:80 nginx
```

Пользователь заходит на `сервер:8080` → попадает в контейнер web1, на `сервер:8081` → в web2. Внутри оба слушают 80 — конфликта нет, потому что различаются **порты хоста**.

```
     хост:8080 ──▶ контейнер web1 :80 (nginx)
     хост:8081 ──▶ контейнер web2 :80 (nginx)
```

**Мини-итог главы 5.** Контейнер сетево изолирован; `-p хост:контейнер` пробрасывает порт наружу. Порт контейнера может повторяться у разных контейнеров, а порт хоста должен быть уникальным.

**Практика.** Поднимите два nginx на `8080:80` и `8081:80`, откройте оба в браузере.

# Глава 6. Переменные окружения

## 6.1. Что это и зачем

**Переменная окружения (environment variable)** — пара «имя=значение», которую видит процесс внутри контейнера. Через них приложения **настраивают**: пароли, режимы, параметры подключения. Задаются опцией `-e` при запуске:

```bash
docker run -e MY_VAR=1234 ubuntu env     # env выведет все переменные, включая MY_VAR
```

Внутри контейнера переменные можно посмотреть командой `env` или `printenv`.

## 6.2. Практический пример — MySQL

Многие официальные образы **конфигурируются именно переменными**. Классика — `mysql`: без обязательной переменной с паролем контейнер просто не стартует.

```bash
docker run -d --name db \
  -e MYSQL_ROOT_PASSWORD=secret123 \
  mysql:5.7
```

- `MYSQL_ROOT_PASSWORD` — задаёт пароль root (обязательная);
- у образа есть и другие переменные (`MYSQL_DATABASE`, `MYSQL_USER`, `MYSQL_PASSWORD`), их список — в документации образа на Docker Hub.

> Идея: одна и та же программа настраивается под задачу **без пересборки образа** — просто разными переменными при запуске.

**Мини-итог главы 6.** `-e ИМЯ=значение` передаёт настройки внутрь контейнера. Официальные образы (mysql, postgres…) конфигурируются переменными; их список смотрите в описании образа.

**Практика.** Запустите `mysql:5.7` с `MYSQL_ROOT_PASSWORD`, зайдите `docker exec -it db bash` и проверьте `env`.

# Глава 7. Постоянные данные: volumes

## 7.1. Проблема эфемерности

Контейнер **эфемерен**: его записываемый слой живёт, пока жив контейнер. Удалили контейнер (или пересоздали) — **все данные внутри пропали**. Для базы данных это катастрофа: перезапустили MySQL — потеряли все таблицы.

Решение — **тома (volumes)**: хранить данные **вне** контейнера, чтобы они переживали его перезапуск и удаление.

## 7.2. Три способа монтирования

**1. Bind mount — привязка папки хоста.** Конкретная директория хоста монтируется внутрь контейнера:

```bash
docker run -d --name db \
  -e MYSQL_ROOT_PASSWORD=secret123 \
  -v /opt/mysql/data:/var/lib/mysql \
  mysql:5.7
```

`/opt/mysql/data` (на хосте) ↔ `/var/lib/mysql` (внутри, где MySQL хранит данные). Теперь данные лежат на хосте и не исчезнут с контейнером. Удобно, когда хотите видеть файлы прямо на сервере.

**2. Именованный том (named volume) — управляется Docker.** Docker сам хранит данные в своём каталоге, вы обращаетесь по имени:

```bash
docker volume create mysql_data
docker run -d --name db \
  -e MYSQL_ROOT_PASSWORD=secret123 \
  -v mysql_data:/var/lib/mysql \
  mysql:5.7
```

**3. Анонимный том.** Указываете только путь в контейнере — Docker создаёт том с автоимененем:

```bash
docker run -d -v /var/lib/mysql mysql:5.7
```

## 7.3. Управление томами

```bash
docker volume ls                 # список томов
docker volume create mysql_data  # создать
docker volume inspect mysql_data # где физически лежит, кто использует
docker volume rm mysql_data      # удалить (том должен быть не занят)
docker volume prune              # удалить неиспользуемые тома
```

## 7.4. Что выбрать

- **Именованный том** — рекомендованный дефолт для БД и «данных приложения»: переносимо, Docker управляет.
- **Bind mount** — когда нужен прямой доступ к файлам с хоста (конфиги, разработка, отдача статики).
- **Анонимный** — на быстрые эксперименты.

**Мини-итог главы 7.** Данные внутри контейнера эфемерны; тома выносят их наружу. Три вида: bind mount (папка хоста), named volume (управляется Docker), анонимный. Для БД — именованный том.

**Практика.** Запустите MySQL с named volume, создайте базу, удалите контейнер, поднимите заново с тем же томом — данные на месте.

# Глава 8. Сети в Docker

## 8.1. Зачем свои сети

Контейнерам часто нужно **общаться между собой** (приложение ↔ база). Docker даёт для этого **сети**. Главный бонус пользовательской сети — контейнеры в ней **находят друг друга по имени** (встроенный DNS), а не по меняющимся IP.

## 8.2. Три типа сетей

| Тип | Что это |
|---|---|
| **bridge** | тип по умолчанию: изолированная внутренняя сеть-«мостик», контейнеры общаются между собой, наружу — через проброс портов |
| **host** | контейнер использует **сеть хоста напрямую** (без изоляции портов; `-p` не нужен и не работает) |
| **none** | без сети вообще (полная сетевая изоляция) |

По умолчанию новый контейнер попадает в стандартную сеть **bridge**.

## 8.3. Создание своей сети и связь контейнеров

```bash
docker network create app-net           # создать сеть (по умолчанию тип bridge)
docker network ls                        # список сетей
docker network inspect app-net           # детали, кто подключён

# подключаем контейнеры к одной сети
docker run -d --name db  --network app-net -e MYSQL_ROOT_PASSWORD=secret mysql:5.7
docker run -d --name app --network app-net -p 8080:80 my-app
```

Теперь контейнер `app` обращается к базе просто по имени **`db`** (например, хост БД = `db`, порт 3306) — Docker сам резолвит имя в нужный IP. Это ключевая причина заводить свою сеть, а не полагаться на IP.

```bash
docker network connect app-net web       # подключить существующий контейнер к сети
docker network disconnect app-net web     # отключить
```

**Мини-итог главы 8.** Сети связывают контейнеры; в пользовательской bridge-сети они видят друг друга **по имени**. Типы: bridge (дефолт, изолированный мостик), host (сеть хоста), none (без сети).

**Практика.** Создайте сеть, поднимите в ней `mysql` (`--name db`) и `adminer`, подключитесь из adminer к хосту `db`.

# Глава 9. Свой образ: Dockerfile

## 9.1. Что такое Dockerfile

**Dockerfile** — текстовый «рецепт», по которому Docker **собирает образ**. В нём по шагам описано: от какого базового образа отталкиваемся, какие пакеты ставим, какие файлы копируем, что запускается при старте. Из этого рецепта командой `docker build` получается образ, из образа — контейнеры.

## 9.2. Основные инструкции

| Инструкция | Назначение |
|---|---|
| `FROM` | **базовый образ**, с которого начинаем (`FROM ubuntu:22.04`). Обязательна, идёт первой |
| `LABEL` | метаданные образа (автор, описание) — необязательно |
| `RUN` | выполнить команду **на этапе сборки** (поставить пакеты, скомпилировать) |
| `WORKDIR` | задать **рабочую директорию** внутри образа |
| `COPY` | скопировать файлы **с хоста в образ** (`COPY index.html /usr/share/nginx/html/`) |
| `ENV` | переменные окружения **по умолчанию** (можно переопределить при `run -e`) |
| `EXPOSE` | **информационно** объявить порт (сам порт не публикует — публикует `-p`) |
| `CMD` | команда по умолчанию при **запуске** контейнера (легко переопределить) |
| `ENTRYPOINT` | основная команда запуска (жёстче CMD; аргументы дописываются к ней) |

Важно про запуск: контейнер живёт, пока в нём работает основной процесс. Если процесс завершился — контейнер останавливается. Поэтому в конце Dockerfile описывают, что запускать (`CMD`/`ENTRYPOINT`).

## 9.3. Пример 1 — простейший образ

`Dockerfile`:

```dockerfile
FROM ubuntu:22.04
CMD echo "Hello, my first Docker image"
```

Сборка и запуск:

```bash
docker build -t myfirst .      # -t = имя (tag) образа; . = где лежит Dockerfile
docker images                  # увидим ubuntu (базовый) и myfirst (наш)
docker run --rm myfirst        # выведет строку и выйдет
```

При сборке видно шаги: `Step 1` (FROM — тянется ubuntu), `Step 2` (CMD) и т.д. Каждый шаг — **слой** образа.

## 9.4. Пример 2 — свой веб-сервер на nginx со своей страницей

`index.html`:

```html
<h1>Моя страница в контейнере</h1>
```

`Dockerfile`:

```dockerfile
FROM nginx:latest
COPY index.html /usr/share/nginx/html/index.html
EXPOSE 80
# CMD не нужен: базовый образ nginx уже запускает сервер
```

Сборка и запуск:

```bash
docker build -t my-site .
docker run -d --name site -p 8080:80 my-site
# открываем http://localhost:8080 — видим свою страницу
```

## 9.5. CMD vs ENTRYPOINT (коротко)

- **`CMD`** — «команда по умолчанию»; если при `docker run` передать свою команду, она **заменит** CMD.
- **`ENTRYPOINT`** — «неизменяемое начало» команды; аргументы из `docker run` **дописываются** к нему.
- Частый паттерн: `ENTRYPOINT` = сама программа, `CMD` = аргументы по умолчанию.

## 9.6. Про слои и кэш (важно для скорости)

Каждая инструкция — **слой**, слои **кэшируются**. Docker пересобирает слой только если он или что-то выше изменилось. Поэтому редко меняющееся (установку пакетов) ставят **выше**, а часто меняющееся (копирование кода) — **ниже**, чтобы не пересобирать тяжёлые слои каждый раз.

**Мини-итог главы 9.** Dockerfile — рецепт образа: `FROM` → `RUN/COPY/WORKDIR/ENV/EXPOSE` → `CMD/ENTRYPOINT`. Сборка — `docker build -t имя .`. Инструкции дают слои, слои кэшируются.

**Практика.** Соберите свой nginx-образ со своей `index.html`, запустите на `8080:80`, откройте в браузере.

# Глава 10. Docker Compose

## 10.1. Зачем

Запускать вручную несколько связанных контейнеров (`app` + `db` + сеть + тома + порты) длинными `docker run` — утомительно и легко ошибиться. **Docker Compose** описывает **весь стек в одном YAML-файле** (`docker-compose.yml`) и поднимает его одной командой.

## 10.2. Пример `docker-compose.yml`

```yaml
services:
  web:
    build: .                 # собрать из Dockerfile в текущей папке
    ports:
      - "8080:80"
    networks:
      - app-net
    depends_on:
      - db

  db:
    image: mysql:5.7
    environment:
      MYSQL_ROOT_PASSWORD: secret123
      MYSQL_DATABASE: appdb
    volumes:
      - db_data:/var/lib/mysql
    networks:
      - app-net

networks:
  app-net:
    driver: bridge

volumes:
  db_data:
```

Что здесь есть: два сервиса (`web`, `db`), их порты, переменные, том для данных БД, общая **bridge-сеть**, по которой `web` обращается к базе по имени `db`.

## 10.3. Основные команды

```bash
docker compose up -d        # собрать (если надо) и поднять весь стек в фоне
docker compose ps           # что запущено в рамках compose
docker compose logs -f      # логи всех сервисов
docker compose stop         # остановить сервисы (контейнеры остаются)
docker compose down         # остановить и удалить контейнеры/сеть
docker compose down -v      # то же + удалить тома (данные!)
```

> Примечание по версиям: раньше была отдельная утилита `docker-compose` (с дефисом), сейчас это встроенная подкоманда `docker compose` (без дефиса). Синтаксис YAML тот же.

**Мини-итог главы 10.** Compose описывает многоконтейнерный стек в `docker-compose.yml` (сервисы, порты, переменные, тома, сети) и поднимает его одной командой `docker compose up -d`. Внутри одной сети сервисы видят друг друга по имени.

**Практика.** Опишите в compose связку `web` (свой nginx-образ) + `db` (mysql) в одной сети, поднимите `docker compose up -d`, проверьте `docker compose ps`, погасите `docker compose down`.

# Глава 11. Portainer

**Portainer** — популярная **графическая веб-оболочка** для управления Docker: контейнеры, образы, тома, сети, логи, консоль — всё мышкой в браузере, без запоминания команд.

Portainer сам запускается как контейнер и хранит своё состояние в томе:

```bash
docker volume create portainer_data
docker run -d \
  --name portainer \
  -p 9443:9443 \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v portainer_data:/data \
  portainer/portainer-ce:latest
```

- `-p 9443:9443` — веб-интерфейс (открывается в браузере, при первом входе создаёте админа);
- `-v /var/run/docker.sock:/var/run/docker.sock` — **ключевая строка**: даёт Portainer доступ к Docker-демону хоста, чтобы он мог управлять контейнерами;
- `-v portainer_data:/data` — том под его настройки.

После старта заходим на `https://localhost:9443`, задаём пароль администратора и видим дашборд: списки контейнеров/образов/томов/сетей, кнопки старт/стоп/логи/консоль.

> ⚠️ Монтирование `docker.sock` = фактически полный контроль над Docker хоста. На проде доступ к Portainer надо закрывать (аутентификация, сеть).

**Мини-итог главы 11.** Portainer — GUI для Docker: удобно смотреть и управлять контейнерами через браузер. Запускается контейнером с доступом к `docker.sock`.

# Шпаргалка команд

```bash
# Образы
docker pull nginx:1.27            # скачать образ

docker rmi nginx:1.27             # удалить образ

docker inspect web                             # вся инфа
docker stop web / docker start web             # стоп/старт
docker rm -f web                               # удалить (принудительно)

# Тома
docker volume create data
docker volume ls / inspect data / rm data

# Сети
docker network create app-net

docker run -e MYSQL_ROOT_PASSWORD=secret mysql:5.7

# Уборка

docker system prune --volumes      # + тома (осторожно)

# Compose
docker compose up -d
docker compose ps / logs -f
docker compose down [-v]
```

# Глоссарий

- **Образ (image)** — неизменяемый шаблон приложения с зависимостями; из него создаются контейнеры.
- **Контейнер (container)** — запущенный экземпляр образа с тонким записываемым слоем.
- **Docker Hub** — публичный реестр образов (откуда идёт `pull` по умолчанию).
- **Тег (tag)** — версия образа (`ubuntu:22.04`); по умолчанию `latest`.
- **Dockerfile** — рецепт сборки образа (`FROM/RUN/COPY/CMD`…).
- **build** — сборка образа из Dockerfile.
- **Проброс портов (`-p`)** — публикация порта контейнера на порт хоста.
- **Переменная окружения (`-e`)** — настройка приложения внутри контейнера.
- **Том (volume)** — хранилище данных вне контейнера (переживает пересоздание). Виды: bind mount, named, анонимный.
- **Сеть (network)** — связь контейнеров; в пользовательской bridge-сети — по имени. Типы: bridge/host/none.
- **CMD / ENTRYPOINT** — что запускается при старте контейнера.
- **Docker Compose** — описание многоконтейнерного стека в YAML + запуск одной командой.
- **Portainer** — веб-GUI для управления Docker.
- **detached (`-d`)** — запуск в фоне; **interactive (`-it`)** — интерактивный терминал внутри контейнера.

# Дополнение. Что нового во втором курсе (Docker для начинающих, Богдан)

Ниже — материал из второго видео, которого **не было** в основной части пособия. Это углубление, а не повтор: архитектура Docker, слои образа и записываемый слой, реестр vs репозиторий, публикация своего образа и дополнительные практики Dockerfile.

## Д1. Архитектура Docker: клиент, демон, хост

Раньше мы говорили «Docker что-то делает». На самом деле Docker — это **клиент-серверная система** из трёх частей:

- **Docker Client (клиент)** — то, что вы вызываете в терминале командой `docker`. Сам он ничего не создаёт — только **отправляет запросы**.
- **Docker Daemon (демон / служба / сервер, `dockerd`)** — служба, которая **делает всю работу**: скачивает образы, создаёт и запускает контейнеры, управляет сетями и томами, обрабатывает запросы клиентов.
- **Docker Host (хост)** — компьютер, на котором запущен демон.

Клиент общается с демоном по **REST API** (локально — обычно через Unix-сокет `/var/run/docker.sock`). Демон может быть **на той же машине** (обычный случай) или **удалённым** — тогда одним клиентом можно управлять Docker на другом сервере.

```
[ docker CLI ]  ──REST API──▶  [ dockerd (демон) ]  ──▶  контейнеры / образы / сети / тома
   (клиент)      /var/run/docker.sock     (сервер)         ▲
                                                           │ pull / push
                                                    [ Registry: Docker Hub ]
```

> Практический вывод: когда вы монтируете `-v /var/run/docker.sock:/var/run/docker.sock` (как в главе про Portainer) — вы даёте контейнеру доступ **к тому самому API демона**, то есть полный контроль над Docker.

## Д2. Слои образа и записываемый слой контейнера

Это ключевая модель, объясняющая, почему образы лёгкие, а контейнеры эфемерны.

**Образ состоит из слоёв (layers).** Слой — это **набор файлов** (кусочек файловой системы). У образа есть **базовый слой** и добавленные поверх слои: слой 1, слой 2, слой 3… **Каждая инструкция Dockerfile создаёт новый слой.** Все слои образа — **только для чтения (read-only)**.

**Слои переиспользуются между образами.** Если два образа основаны на одном базовом слое (например, оба на `node`), этот слой **хранится на диске один раз** и шарится. Отсюда:

- при `docker pull` скачиваются **только недостающие** слои (архивами); уже имеющиеся локально не качаются повторно — быстрее и меньше трафика;
- одинаковые слои не дублируются на диске — экономия места.

**Контейнер = образ (read-only слои) + тонкий верхний ЗАПИСЫВАЕМЫЙ слой.** Всё, что процесс меняет во время работы, пишется в этот верхний слой по принципу **copy-on-write**. Из одного образа можно поднять много контейнеров — у каждого свой отдельный записываемый слой, база общая.

```
контейнер:  [■ записываемый слой (свой у каждого контейнера)]
образ:      [ слой 3 ] ┐
            [ слой 2 ] ├─ read-only, общие/переиспользуемые
            [ базовый ]┘
```

> Отсюда прямо следует **эфемерность из главы 7**: удалили контейнер → пропал его записываемый слой со всеми изменениями. Поэтому данные выносят в тома.

## Д3. Реестр (registry) vs репозиторий (repository)

Во втором курсе чётко разведены два понятия, которые часто путают:

- **Registry (реестр)** — хранилище **репозиториев**. Бывает публичный (**Docker Hub** — самый большой) и приватный/self-hosted (GitLab Container Registry, Harbor, AWS ECR и т.п.).
- **Repository (репозиторий)** — набор **версий одного и того же образа**, различающихся **тегами**. Аналогия с git: как git-репозиторий хранит версии кода, docker-репозиторий хранит версии образа. Пример: репозиторий `nginx` с тегами `latest`, `1.27`, `1.27-alpine`.

Полное имя образа: **`[реестр/]репозиторий:тег`**, например `docker.io/library/nginx:1.27`. Когда пишете просто `nginx:1.27`, подразумевается Docker Hub. Приватные репозитории — для закрытых образов компании.

## Д4. Публикация своего образа на Docker Hub

Свой собранный образ можно **выложить**, чтобы его тянули другие (или ваши другие машины):

```bash
docker login                                   # войти в аккаунт Docker Hub
docker tag my-site username/my-site:1.0        # дать имя вида репозиторий:тег
docker push username/my-site:1.0               # загрузить в реестр

# на другой машине — просто скачать и запустить:
docker pull username/my-site:1.0
docker run -d -p 8080:80 username/my-site:1.0
```

- `docker tag` не копирует образ, а **добавляет ему ещё одно имя** (нужного формата `username/repo:tag`).
- `docker push` заливает **послойно**; уже существующие в реестре слои не загружаются повторно.

## Д5. Dockerfile — дополнительные практики (из второго курса)

Разбор Dockerfile на примере Python-приложения дал несколько практик, которых не было в главе 9:

```dockerfile
FROM python:3.12-alpine        # alpine = минимальный образ
WORKDIR /app                   # рабочая директория (не корень!)
COPY . .                       # скопировать файлы проекта в /app
CMD ["python", "main.py"]      # что запустится в контейнере
```

- **`WORKDIR /app` — не класть файлы в корень `/`.** Заводите отдельную рабочую папку под приложение: в корне лежат системные каталоги, и файлы приложения там могут **перезаписать системные**. `WORKDIR` создаёт папку и делает её текущей для последующих `COPY`/`RUN`/`CMD`.
- **alpine-образы** (`python:3.12-alpine`, `node:20-alpine`) — самые **минимальные** по размеру. Плюс — лёгкие; минус — в них **нет части утилит**. Берите alpine, когда уверены, что всё нужное есть; иначе — обычный тег (`python:3.12`).
- **Имя файла и `-f`.** По умолчанию Docker ищет файл `Dockerfile`. Если он назван иначе (`Dockerfile.dev`, `Dockerfile.prod`) — укажите `docker build -f Dockerfile.dev -t myapp .`.
- **Dockerfile — в корне репозитория** рядом с приложением: он попадёт в git вместе с кодом и не мешает запуску приложения.
- **`.dockerignore`** — файл рядом с Dockerfile, исключает из контекста сборки лишнее (`node_modules`, `.git`, логи). Ускоряет сборку и уменьшает образ (аналог `.gitignore`).
- Напоминание: **каждая инструкция = слой**, слои кэшируются — редко меняющееся ставьте выше, часто меняющееся (копирование кода) ниже (см. главу 9).

## Д6. Dev-режим: hot reload без пересборки

Отдельный приём для **разработки** (второй курс показывает на Node.js): чтобы не пересобирать образ на каждое изменение кода, код **монтируют внутрь контейнера bind mount'ом**, а внутри запускают watcher (например, `nodemon`), который сам перезапускает приложение при правках:

```bash
docker run -d -p 3000:3000 \
  -v $(pwd):/app \        # код с хоста монтируется в контейнер
  -w /app \
  node:20-alpine \
  npx nodemon main.js     # следит за файлами и перезапускает
```

Изменили файл на хосте → nodemon внутри контейнера подхватил → приложение перезапустилось, **без `docker build`**. Это стандартный паттерн локальной разработки в Docker.

## Итог дополнения

Второй курс добавил к пособию: **клиент-серверную архитектуру** (client → daemon → host по REST API), **модель слоёв** (read-only слои образа + записываемый слой контейнера, переиспользование слоёв), **чёткое различие реестр vs репозиторий**, **публикацию образа** (`login → tag → push`) и **практики Dockerfile** (`WORKDIR /app`, alpine, `-f`, `.dockerignore`) плюс **dev hot-reload** через bind-mount кода. Всё остальное (команды, порты, тома, сети, compose, Portainer) в двух курсах совпадает и уже разобрано выше.
