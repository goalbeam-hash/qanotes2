# Глава 1. Основы Docker

## 1.1. Проблема классического сервера

Возьмём обычный сервер (или ваш ноутбук). Снизу вверх:

- **железо** (CPU, память, диск);
- **операционная система** (Linux/Windows);
- **программы**, которые вы ставите поверх ОС.

Проблема в **зависимостях**. Каждая программа использует библиотеки нужных версий. Пока приложения не пересекаются — всё хорошо. Но как только двум приложениям нужны **разные версии** одной и той же библиотеки — начинаются «танцы с бубном»: конфликт версий, «у меня на машине работает, а на сервере нет», хрупкая настройка окружения.

## 1.2. Идея Docker: изоляция в контейнере

Docker решает это через **контейнеры**. Поверх ОС ставится программа **Docker**, а каждое приложение упаковывается в свой **контейнер** — «капсулу», внутри которой лежит и само приложение, **и все нужные ему библиотеки и зависимости** именно тех версий, что ему нужны.

Ключевой эффект: приложение внутри контейнера **не обращается к библиотекам операционной системы** — у него всё своё. Поэтому:

- контейнеры **независимы** друг от друга (у каждого свои версии зависимостей — конфликтов нет);
- приложение работает **стабильно и одинаково** везде, где есть Docker;
- под каждую программу — свой контейнер, они не мешают друг другу.

```
Классический сервер            Сервер с Docker
──────────────────            ──────────────────
   [ Приложения ]              [конт.A][конт.B][конт.C]  ← у каждого свои
   [     ОС     ]              [        Docker        ]     библиотеки
   [   Железо   ]              [          ОС          ]
                               [        Железо        ]
```

## 1.3. Docker vs виртуальные машины (важное отличие)

Оба дают изоляцию, но по-разному:

|                   | Виртуальная машина                   | Docker-контейнер            |
| ----------------- | ------------------------------------ | --------------------------- |
| Что изолирует     | целую **гостевую ОС** со своим ядром | процесс + его зависимости   |
| Ядро ОС           | своё в каждой ВМ                     | **общее ядро хоста**        |
| Вес               | гигабайты, медленный старт           | мегабайты, старт за секунды |
| Накладные расходы | высокие (гипервизор)                 | минимальные                 |

ВМ виртуализирует **железо** и тащит полноценную ОС в каждой машине. Контейнер же **шарит ядро хоста** и упаковывает только приложение с зависимостями — поэтому он лёгкий и быстрый.

## 1.4. Почему Docker «работает только на Linux»

Docker опирается на возможности **ядра Linux** (namespaces, cgroups). Поэтому:

- на **Linux** контейнеры запускаются нативно поверх ядра хоста;
- на **Windows/macOS** Docker поднимает под капотом **лёгкую виртуальную Linux-машину**, и контейнеры работают уже в ней. Ставится это автоматически (Docker Desktop / WSL2) — вам ничего вручную делать не нужно, но «промежуточный Linux» там всегда есть.

Вывод: по сути Docker — это про Linux; на других ОС он живёт через тонкую Linux-прослойку.

**Мини-итог главы 1.** Docker упаковывает приложение вместе с зависимостями в изолированную капсулу-контейнер, что убирает конфликты версий и даёт «работает одинаково везде». В отличие от ВМ, контейнеры лёгкие, потому что делят ядро хоста.

# Глава 2. Установка Docker

## 2.1. Linux

На Linux Docker ставится нативно. Общая схема (Ubuntu/Debian) — через официальный репозиторий:

```bash
# быстрый способ (официальный скрипт)
curl -fsSL https://get.docker.com | sh

# проверка
docker --version
docker run hello-world     # тестовый контейнер: если вывелось приветствие — всё ок
```

**Зачем `hello-world`, а не просто `docker --version`.** `--version` показывает только, что установлен **клиент**. А `docker run hello-world` проверяет **всю цепочку целиком**: клиент → демон → скачивание образа из Docker Hub → создание и запуск контейнера. Если приветствие вывелось — работает всё, от сети до запуска контейнеров.

**Зачем группа docker.** По умолчанию обращаться к демону может только root, поэтому каждую команду пришлось бы писать через `sudo docker …` — неудобно. Добавление в группу `docker` снимает `sudo`:

```bash
sudo usermod -aG docker $USER   # затем выйти и зайти в сессию заново
```

> ⚠️ Нюанс безопасности: член группы `docker` фактически имеет права root на хосте (через демон можно смонтировать любой каталог). На личной машине это норм, на общем сервере — учитывайте.

## 2.2. Windows / macOS

Ставится **Docker Desktop** — приложение, которое само поднимает Linux-прослойку (на Windows — через **WSL2**, подсистему Linux). Скачивается с docker.com, ставится «далее-далее», после запуска в трее появляется кит. Проверка — та же (`docker run hello-world`).

**Зачем WSL2.** Контейнеры — это Linux-технология (см. главу 1). WSL2 даёт настоящее Linux-ядро внутри Windows, поверх которого и крутятся контейнеры. Поэтому Docker на Windows работает почти как на Linux, а не «эмулирует» его медленно.

**Частые проблемы установки (и что с ними делать):**

- **`docker: command not found`** после установки на Windows — не запущен Docker Desktop (демон стартует вместе с приложением; нет кита в трее — нет демона).
- **`Cannot connect to the Docker daemon`** — демон не запущен/не поднялся. На Linux: `sudo systemctl start docker`; на Windows/Mac — запустить Docker Desktop.
- **На Windows не стартует Docker Desktop** — обычно выключена аппаратная **виртуализация** (включается в BIOS/UEFI) или не установлен WSL2 (`wsl --install`).
- **`permission denied` при `docker ...` на Linux** — не добавлены в группу docker или не перезашли в сессию.

**Мини-итог главы 2.** Linux — нативно; Windows/macOS — Docker Desktop (Linux через WSL2). `docker run hello-world` проверяет всю цепочку. Группа `docker` убирает `sudo`. «Cannot connect to daemon» = не запущен демон.

# Глава 3. Образы и контейнеры

Два центральных понятия, которые нельзя путать.

- **Образ (image)** — неизменяемый «слепок»/шаблон: файловая система + приложение + зависимости + инструкция запуска. Как ISO-образ, из которого ставят систему. Образ **только для чтения**.
- **Контейнер (container)** — **запущенный экземпляр образа**. Из одного образа можно поднять сколько угодно контейнеров. Контейнер добавляет поверх образа тонкий **записываемый слой**.

Аналогия: образ — это класс, контейнер — объект этого класса.

**Зачем эта разница на практике** (не терминология ради терминологии):

- **Один образ → много контейнеров.** Собрали образ приложения один раз — подняли из него 5 одинаковых контейнеров под нагрузку. Не надо 5 раз настраивать окружение.
- **Обновление = новый образ + пересоздание контейнера.** Контейнеры не «правят на лету»: чтобы обновить приложение, собирают новую версию образа и **пересоздают** контейнер из неё. Отсюда важный вывод: **всё ценное (данные) должно жить вне контейнера** (тома, глава 7), иначе потеряется при пересоздании.
- **Откат — это просто запуск старого образа.** Новая версия сломалась — поднимаете контейнер из предыдущего образа/тега. Быстрый rollback без «чинить на проде».

## 3.1. Docker Hub и теги

Образы берутся из **реестра** — по умолчанию это **Docker Hub** (публичный каталог). Когда вы пишете `docker run nginx`, Docker:

1. ищет образ `nginx` локально;
2. если нет — **скачивает** (pull) его с Docker Hub;
3. создаёт из него контейнер и запускает.

**Тег** — версия образа, указывается через двоеточие: `nginx:1.27`, `ubuntu:22.04`, `mysql:5.7`. Если тег не указан — берётся **`latest`** (последняя стабильная).

```bash
docker run ubuntu          # = ubuntu:latest
docker run ubuntu:20.04    # конкретная версия
```

> Правило: в проде **всегда фиксируйте тег** (`ubuntu:22.04`), а не `latest` — иначе завтра образ обновится и поведение изменится.

**Зачем нужны теги (конкретно).** Тег — это версия, и от него зависит **воспроизводимость**. `latest` опасен тем, что это «движущаяся мишень»: сегодня за ним `nginx 1.27`, через месяц — `1.29`, и ваш стенд, что «вчера работал», сегодня падает без единой правки с вашей стороны. Фиксированный тег даёт: одинаковое поведение на всех машинах (dev/CI/прод), возможность **отката** к конкретной версии и понятную историю «что именно крутится в проде».

**Мини-итог главы 3.** Образ — шаблон (read-only), контейнер — его запущенный экземпляр. Образы тянутся из Docker Hub, версия задаётся тегом; без тега — `latest`.

# Глава 4. Основные команды

Здесь — рабочий минимум на каждый день. Разберём на образах `ubuntu` и `nginx`.

## 4.1. Запуск контейнера: `docker run`

Общая форма:

```
docker run [опции] ОБРАЗ[:тег] [команда] [аргументы]
```

Примеры:

```bash
docker run ubuntu:20.04 echo "hello"     # запустить, выполнить команду и выйти
docker run -it ubuntu:20.04 bash         # интерактивный терминал внутри контейнера
docker run -d nginx                      # запустить в фоне (detached)
```

**Ключевые опции `run`:**

| Опция | Что делает |
|---|---|
| `-d` (`--detach`) | запустить в **фоне**, вернуть управление терминалу |
| `-it` | **интерактивный** режим + терминал (`-i` держит STDIN, `-t` даёт TTY) — чтобы «зайти внутрь» |
| `--rm` | **удалить** контейнер автоматически после остановки (не копить мусор) |
| `--name ИМЯ` | дать контейнеру **имя** (иначе Docker придумает случайное) |
| `-p ХОСТ:КОНТ` | проброс порта (глава 5) |
| `-e ПЕРЕМ=знач` | переменная окружения (глава 6) |
| `-v ...` | монтирование данных (глава 7) |

Имя удобно тем, что дальше можно управлять контейнером по нему, а не по ID:

```bash
docker run -d --name web nginx
docker stop web
docker start web
```

## 4.2. Список контейнеров: `docker ps`

```bash
docker ps          # только РАБОТАЮЩИЕ контейнеры
docker ps -a       # ВСЕ контейнеры, включая остановленные
```

В выводе: `CONTAINER ID`, `IMAGE`, `COMMAND`, `STATUS`, `PORTS`, `NAMES`.

## 4.3. Логи: `docker logs`

```bash
docker logs web        # показать логи контейнера
docker logs -f web     # follow: живой поток логов (как tail -f)
```

Незаменимо, когда ищете ошибку или следите за процессом в реальном времени.

## 4.4. Зайти внутрь работающего контейнера: `docker exec`

```bash
docker exec -it web bash     # открыть shell внутри контейнера web
```

Важно: внутри минимальных образов (nginx и т.п.) **нет многих привычных команд** — контейнеры делают минимальными, только необходимое для работы приложения. Иногда вместо `bash` есть только `sh`.

> ⚠️ Файлы, созданные внутри контейнера «руками», **теряются при его удалении** — контейнер эфемерен. Чтобы данные жили дольше — тома (глава 7).

## 4.5. Мониторинг ресурсов: `docker stats`

```bash
docker stats            # живая таблица: CPU %, память, сеть, диск по контейнерам
docker stats web        # по одному контейнеру
```

## 4.6. Полная информация: `docker inspect`

```bash
docker inspect web      # весь JSON о контейнере: порты, тома, сеть, как собран
```

Полезно, когда пришли на незнакомый сервер и надо понять, как настроен контейнер.

## 4.7. Остановка, запуск, удаление

```bash
docker stop web         # мягко остановить
docker start web        # запустить снова
docker rm web           # удалить контейнер (сначала остановить, либо docker rm -f web)
docker images           # список локальных образов
docker rmi nginx        # удалить образ
```

## 4.8. Массовая уборка: `docker system prune`

```bash
docker system prune              # удалить всё неиспользуемое (остановленные конт., висячие образы, сети)
docker system prune --volumes    # плюс неиспользуемые тома (данные!) — с осторожностью
```

> ⚠️ `--volumes` удаляет данные томов безвозвратно. Перед этим убедитесь, что там нет нужного.

**Мини-итог главы 4.** `run` (+`-d/-it/--rm/--name`) запускает; `ps/ps -a` показывает; `logs -f` следит; `exec -it` заходит внутрь; `stats`/`inspect` диагностируют; `stop/start/rm/rmi` управляют; `system prune` убирает мусор.

**Практика.** Запустите `nginx` в фоне с именем `web`, посмотрите `docker ps`, гляньте `docker logs web`, зайдите внутрь `docker exec -it web sh`, выйдите, остановите и удалите.

# Глава 5. Проброс портов (port mapping)

## 5.1. Зачем

Docker-контейнер по умолчанию **изолирован по сети** — порт, открытый внутри контейнера, снаружи недоступен. Если внутри контейнера работает веб-сервер nginx на порту **80**, извне к нему **не подключиться напрямую**: порт открыт только внутри контейнера.

Чтобы дать доступ снаружи, порт контейнера нужно **пробросить** на порт хоста опцией `-p`:

```
-p ПОРТ_ХОСТА:ПОРТ_КОНТЕЙНЕРА
```

## 5.2. Примеры

```bash
docker run -d --name web -p 80:80 nginx
```

Здесь `80:80` означает: запросы на порт **80 сервера** пробрасываются в порт **80 контейнера**. Теперь по IP/домену сервера на порту 80 открывается nginx.

Если на одном сервере нужно несколько nginx (все слушают 80 внутри), снаружи их разводят по **разным портам хоста**:

```bash
docker run -d --name web1 -p 8080:80 nginx
docker run -d --name web2 -p 8081:80 nginx
```

Пользователь заходит на `сервер:8080` → попадает в контейнер web1, на `сервер:8081` → в web2. Внутри оба слушают 80 — конфликта нет, потому что различаются **порты хоста**.

```
     хост:8080 ──▶ контейнер web1 :80 (nginx)
     хост:8081 ──▶ контейнер web2 :80 (nginx)
```

**Зачем изоляция по умолчанию (а не «всё открыто»).** Это безопасность: контейнер может слушать десяток внутренних портов (БД, админка, метрики), но наружу вы **осознанно** выставляете только то, что нужно, — одним `-p`. Ничего не пробросили — снаружи ничего не видно. То есть по умолчанию «закрыто», открываете точечно.

**Полезные варианты `-p`:**

- `-p 8080:80` — открыть на **всех** интерфейсах хоста (доступно из сети).
- `-p 127.0.0.1:8080:80` — открыть **только на localhost**: контейнер доступен с самого сервера, но не из внешней сети (частый приём для БД и приватных сервисов).
- `-P` (заглавная) — пробросить **все** порты из `EXPOSE` образа на случайные порты хоста (быстро для тестов).

**Частая ошибка — `port is already allocated`.** Значит порт **хоста** уже занят другим контейнером/процессом. Лечится: взять другой порт хоста (`-p 8082:80`) или освободить занятый. Помните: **порт хоста уникален**, порт контейнера — нет.

**Мини-итог главы 5.** Контейнер сетево изолирован — наружу видно только то, что пробросили `-p хост:контейнер`. Порт контейнера может повторяться, порт хоста — уникален. `127.0.0.1:порт` открывает только локально; `port already allocated` = порт хоста занят.

**Практика.** Поднимите два nginx на `8080:80` и `8081:80`, откройте оба в браузере. Затем поднимите третий на занятом `8080` и посмотрите на ошибку.

# Глава 6. Переменные окружения

## 6.1. Что это и зачем

**Переменная окружения (environment variable)** — пара «имя=значение», которую видит процесс внутри контейнера. Через них приложения **настраивают**: пароли, режимы, параметры подключения к БД. Задаются опцией `-e` при запуске:

```bash
docker run -e MY_VAR=1234 ubuntu env     # env выведет все переменные, включая MY_VAR
```

Внутри контейнера переменные можно посмотреть командой `env` или `printenv`.

**Зачем это, а не «зашить настройки в образ».** Ключевая идея — **один образ, много сред**. Вы собираете образ приложения **один раз**, а под dev/stage/prod передаёте **разные переменные** (адрес БД, режим debug, ключи) при запуске — без пересборки. Это принцип 12-factor app «конфиг — в окружении, а не в коде». Плюс: **секреты (пароли, токены) не хардкодятся в образ** — иначе они утекут вместе с образом в реестр; их подкидывают переменными при запуске.

**Удобно: файл с переменными вместо длинной строки `-e`.** Когда переменных много, их выносят в файл:

```bash
# app.env
MYSQL_ROOT_PASSWORD=secret123
MYSQL_DATABASE=appdb

docker run -d --name db --env-file app.env mysql:5.7
```

## 6.2. Практический пример — MySQL

Многие официальные образы **конфигурируются именно переменными**. Классика — `mysql`: без обязательной переменной с паролем контейнер просто не стартует.

```bash
docker run -d --name db \
  -e MYSQL_ROOT_PASSWORD=secret123 \
  mysql:5.7
```

- `MYSQL_ROOT_PASSWORD` — задаёт пароль root (обязательная);
- у образа есть и другие переменные (`MYSQL_DATABASE`, `MYSQL_USER`, `MYSQL_PASSWORD`), их список — в документации образа на Docker Hub.

> Идея: одна и та же программа настраивается под задачу **без пересборки образа** — просто разными переменными при запуске.

**Мини-итог главы 6.** `-e ИМЯ=значение` передаёт настройки внутрь контейнера. Официальные образы (mysql, postgres…) конфигурируются переменными; их список смотрите в описании образа.

**Практика.** Запустите `mysql:5.7` с `MYSQL_ROOT_PASSWORD`, зайдите `docker exec -it db bash` и проверьте `env`.

# Глава 7. Постоянные данные: volumes

## 7.1. Проблема эфемерности

Контейнер **эфемерен**: его записываемый слой живёт, пока жив контейнер. Удалили контейнер (или пересоздали) — **все данные внутри пропали**. Для базы данных это катастрофа: перезапустили MySQL — потеряли все таблицы.

Решение — **тома (volumes)**: хранить данные **вне** контейнера, чтобы они переживали его перезапуск и удаление.

## 7.2. Три способа монтирования

**1. Bind mount — привязка папки хоста.** Конкретная директория хоста монтируется внутрь контейнера:

```bash
docker run -d --name db \
  -e MYSQL_ROOT_PASSWORD=secret123 \
  -v /opt/mysql/data:/var/lib/mysql \
  mysql:5.7
```

`/opt/mysql/data` (на хосте) ↔ `/var/lib/mysql` (внутри, где MySQL хранит данные). Теперь данные лежат на хосте и не исчезнут с контейнером. Удобно, когда хотите видеть файлы прямо на сервере.

**2. Именованный том (named volume) — управляется Docker.** Docker сам хранит данные в своём каталоге, вы обращаетесь по имени:

```bash
docker volume create mysql_data
docker run -d --name db \
  -e MYSQL_ROOT_PASSWORD=secret123 \
  -v mysql_data:/var/lib/mysql \
  mysql:5.7
```

**3. Анонимный том.** Указываете только путь в контейнере — Docker создаёт том с автоимененем:

```bash
docker run -d -v /var/lib/mysql mysql:5.7
```

## 7.3. Управление томами

```bash
docker volume ls                 # список томов
docker volume create mysql_data  # создать
docker volume inspect mysql_data # где физически лежит, кто использует
docker volume rm mysql_data      # удалить (том должен быть не занят)
docker volume prune              # удалить неиспользуемые тома
```

## 7.4. Что выбрать

- **Именованный том** — рекомендованный дефолт для БД и «данных приложения»: переносимо, Docker управляет.
- **Bind mount** — когда нужен прямой доступ к файлам с хоста (конфиги, разработка, отдача статики).
- **Анонимный** — на быстрые эксперименты.

**Мини-итог главы 7.** Данные внутри контейнера эфемерны; тома выносят их наружу. Три вида: bind mount (папка хоста), named volume (управляется Docker), анонимный. Для БД — именованный том.

**Практика.** Запустите MySQL с named volume, создайте базу, удалите контейнер, поднимите заново с тем же томом — данные на месте.

# Глава 8. Сети в Docker

## 8.1. Зачем свои сети

Контейнерам часто нужно **общаться между собой** (приложение ↔ база). Docker даёт для этого **сети**. Главный бонус пользовательской сети — контейнеры в ней **находят друг друга по имени** (встроенный DNS), а не по меняющимся IP.

## 8.2. Три типа сетей

| Тип | Что это |
|---|---|
| **bridge** | тип по умолчанию: изолированная внутренняя сеть-«мостик», контейнеры общаются между собой, наружу — через проброс портов |
| **host** | контейнер использует **сеть хоста напрямую** (без изоляции портов; `-p` не нужен и не работает) |
| **none** | без сети вообще (полная сетевая изоляция) |

По умолчанию новый контейнер попадает в стандартную сеть **bridge**.

## 8.3. Создание своей сети и связь контейнеров

```bash
docker network create app-net           # создать сеть (по умолчанию тип bridge)
docker network ls                        # список сетей
docker network inspect app-net           # детали, кто подключён

# подключаем контейнеры к одной сети
docker run -d --name db  --network app-net -e MYSQL_ROOT_PASSWORD=secret mysql:5.7
docker run -d --name app --network app-net -p 8080:80 my-app
```

Теперь контейнер `app` обращается к базе просто по имени **`db`** (например, хост БД = `db`, порт 3306) — Docker сам резолвит имя в нужный IP. Это ключевая причина заводить свою сеть, а не полагаться на IP.

```bash
docker network connect app-net web       # подключить существующий контейнер к сети
docker network disconnect app-net web     # отключить
```

**Мини-итог главы 8.** Сети связывают контейнеры; в пользовательской bridge-сети они видят друг друга **по имени**. Типы: bridge (дефолт, изолированный мостик), host (сеть хоста), none (без сети).

**Практика.** Создайте сеть, поднимите в ней `mysql` (`--name db`) и `adminer`, подключитесь из adminer к хосту `db`.

# Глава 9. Свой образ: Dockerfile

## 9.1. Что такое Dockerfile

**Dockerfile** — текстовый «рецепт», по которому Docker **собирает образ**. В нём по шагам описано: от какого базового образа отталкиваемся, какие пакеты ставим, какие файлы копируем, что запускается при старте. Из этого рецепта командой `docker build` получается образ, из образа — контейнеры.

## 9.2. Основные инструкции

| Инструкция | Назначение |
|---|---|
| `FROM` | **базовый образ**, с которого начинаем (`FROM ubuntu:22.04`). Обязательна, идёт первой |
| `LABEL` | метаданные образа (автор, описание) — необязательно |
| `RUN` | выполнить команду **на этапе сборки** (поставить пакеты, скомпилировать) |
| `WORKDIR` | задать **рабочую директорию** внутри образа |
| `COPY` | скопировать файлы **с хоста в образ** (`COPY index.html /usr/share/nginx/html/`) |
| `ENV` | переменные окружения **по умолчанию** (можно переопределить при `run -e`) |
| `EXPOSE` | **информационно** объявить порт (сам порт не публикует — публикует `-p`) |
| `CMD` | команда по умолчанию при **запуске** контейнера (легко переопределить) |
| `ENTRYPOINT` | основная команда запуска (жёстче CMD; аргументы дописываются к ней) |

Важно про запуск: контейнер живёт, пока в нём работает основной процесс. Если процесс завершился — контейнер останавливается. Поэтому в конце Dockerfile описывают, что запускать (`CMD`/`ENTRYPOINT`).

## 9.3. Пример 1 — простейший образ

`Dockerfile`:

```dockerfile
FROM ubuntu:22.04
CMD echo "Hello, my first Docker image"
```

Сборка и запуск:

```bash
docker build -t myfirst .      # -t = имя (tag) образа; . = где лежит Dockerfile
docker images                  # увидим ubuntu (базовый) и myfirst (наш)
docker run --rm myfirst        # выведет строку и выйдет
```

При сборке видно шаги: `Step 1` (FROM — тянется ubuntu), `Step 2` (CMD) и т.д. Каждый шаг — **слой** образа.

## 9.4. Пример 2 — свой веб-сервер на nginx со своей страницей

`index.html`:

```html
<h1>Моя страница в контейнере</h1>
```

`Dockerfile`:

```dockerfile
FROM nginx:latest
COPY index.html /usr/share/nginx/html/index.html
EXPOSE 80
# CMD не нужен: базовый образ nginx уже запускает сервер
```

Сборка и запуск:

```bash
docker build -t my-site .
docker run -d --name site -p 8080:80 my-site
# открываем http://localhost:8080 — видим свою страницу
```

## 9.5. CMD vs ENTRYPOINT (коротко)

- **`CMD`** — «команда по умолчанию»; если при `docker run` передать свою команду, она **заменит** CMD.
- **`ENTRYPOINT`** — «неизменяемое начало» команды; аргументы из `docker run` **дописываются** к нему.
- Частый паттерн: `ENTRYPOINT` = сама программа, `CMD` = аргументы по умолчанию.

## 9.6. Про слои и кэш (важно для скорости)

Каждая инструкция — **слой**, слои **кэшируются**. Docker пересобирает слой только если он или что-то выше изменилось. Поэтому редко меняющееся (установку пакетов) ставят **выше**, а часто меняющееся (копирование кода) — **ниже**, чтобы не пересобирать тяжёлые слои каждый раз.

**Мини-итог главы 9.** Dockerfile — рецепт образа: `FROM` → `RUN/COPY/WORKDIR/ENV/EXPOSE` → `CMD/ENTRYPOINT`. Сборка — `docker build -t имя .`. Инструкции дают слои, слои кэшируются.

**Практика.** Соберите свой nginx-образ со своей `index.html`, запустите на `8080:80`, откройте в браузере.

# Глава 10. Docker Compose

## 10.1. Зачем

Запускать вручную несколько связанных контейнеров (`app` + `db` + сеть + тома + порты) длинными `docker run` — утомительно и легко ошибиться. **Docker Compose** описывает **весь стек в одном YAML-файле** (`docker-compose.yml`) и поднимает его одной командой.

## 10.2. Пример `docker-compose.yml`

```yaml
services:
  web:
    build: .                 # собрать из Dockerfile в текущей папке
    ports:
      - "8080:80"
    networks:
      - app-net
    depends_on:
      - db

  db:
    image: mysql:5.7
    environment:
      MYSQL_ROOT_PASSWORD: secret123
      MYSQL_DATABASE: appdb
    volumes:
      - db_data:/var/lib/mysql
    networks:
      - app-net

networks:
  app-net:
    driver: bridge

volumes:
  db_data:
```

Что здесь есть: два сервиса (`web`, `db`), их порты, переменные, том для данных БД, общая **bridge-сеть**, по которой `web` обращается к базе по имени `db`.

## 10.3. Основные команды

```bash
docker compose up -d        # собрать (если надо) и поднять весь стек в фоне
docker compose ps           # что запущено в рамках compose
docker compose logs -f      # логи всех сервисов
docker compose stop         # остановить сервисы (контейнеры остаются)
docker compose down         # остановить и удалить контейнеры/сеть
docker compose down -v      # то же + удалить тома (данные!)
```

> Примечание по версиям: раньше была отдельная утилита `docker-compose` (с дефисом), сейчас это встроенная подкоманда `docker compose` (без дефиса). Синтаксис YAML тот же.

**Мини-итог главы 10.** Compose описывает многоконтейнерный стек в `docker-compose.yml` (сервисы, порты, переменные, тома, сети) и поднимает его одной командой `docker compose up -d`. Внутри одной сети сервисы видят друг друга по имени.

**Практика.** Опишите в compose связку `web` (свой nginx-образ) + `db` (mysql) в одной сети, поднимите `docker compose up -d`, проверьте `docker compose ps`, погасите `docker compose down`.

# Глава 11. Portainer

**Portainer** — **графическая веб-оболочка** для управления Docker: контейнеры, образы, тома, сети, логи, консоль — всё мышкой в браузере, без запоминания команд.

**Зачем он нужен (когда полезен).**

- **Наглядность.** Видишь всё разом: что запущено, сколько ест ресурсов, какие тома/сети, — вместо десятка `docker ps/stats/inspect`.
- **Порог входа.** Удобно для тех, кто не хочет держать команды в голове (джуны, не-девопсы, коллеги-аналитики) — старт/стоп/логи/консоль кнопками.
- **Быстрая диагностика.** Логи и консоль контейнера в один клик — удобно на удалённом сервере.

**Когда лучше остаться на CLI.** Для **автоматизации** (CI/CD, скрипты, воспроизводимые деплои) GUI не годится — там нужны команды и `docker-compose.yml` в git. Portainer — это «пульт для наблюдения и ручных действий», а не замена коду. Обычно его держат **в дополнение** к CLI, а не вместо.

Portainer сам запускается как контейнер и хранит своё состояние в томе:

```bash
docker volume create portainer_data
docker run -d \
  --name portainer \
  -p 9443:9443 \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v portainer_data:/data \
  portainer/portainer-ce:latest
```

- `-p 9443:9443` — веб-интерфейс (открывается в браузере, при первом входе создаёте админа);
- `-v /var/run/docker.sock:/var/run/docker.sock` — **ключевая строка**: даёт Portainer доступ к Docker-демону хоста, чтобы он мог управлять контейнерами;
- `-v portainer_data:/data` — том под его настройки.

После старта заходим на `https://localhost:9443`, задаём пароль администратора и видим дашборд: списки контейнеров/образов/томов/сетей, кнопки старт/стоп/логи/консоль. Можно даже разворачивать целые стеки — Portainer умеет принимать `docker-compose.yml` («Stacks»).

**Зачем `-v /var/run/docker.sock:/var/run/docker.sock` (и почему это важно понимать).** Это тот самый сокет, через который клиент общается с демоном (см. Дополнение Д1). Прокинув его внутрь Portainer, вы даёте контейнеру **управлять всем Docker хоста** — иначе GUI просто нечем было бы рулить.

> ⚠️ Обратная сторона: доступ к `docker.sock` = фактически права **root на хосте**. Поэтому Portainer нельзя оставлять открытым в интернет: держите его за VPN/файрволом, с сильным паролем админа, а на проде — с ограниченным доступом.

> ⚠️ Монтирование `docker.sock` = фактически полный контроль над Docker хоста. На проде доступ к Portainer надо закрывать (аутентификация, сеть).

**Мини-итог главы 11.** Portainer — GUI для Docker: удобно смотреть и управлять контейнерами через браузер. Запускается контейнером с доступом к `docker.sock`.

# Глава 12. Что такое nginx (веб-сервер)

nginx встречается в пособии постоянно — как пример контейнера (главы 4–5), как база для своего образа (глава 9.4) и как reverse proxy (Дополнение 5). Разберём отдельно, что это и зачем. Но сначала — что такое **веб-сервер** вообще, потому что nginx это частный случай.

## 12.0. Что такое веб-сервер (определение + SMART + инженерная схема + мясо)

### Короткое определение (скелет)

**Веб-сервер** — это программа (и/или машина, где она работает), которая **слушает сетевой порт, принимает HTTP/HTTPS-запросы от клиентов (браузеров, приложений) и возвращает им ответы**: готовые файлы (HTML, картинки) или результат работы приложения. По сути — «официант» между пользователем и содержимым сайта: принял заказ (запрос) → принёс ответ.

### SMART-определение (как назвать точно)

- **S (Specific):** серверная программа, реализующая протокол **HTTP/HTTPS**: слушает порт (80/443), парсит запрос (метод, URL, заголовки), формирует ответ (статус-код, заголовки, тело).
- **M (Measurable):** измеряется в **RPS** (запросов в секунду), числе одновременных соединений, латентности (p95/p99); отдаёт понятные **статус-коды** (200, 404, 502…).
- **A (Achievable):** реализуемо готовыми серверами — **nginx, Apache, Caddy**, встроенные серверы приложений (gunicorn, uvicorn, Node http).
- **R (Relevant):** это **точка входа** любого веб-приложения — без веб-сервера сайт/API недоступны из сети.
- **T (Time-bound):** запрос обрабатывается за **миллисекунды**; веб-сервер должен держать тысячи соединений одновременно.

### Инженерная схема

- **Проблема:** у пользователя есть браузер, а у нас — файлы сайта и код приложения; их надо как-то **отдать по сети** по стандартному протоколу, безопасно и под нагрузкой.
- **Если проигнорировать (нет веб-сервера):** приложение недоступно из интернета; каждый разработчик изобретал бы свой способ раздачи по сети; нет единого протокола, безопасности, обработки тысяч клиентов.
- **Куда дальше / трудности:** веб-сервер решает это через HTTP: слушает порт, маршрутизирует по URL, отдаёт статику сам, динамику **проксирует** приложению; сверху — TLS, кэш, сжатие, лимиты, логи. Трудности — держать высокую конкуренцию (много соединений), безопасность, TLS.
- **Что даёт:** стандартную, безопасную, масштабируемую **точку входа** для сайта/API — одну «дверь», за которой прячется вся логика.

### Мясо на скелет (как объяснить подробно / на собесе)

> «Веб-сервер — это программа, которая говорит по протоколу HTTP. Она **слушает порт** — обычно 80 для HTTP и 443 для HTTPS — и ждёт запросы. Когда браузер открывает сайт, он шлёт HTTP-запрос: метод (GET/POST), URL, заголовки, иногда тело. Веб-сервер этот запрос **разбирает** и решает, что вернуть.
>
> Дальше есть развилка. Если запрошен **статический ресурс** — HTML-страница, CSS, картинка, — веб-сервер просто **берёт файл с диска и отдаёт** его в ответе. Это быстро и не требует никакой логики. А если нужен **динамический** ответ — например, персональная страница, где данные зависят от пользователя и берутся из базы, — тут работает **приложение** (на Python, Node, Java), и веб-сервер либо сам запускает его, либо **проксирует** запрос на отдельный сервер приложения и возвращает клиенту его результат.
>
> В ответе веб-сервер всегда отдаёт **статус-код** — 200 “ок”, 404 “не найдено”, 500/502 “ошибка”, — заголовки и тело. По этим кодам и клиент, и мы в логах понимаем, что произошло.
>
> Почему это отдельный компонент, а не часть приложения. Веб-сервер берёт на себя всё “сетевое и инфраструктурное”, что не относится к бизнес-логике: **терминацию HTTPS** (сертификаты), **отдачу статики** без нагрузки на приложение, **балансировку** между несколькими копиями приложения, **кэширование**, **сжатие**, **ограничение частоты запросов**, **логи доступа**. Приложение занимается своей логикой, а веб-сервер — тем, чтобы это надёжно и быстро доехало до пользователя.
>
> Ключевая метрика веб-сервера — сколько **одновременных соединений** и **запросов в секунду** он держит с приемлемой задержкой. Отсюда и разные архитектуры: старые серверы делали процесс или поток на каждого клиента и захлёбывались под тысячами соединений, а современные, как **nginx**, используют событийную модель — один процесс обслуживает тысячи соединений. Поэтому nginx часто ставят **впереди** как “входную дверь”, а за ним прячут само приложение.»

**Связь с остальной главой:** nginx — это как раз **веб-сервер**, который умеет обе роли: и отдавать статику сам, и работать reverse proxy перед приложением. Ниже — конкретно про него.

## 12.1. Что это

**nginx** (произносится «энджин-икс») — это **веб-сервер** и одновременно **reverse proxy / балансировщик нагрузки**. Его задача — принимать HTTP/HTTPS-запросы от клиентов (браузеров) и либо **сам отдавать** ответ (файлы сайта), либо **передавать** запрос вглубь — на приложение или другой сервер.

Ключевая особенность — **событийная (асинхронная) архитектура**: один рабочий процесс держит **тысячи одновременных соединений**, не создавая поток на каждого клиента. Поэтому nginx лёгкий, быстрый и хорошо переносит высокую нагрузку — за это его и любят.

## 12.2. Зачем он нужен (роли)

Одна программа закрывает сразу несколько задач:

- **Статический веб-сервер.** Отдаёт файлы сайта напрямую — HTML, CSS, JS, картинки. Быстро и без участия приложения. (Так мы использовали его в главе 9.4 — положили свою `index.html`.)
- **Reverse proxy.** Стоит **перед** приложением (Flask/Django на gunicorn, Node и т.п.) и **проксирует** на него динамические запросы (`proxy_pass`). Приложение при этом наружу не торчит. (Дополнение 5.)
- **Балансировщик нагрузки.** Если приложение поднято в нескольких репликах — nginx **распределяет** запросы между ними (`upstream`). Это основа горизонтального масштабирования.
- **TLS/SSL-терминация.** HTTPS-сертификаты вешают на nginx: он расшифровывает трафик и отдаёт приложению уже обычный HTTP. Приложению не нужно возиться с сертификатами.
- **Кэширование, сжатие, лимиты.** Кэширует ответы, жмёт gzip/brotli, ограничивает частоту запросов (rate limiting), делает редиректы (http→https, www→без www).

**Зачем это в связке с Docker.** Типичная схема прод-приложения в контейнерах: снаружи — **контейнер nginx** (единственный, кто виден в интернет), а за ним во внутренней docker-сети — контейнеры приложения и БД. nginx — «входная дверь» и щит: терминирует HTTPS, отдаёт статику, балансирует, а бэкенд закрыт от прямого доступа.

## 12.3. Reverse proxy vs forward proxy (частый вопрос)

- **Forward proxy** («прямой») работает **на стороне клиента**: скрывает клиента от сервера (клиент ходит в интернет через прокси). Пример — корпоративный прокси/VPN.
- **Reverse proxy** («обратный») работает **на стороне сервера**: скрывает **серверы** от клиента. Клиент думает, что общается с одним сервером (nginx), а тот распределяет запросы по бэкендам. Именно в этой роли nginx стоит перед приложением.

## 12.4. Как устроен конфиг

Конфиг nginx — это вложенные **блоки директив**: `http → server → location`.

```nginx
server {
    listen 80;                     # на каком порту слушать
    server_name example.com;       # для какого домена

    location /static/ {            # маршрут для статики
        root /var/www;             # откуда брать файлы
    }
    location / {                   # всё остальное
        proxy_pass http://backend; # проксируем на бэкенд (reverse proxy)
    }
}
```

- **`server`** — виртуальный хост (один сайт/домен). На одном nginx может быть много `server`-блоков.
- **`location`** — правило для пути URL: что отдавать/куда проксировать.
- **`listen` / `server_name`** — порт и домен; **`root` / `index`** — где файлы статики; **`proxy_pass` / `upstream`** — проксирование и балансировка.

Балансировка (несколько реплик бэкенда):

```nginx
upstream backend {
    server app1:8000;
    server app2:8000;   # nginx раскидывает запросы между ними
}
```

## 12.5. nginx в Docker

- Официальный образ — **`nginx`** (обычно `nginx:alpine` для минимального размера).
- Порты: **80** (HTTP) и **443** (HTTPS).
- Дефолтные пути внутри контейнера: статика — **`/usr/share/nginx/html/`**, конфиги — **`/etc/nginx/conf.d/`**.
- Свою статику и конфиг подкладывают **bind mount'ом** (правки без пересборки) или **`COPY`** в свой образ:

```bash
docker run -d --name web -p 80:80 \
  -v ./site:/usr/share/nginx/html:ro \
  -v ./default.conf:/etc/nginx/conf.d/default.conf:ro \
  nginx:alpine
```

Полезные команды внутри контейнера: **`nginx -t`** — проверить конфиг на ошибки перед перезапуском; **`nginx -s reload`** — применить конфиг без остановки.

## 12.6. nginx vs Apache (кратко, для собеса)

Оба — веб-серверы. Историческое отличие: **Apache** по классике создавал **процесс/поток на каждое соединение** (тяжелее под большим числом клиентов), **nginx** — **событийная модель** (один процесс, тысячи соединений). Поэтому nginx лучше держит высокую конкуренцию и часто ставится **впереди** как reverse proxy/балансировщик, даже если само приложение на другом сервере.

**Мини-итог главы 12.** nginx — быстрый веб-сервер и reverse proxy на событийной архитектуре. Роли: отдавать статику, проксировать на бэкенд (`proxy_pass`), балансировать реплики (`upstream`), терминировать HTTPS, кэшировать. В Docker это «входная дверь»: единственный контейнер, видимый снаружи, за которым спрятаны приложение и БД. Конфиг — блоки `server`/`location`; проверка — `nginx -t`.

# Глоссарий

- **Образ (image)** — неизменяемый шаблон приложения с зависимостями; из него создаются контейнеры.
- **Контейнер (container)** — запущенный экземпляр образа с тонким записываемым слоем.
- **Docker Hub** — публичный реестр образов (откуда идёт `pull` по умолчанию).
- **Тег (tag)** — версия образа (`ubuntu:22.04`); по умолчанию `latest`.
- **Dockerfile** — рецепт сборки образа (`FROM/RUN/COPY/CMD`…).
- **build** — сборка образа из Dockerfile.
- **Проброс портов (`-p`)** — публикация порта контейнера на порт хоста.
- **Переменная окружения (`-e`)** — настройка приложения внутри контейнера.
- **Том (volume)** — хранилище данных вне контейнера (переживает пересоздание). Виды: bind mount, named, анонимный.
- **Сеть (network)** — связь контейнеров; в пользовательской bridge-сети — по имени. Типы: bridge/host/none.
- **CMD / ENTRYPOINT** — что запускается при старте контейнера.
- **Docker Compose** — описание многоконтейнерного стека в YAML + запуск одной командой.
- **Portainer** — веб-GUI для управления Docker.
- **detached (`-d`)** — запуск в фоне; **interactive (`-it`)** — интерактивный терминал внутри контейнера.

# Дополнение. Что нового во втором курсе (Docker для начинающих, Богдан)

Ниже — материал из второго видео, которого **не было** в основной части пособия. Это углубление, а не повтор: архитектура Docker, слои образа и записываемый слой, реестр vs репозиторий, публикация своего образа и дополнительные практики Dockerfile.

## Д1. Архитектура Docker: клиент, демон, хост

Раньше мы говорили «Docker что-то делает». На самом деле Docker — это **клиент-серверная система** из трёх частей:

- **Docker Client (клиент)** — то, что вы вызываете в терминале командой `docker`. Сам он ничего не создаёт — только **отправляет запросы**.
- **Docker Daemon (демон / служба / сервер, `dockerd`)** — служба, которая **делает всю работу**: скачивает образы, создаёт и запускает контейнеры, управляет сетями и томами, обрабатывает запросы клиентов.
- **Docker Host (хост)** — компьютер, на котором запущен демон.

Клиент общается с демоном по **REST API** (локально — обычно через Unix-сокет `/var/run/docker.sock`). Демон может быть **на той же машине** (обычный случай) или **удалённым** — тогда одним клиентом можно управлять Docker на другом сервере.

```
[ docker CLI ]  ──REST API──▶  [ dockerd (демон) ]  ──▶  контейнеры / образы / сети / тома
   (клиент)      /var/run/docker.sock     (сервер)         ▲
                                                           │ pull / push
                                                    [ Registry: Docker Hub ]
```

> Практический вывод: когда вы монтируете `-v /var/run/docker.sock:/var/run/docker.sock` (как в главе про Portainer) — вы даёте контейнеру доступ **к тому самому API демона**, то есть полный контроль над Docker.

## Д2. Слои образа и записываемый слой контейнера

Это ключевая модель, объясняющая, почему образы лёгкие, а контейнеры эфемерны.

**Образ состоит из слоёв (layers).** Слой — это **набор файлов** (кусочек файловой системы). У образа есть **базовый слой** и добавленные поверх слои: слой 1, слой 2, слой 3… **Каждая инструкция Dockerfile создаёт новый слой.** Все слои образа — **только для чтения (read-only)**.

**Слои переиспользуются между образами.** Если два образа основаны на одном базовом слое (например, оба на `node`), этот слой **хранится на диске один раз** и шарится. Отсюда:

- при `docker pull` скачиваются **только недостающие** слои (архивами); уже имеющиеся локально не качаются повторно — быстрее и меньше трафика;
- одинаковые слои не дублируются на диске — экономия места.

**Контейнер = образ (read-only слои) + тонкий верхний ЗАПИСЫВАЕМЫЙ слой.** Всё, что процесс меняет во время работы, пишется в этот верхний слой по принципу **copy-on-write**. Из одного образа можно поднять много контейнеров — у каждого свой отдельный записываемый слой, база общая.

```
контейнер:  [■ записываемый слой (свой у каждого контейнера)]
образ:      [ слой 3 ] ┐
            [ слой 2 ] ├─ read-only, общие/переиспользуемые
            [ базовый ]┘
```

> Отсюда прямо следует **эфемерность из главы 7**: удалили контейнер → пропал его записываемый слой со всеми изменениями. Поэтому данные выносят в тома.

## Д3. Реестр (registry) vs репозиторий (repository)

Во втором курсе чётко разведены два понятия, которые часто путают:

- **Registry (реестр)** — хранилище **репозиториев**. Бывает публичный (**Docker Hub** — самый большой) и приватный/self-hosted (GitLab Container Registry, Harbor, AWS ECR и т.п.).
- **Repository (репозиторий)** — набор **версий одного и того же образа**, различающихся **тегами**. Аналогия с git: как git-репозиторий хранит версии кода, docker-репозиторий хранит версии образа. Пример: репозиторий `nginx` с тегами `latest`, `1.27`, `1.27-alpine`.

Полное имя образа: **`[реестр/]репозиторий:тег`**, например `docker.io/library/nginx:1.27`. Когда пишете просто `nginx:1.27`, подразумевается Docker Hub. Приватные репозитории — для закрытых образов компании.

## Д4. Публикация своего образа на Docker Hub

Свой собранный образ можно **выложить**, чтобы его тянули другие (или ваши другие машины):

```bash
docker login                                   # войти в аккаунт Docker Hub
docker tag my-site username/my-site:1.0        # дать имя вида репозиторий:тег
docker push username/my-site:1.0               # загрузить в реестр

# на другой машине — просто скачать и запустить:
docker pull username/my-site:1.0
docker run -d -p 8080:80 username/my-site:1.0
```

- `docker tag` не копирует образ, а **добавляет ему ещё одно имя** (нужного формата `username/repo:tag`).
- `docker push` заливает **послойно**; уже существующие в реестре слои не загружаются повторно.

## Д5. Dockerfile — дополнительные практики (из второго курса)

Разбор Dockerfile на примере Python-приложения дал несколько практик, которых не было в главе 9:

```dockerfile
FROM python:3.12-alpine        # alpine = минимальный образ
WORKDIR /app                   # рабочая директория (не корень!)
COPY . .                       # скопировать файлы проекта в /app
CMD ["python", "main.py"]      # что запустится в контейнере
```

- **`WORKDIR /app` — не класть файлы в корень `/`.** Заводите отдельную рабочую папку под приложение: в корне лежат системные каталоги, и файлы приложения там могут **перезаписать системные**. `WORKDIR` создаёт папку и делает её текущей для последующих `COPY`/`RUN`/`CMD`.
- **alpine-образы** (`python:3.12-alpine`, `node:20-alpine`) — самые **минимальные** по размеру. Плюс — лёгкие; минус — в них **нет части утилит**. Берите alpine, когда уверены, что всё нужное есть; иначе — обычный тег (`python:3.12`).
- **Имя файла и `-f`.** По умолчанию Docker ищет файл `Dockerfile`. Если он назван иначе (`Dockerfile.dev`, `Dockerfile.prod`) — укажите `docker build -f Dockerfile.dev -t myapp .`.
- **Dockerfile — в корне репозитория** рядом с приложением: он попадёт в git вместе с кодом и не мешает запуску приложения.
- **`.dockerignore`** — файл рядом с Dockerfile, исключает из контекста сборки лишнее (`node_modules`, `.git`, логи). Ускоряет сборку и уменьшает образ (аналог `.gitignore`).
- Напоминание: **каждая инструкция = слой**, слои кэшируются — редко меняющееся ставьте выше, часто меняющееся (копирование кода) ниже (см. главу 9).

## Д6. Dev-режим: hot reload без пересборки

Отдельный приём для **разработки** (второй курс показывает на Node.js): чтобы не пересобирать образ на каждое изменение кода, код **монтируют внутрь контейнера bind mount'ом**, а внутри запускают watcher (например, `nodemon`), который сам перезапускает приложение при правках:

```bash
docker run -d -p 3000:3000 \
  -v $(pwd):/app \        # код с хоста монтируется в контейнер
  -w /app \
  node:20-alpine \
  npx nodemon main.js     # следит за файлами и перезапускает
```

Изменили файл на хосте → nodemon внутри контейнера подхватил → приложение перезапустилось, **без `docker build`**. Это стандартный паттерн локальной разработки в Docker.

## Итог дополнения

Второй курс добавил к пособию: **клиент-серверную архитектуру** (client → daemon → host по REST API), **модель слоёв** (read-only слои образа + записываемый слой контейнера, переиспользование слоёв), **чёткое различие реестр vs репозиторий**, **публикацию образа** (`login → tag → push`) и **практики Dockerfile** (`WORKDIR /app`, alpine, `-f`, `.dockerignore`) плюс **dev hot-reload** через bind-mount кода. Всё остальное (команды, порты, тома, сети, compose, Portainer) в двух курсах совпадает и уже разобрано выше.

## В1. Что такое `.dockerignore` и зачем он нужен?

**Ответ.** Файл рядом с Dockerfile (аналог `.gitignore`), который **исключает файлы/папки из контекста сборки** — они не попадают в образ.

**Зачем (конкретно).** Уменьшить размер образа и ускорить сборку. Что обычно исключают:

- **тесты и конфиги линтеров/форматтеров** — на проде не нужны;
- **виртуальные окружения** (`venv`, `node_modules` если ставятся при сборке) — образ и так изолирован, тащить их бессмысленно;
- **`.git`, логи, временные файлы, локальные `.env`** с секретами.

Эффект — реальный: образ легко ужать, например, с ~1 ГБ до ~300 МБ, просто выкинув лишнее.

```
# .dockerignore
.git
tests/
venv/
node_modules/
*.log
.env
```

**💬 Идеальный ответ (проговор):**
> «`.dockerignore` — это как `.gitignore`, только для Docker: он исключает файлы и папки из **контекста сборки**, чтобы они не попали в образ. Нужен, чтобы образ был лёгким, а сборка быстрой. Я туда всегда кладу `.git`, тесты, конфиги линтеров, виртуальные окружения и `node_modules`, логи и локальные `.env` с секретами — всё, что приложению в проде не нужно. На практике это ужимает образ в разы — условно с гигабайта до трёхсот мегабайт — и заодно не даёт секретам утечь в образ.»

## В2. Что такое multi-stage build (мультистейдж) и зачем?

**Ответ.** Dockerfile с **несколькими стадиями `FROM`**: в одной стадии приложение **собирают/компилируют** (нужен компилятор, dev-зависимости), а в **финальный** образ копируют **только результат** — готовые артефакты, без инструментов сборки.

**Зачем.** Финальный образ получается **маленьким и безопасным**: в нём нет компилятора, dev-пакетов, исходников. Особенно важно для компилируемых языков (Go, C++), где в прод нужен только бинарник, а не весь тулчейн.

```dockerfile
# стадия сборки
FROM golang:1.22 AS build
WORKDIR /src
COPY . .
RUN go build -o app .

# финальная стадия — только бинарник
FROM alpine:3.20
COPY --from=build /src/app /app
CMD ["/app"]
```

В реальных проектах Dockerfile бывают на 20–40 инструкций с несколькими стадиями — это норма.

**💬 Идеальный ответ (проговор):**
> «Multi-stage build — это Dockerfile с несколькими `FROM`, то есть несколькими стадиями. В первой стадии я собираю или компилирую приложение — там есть компилятор и dev-зависимости. А в финальную стадию через `COPY --from=build` копирую **только результат** — готовый бинарник или собранные ассеты — и беру лёгкий базовый образ вроде alpine. Смысл в том, что в прод-образ не тащится тулчейн: он получается маленьким и более безопасным, потому что в нём нет ни компилятора, ни исходников. Особенно критично для Go и C++, где нужен только бинарник.»

**SMART:** S — несколько `FROM` + `COPY --from`; M — размер прод-образа падает в разы, нет dev-инструментов; A — штатная фича Docker; R — ответ на «как уменьшить и обезопасить прод-образ»; T — ~30 сек.

## В3. Чем `RUN` отличается от `CMD`?

**Ответ.** Разные фазы жизни:

- **`RUN`** выполняется **на этапе сборки образа** (`docker build`) — ставит пакеты, компилирует. `RUN` может быть **много**, они идут друг за другом, каждый создаёт слой.
- **`CMD`** выполняется **при запуске контейнера** (`docker run`) — это команда старта приложения. `CMD` **один** (последний перекрывает предыдущие).

**Зачем различать.** Частая путаница на собесе. Правило: «готовим образ» → `RUN`; «что запустится в контейнере» → `CMD`.

**💬 Идеальный ответ (проговор):**
> «Они работают в разные моменты. `RUN` выполняется на этапе **сборки** образа — им я ставлю пакеты, компилирую; таких `RUN` может быть сколько угодно, каждый добавляет слой. А `CMD` — это команда **запуска** контейнера, срабатывает при `docker run`, и она одна. Простое правило: “готовлю образ” — это `RUN`, “что стартует в контейнере” — это `CMD`.»

## В4. `CMD` vs `ENTRYPOINT` — три варианта и зачем ENTRYPOINT

**Ответ.** Зависит от комбинации:

- **только `CMD`** — команду запуска можно **полностью переопределить** при `docker run` (например, вместо `uvicorn` запустить `gunicorn`).
- **только `ENTRYPOINT`** — основную команду **нельзя переопределить**, можно лишь **дописать аргументы** сбоку.
- **`ENTRYPOINT` + `CMD`** — `ENTRYPOINT` фиксирует **саму программу** (например, `uvicorn main:app`), а `CMD` задаёт **аргументы по умолчанию** (например, число воркеров), которые при запуске **можно** переопределить.

**Зачем ENTRYPOINT.** Детерминированный запуск и защита от ошибок: джун/стажёр не запустит контейнер «не той командой» — основная команда зашита. На практике чаще всего используют просто `CMD`; `ENTRYPOINT` — когда нужно жёстко зафиксировать точку входа.

**💬 Идеальный ответ (проговор):**
> «Тут три варианта. Только `CMD` — команду запуска при `docker run` можно полностью заменить, например, вместо uvicorn запустить gunicorn. Только `ENTRYPOINT` — основную команду переопределить нельзя, можно лишь дописать аргументы сбоку. И связка `ENTRYPOINT` + `CMD` — самый удобный вариант: `ENTRYPOINT` жёстко фиксирует саму программу, а `CMD` задаёт аргументы по умолчанию, которые при запуске можно переопределить. Зачем `ENTRYPOINT` — детерминированный запуск и защита от ошибок: никто не стартанёт контейнер “не той командой”. На практике чаще хватает `CMD`, а `ENTRYPOINT` беру, когда точку входа надо зафиксировать намертво.»

## В5. Зачем пробрасывать порты, если в Dockerfile есть `EXPOSE`?

**Ответ.** `EXPOSE` **ничего не открывает** — это чисто **документация**: он сообщает разработчику, на каком порту работает приложение внутри контейнера. Реальный доступ снаружи даёт **только `-p хост:контейнер`** при запуске.

**Зачем тогда EXPOSE.** Чтобы, читая Dockerfile, было понятно, какой порт пробрасывать. То есть EXPOSE помогает **грамотно** сделать `-p`, но сам по себе доступ не открывает. (Связано с главой 5.)

**💬 Идеальный ответ (проговор):**
> «`EXPOSE` в Dockerfile ничего не открывает — это документация: он сообщает, на каком порту работает приложение внутри контейнера. Реальный доступ снаружи даёт только `-p хост:контейнер` при запуске. То есть `EXPOSE` нужен, чтобы, читая Dockerfile, я знал, какой порт пробрасывать, но сам порт наружу он не выставляет. По умолчанию контейнер закрыт — открываю осознанно через `-p`.»

## В6. `volume` vs `bind mount` — когда что?

**Ответ.**

- **Named volume** — для **прода и баз данных**: Docker сам решает, где хранить данные, путь не привязан к конкретной машине → переносимо между серверами.
- **Bind mount** — для **локальной разработки**: монтируешь свою рабочую папку в контейнер, и правки в коде **сразу видны внутри** (сохранил файл — контейнер увидел). Удобно разрабатывать прямо в контейнере, не пересобирая.

**Зачем разрабатывать в контейнере.** Когда система из 5–6 сервисов (compose), локальный запуск в контейнерах **приближен к проду** — ловишь «у меня работает, а на стенде нет» ещё до коммита. Правило: **прод/БД → volume, локальная разработка → bind mount**. (Расширяет главу 7.)

**💬 Идеальный ответ (проговор):**
> «Оба монтируют данные, но под разные задачи. **Named volume** — для прода и баз данных: Docker сам решает, где физически хранить данные, путь не привязан к машине, поэтому переносимо между серверами. **Bind mount** — для локальной разработки: монтирую свою рабочую папку в контейнер, и правки в коде сразу видны внутри — сохранил файл, контейнер увидел, пересобирать не надо. Зачем разрабатывать в контейнере: когда система из пяти-шести сервисов, локальный запуск в контейнерах максимально близок к проду, и ловишь “у меня работает, а на стенде нет” ещё до коммита. Правило простое: прод и БД — volume, локальная разработка — bind mount.»

**Инженерная схема:**
- *Проблема:* данные внутри контейнера эфемерны (пропадут при пересоздании); а при разработке хочется, чтобы правки кода применялись без пересборки.
- *Если проигнорировать:* потеря данных БД при рестарте / медленный цикл разработки (пересборка образа на каждую правку).
- *Куда дальше:* прод/БД → named volume (переносимо, Docker управляет), разработка → bind mount (правки видны сразу).
- *Что даёт:* сохранность данных в проде и быстрый dev-цикл локально.

## В7. В чём разница между Docker и Docker Compose?

**Ответ.** **Docker Compose — надстройка над Docker**, которая описывает конфигурацию контейнеров в **YAML-файле** и управляет **жизненным циклом сразу многих** контейнеров одной командой.

**Зачем Compose, даже для ОДНОГО контейнера.** В «голом» Docker нет удобного файла конфигурации — все настройки (образ, имя, сеть, порты, переменные) приходится передавать флагами в длинной команде `docker run`, которую надо где-то хранить. Compose переносит это в понятный `docker-compose.yml`: `docker compose up` — поднять, `down` — погасить, `build` — собрать. Читаемо, воспроизводимо, в git. (Дополняет главу 10.)

**💬 Идеальный ответ (проговор):**
> «Docker Compose — это надстройка над Docker, которая описывает контейнеры в YAML-файле и управляет жизненным циклом сразу многих контейнеров одной командой. Ценность даже для одного контейнера: в голом Docker нет удобного конфиг-файла, все настройки — образ, имя, сеть, порты, переменные — приходится передавать флагами в длинной `docker run`, которую надо где-то хранить. Compose переносит это в читаемый `docker-compose.yml`: `up` — поднять, `down` — погасить, `build` — собрать. Плюс несколько сервисов автоматически попадают в одну сеть и общаются по имени контейнера. Читаемо, воспроизводимо и лежит в git рядом с кодом.»

## В8. Зачем Docker, если в компании Kubernetes?

**Ответ.** Kubernetes оркестрирует контейнеры в проде, но **разработка всё равно на Docker**:

- локально поднять приложение в контейнере, чтобы проверить «как в проде» до коммита;
- быстро развернуть локально **БД / Redis / брокер** нужных версий, не ставя их на систему;
- держать **разные версии** зависимостей под разные микросервисы.

То есть Docker (и Compose) — рабочий инструмент **локальной разработки и тестирования**, даже когда в проде Kubernetes.

**💬 Идеальный ответ (проговор):**
> «Kubernetes оркестрирует контейнеры в проде, но разработка всё равно на Docker. Локально я поднимаю приложение в контейнере, чтобы проверить “как в проде” и не закоммитить баг; одной командой разворачиваю нужные версии БД, Redis, брокера, не ставя их на систему; и держу разные версии зависимостей под разные микросервисы. Так что Docker и Compose нужны как инструмент локальной разработки и тестирования независимо от того, что в проде Kubernetes. По сути Kubernetes управляет теми же контейнерами, что я собираю Docker'ом.»

## В9. Как работает кэш слоёв и как правильно строить Dockerfile? (кратко)

**Ответ.** Каждая инструкция — слой, слои кэшируются; при изменении слоя пересобираются он и все **ниже**. Поэтому **сначала ставим зависимости, потом копируем код**: код меняется постоянно, и если `COPY` кода стоит вверху, кэш зависимостей сбрасывается каждый раз (долгая пересборка). (Подробно — глава 9.6.)

**💬 Идеальный ответ (проговор):**
> «Каждая инструкция Dockerfile — это слой, и слои кэшируются: при изменении слоя пересобирается он и все, что ниже. Отсюда правило порядка — сначала ставим зависимости, потом копируем код. Если `COPY` кода стоит вверху, то любая правка кода, а он меняется постоянно, сбрасывает кэш и заставляет заново ставить зависимости, а это самая долгая часть сборки. Поэтому редко меняющееся — выше, часто меняющееся — ниже. Типичный питоновский порядок: сначала `COPY requirements.txt` + `RUN pip install`, и только потом `COPY . .` с кодом.»

Разбор из четвёртого видео — 15 частых вопросов с **ловушками собеса** и идеальными ответами. Формат по каждому: **Ответ** (по сути) → **⚠️ Ловушка** → **💬 Идеальный ответ (проговор)**; где полезно — SMART/инженерная схема. ## В1. Чем отличается image от контейнера?

**Ответ.** Image — **read-only шаблон**: слои файловой системы + метаданные, **неизменяем**. Контейнер — **запущенный экземпляр** image с добавленным сверху **writable-слоем** и процессом внутри. Из одного image — много контейнеров. ООП-аналогия: image = класс, контейнер = объект. Команды: `docker images`, `docker ps`, `docker ps -a`.

**⚠️ Ловушка.** «Можно ли изменить image напрямую?» — **нет, image immutable**. Изменения идут только в writable-слой контейнера; сохранить их можно `docker commit`, но это **антипаттерн** — образ должен собираться из Dockerfile, а не «замораживанием» контейнера.

**💬 Идеальный ответ:**
> «Image — это неизменяемый read-only шаблон: слои файловой системы плюс метаданные. Контейнер — запущенный экземпляр этого образа: сверху добавляется тонкий writable-слой и внутри крутится процесс. Из одного образа поднимается сколько угодно контейнеров, у каждого свой writable-слой, база общая. Проще всего через ООП: образ — класс, контейнер — объект. И важный момент: образ менять напрямую нельзя, он immutable; всё меняется в слое контейнера. Есть `docker commit`, чтобы заморозить контейнер в образ, но это антипаттерн — правильно пересобирать из Dockerfile.»

## В2. Что такое Docker layer и почему это важно?

**Ответ.** Каждая инструкция Dockerfile создаёт **слой**; слои кэшируются и переиспользуются между сборками. Изменился слой N → **все слои ниже** пересобираются. Отсюда порядок инструкций критичен: редко меняющееся (зависимости) — выше, часто меняющееся (код) — ниже. `docker history <образ>` показывает слои и их размер. (Механика — глава 9.6, Д2.)

**⚠️ Ловушка.** Покажут Dockerfile, где `COPY . .` стоит **до** `RUN npm install` — это убивает кэш при любой правке кода. Правильно: сначала `COPY package.json`, затем `RUN npm install`, и только потом `COPY . .`.

**💬 Идеальный ответ:**
> «Каждая инструкция Dockerfile — это слой, слои кэшируются по содержимому. Если слой изменился, пересобирается он и все, что ниже, — как каскад. Поэтому порядок критичен: зависимости, которые меняются редко, ставлю выше, а код, который меняется постоянно, — ниже. Классическая ошибка — `COPY . .` до установки зависимостей: тогда любая правка кода сбрасывает кэш и заново тянет зависимости. Правильно — сначала скопировать манифест зависимостей, установить их, и только потом копировать код. Посмотреть слои и их размер — `docker history`.»

## В3. Что такое multi-stage build и зачем?

**Ответ.** Несколько `FROM` в одном Dockerfile: в первой стадии собираешь приложение (компилятор, build-инструменты), в финальную копируешь `COPY --from=build` **только артефакт** в минимальный образ. Финал не содержит компиляторы и исходники — размер падает в разы. Можно остановиться на промежуточной стадии для дебага: `docker build --target build`.

**⚠️ Ловушка.** «Как уменьшить размер образа?» — multi-stage называть **первым**.

**💬 Идеальный ответ:**
> «Multi-stage — это несколько стадий `FROM` в одном Dockerfile. В стадии сборки есть компилятор и dev-зависимости, там я собираю приложение. А в финальную стадию через `COPY --from` переношу только готовый артефакт и беру лёгкий базовый образ. В итоге в прод-образе нет ни компилятора, ни исходников — он маленький и безопаснее. Аналогия: цех сборки и витрина — на витрину выставляем только готовый продукт. Ещё удобно, что можно собраться до промежуточной стадии через `--target` для отладки.»

**SMART:** S — несколько `FROM` + `COPY --from`; M — размер прод-образа падает в разы; A — штатная фича; R — «как уменьшить/обезопасить образ»; T — ~30 сек.

## В4. Разница между CMD и ENTRYPOINT (+ exec form vs shell form)

**Ответ.** `ENTRYPOINT` — **неизменяемая точка входа** (исполняемый файл, который всегда запускается). `CMD` — **аргументы по умолчанию**, легко переопределяемые при запуске. Если указаны оба — `CMD` становится аргументами для `ENTRYPOINT` (ENTRYPOINT = программа, CMD = её флаги).

**⚠️ Ловушка — exec form vs shell form.** **Exec form** — в квадратных скобках `["nginx","-g","daemon off;"]` — запускает процесс напрямую, **без обёртки-shell**, и сигналы (`SIGTERM` при остановке) идут **прямо в приложение** → корректный graceful shutdown. **Shell form** — `nginx -g "daemon off;"` — создаёт лишний процесс-обёртку `/bin/sh -c`, и сигналы могут **не дойти** до приложения. Для `CMD`/`ENTRYPOINT` предпочитают **exec form**.

**💬 Идеальный ответ:**
> «`ENTRYPOINT` — это неизменяемая точка входа, сама программа, которая всегда стартует. `CMD` — аргументы по умолчанию, их можно переопределить при `docker run`. Если указаны оба, `CMD` работает как аргументы к `ENTRYPOINT`: ENTRYPOINT — это, например, nginx, а CMD — его флаги. Отдельно важна форма записи: exec form в квадратных скобках запускает процесс напрямую, и сигналы вроде SIGTERM идут прямо в приложение — это правильный graceful shutdown. Shell form создаёт лишнюю обёртку `sh -c`, и сигнал может не дойти. Поэтому пишу в exec form.»

## В5. Что такое Docker Network и какие типы бывают?

**Ответ.** Изолированное сетевое пространство для контейнеров. Типы:

- **bridge** — по умолчанию, изолированная сеть на хосте;
- **host** — контейнер использует сеть хоста напрямую, без NAT;
- **none** — сеть отключена полностью;
- **overlay** — мульти-хостовая сеть (Swarm/оркестрация несколько машин);
- **macvlan** — контейнеру даётся собственный MAC-адрес, он виден в физической сети как отдельное устройство.

В пользовательской bridge-сети контейнеры **резолвят друг друга по имени** через встроенный DNS. (База — глава 8.)

**⚠️ Ловушка.** В **дефолтной** bridge-сети контейнеры общаются **только по IP**, а в **пользовательской** (user-defined) bridge — уже **по имени** через DNS. Частая путаница.

**💬 Идеальный ответ:**
> «Docker Network — изолированное сетевое пространство для контейнеров. Основные типы: bridge — дефолтная изолированная сеть на хосте; host — контейнер сидит прямо в сети хоста без NAT; none — сети нет; overlay — для мульти-хостовых сетей в оркестрации; macvlan — контейнер получает свой MAC и виден в физической сети как отдельное устройство. Ключевой нюанс: в пользовательской bridge-сети контейнеры находят друг друга по имени через встроенный DNS, а в дефолтной bridge — только по IP. Поэтому под свои сервисы всегда создаю отдельную сеть.»

## В6. Чем COPY отличается от ADD?

**Ответ.** `COPY` просто копирует файлы из build-контекста в образ. `ADD` делает то же, но ещё умеет **авто-распаковывать tar-архивы** и **скачивать файлы по URL**. Официальная рекомендация Docker — **всегда `COPY`** ради прозрачности; `ADD` оправдан только если реально нужна авто-распаковка архива.

**⚠️ Ловушка.** Скачивание по URL через `ADD` — **антипаттерн**; лучше явно `RUN curl` / `RUN wget` (видно, что и откуда качается, и можно проверить контрольную сумму).

**💬 Идеальный ответ:**
> «`COPY` — тупой копировщик: берёт файлы из контекста и кладёт в образ, ничего больше. `ADD` умеет сверх этого автоматически распаковывать tar-архивы и качать по URL — и именно поэтому он опаснее, поведение менее предсказуемо. Рекомендация Docker — по умолчанию использовать `COPY` ради прозрачности, а `ADD` брать только когда реально нужна авто-распаковка локального архива. Качать по URL через `ADD` — антипаттерн, лучше явный `RUN curl` с проверкой хэша.»

## В7. Как работают volumes и чем они лучше bind mounts?

**Ответ.** **Volume** — именованное хранилище, которым **управляет сам Docker** (лежит в его системной директории). **Bind mount** — монтирование конкретного пути хоста внутрь контейнера. Volumes лучше для прода: не зависят от структуры хоста, проще бэкапить и переносить между серверами. Bind mount — для разработки: правки на хосте сразу видны в контейнере. (База — глава 7, В6.)

**⚠️ Ловушка.** «Что будет при удалении контейнера?» — и volume, и bind mount **останутся** (данные не привязаны к жизни контейнера). Но если удалить volume **явно** — `docker volume rm` — данные пропадут навсегда.

**💬 Идеальный ответ:**
> «Volume — именованное хранилище, которым управляет Docker: он сам решает, где физически лежат данные, поэтому они не зависят от структуры хоста, их проще бэкапить и переносить между серверами — это выбор для прода и баз данных. Bind mount — это монтирование конкретной папки хоста в контейнер, правки видны сразу, поэтому он удобен для локальной разработки. Аналогия: volume — чемодан, который Docker несёт с собой куда угодно, а bind mount — верёвка, привязанная к конкретному месту. При удалении контейнера данные и там, и там остаются; пропадут они, только если явно сделать `docker volume rm`.»

## В8. Что такое `.dockerignore` и почему он важен?

**Ответ.** Файл с паттернами, которые **исключаются из build-контекста** перед отправкой демону. Без него в контекст попадают `.git`, `node_modules`, логи, `.env` с секретами → контекст раздувается, сборка тормозит, есть риск **утечки секретов** в образ. Это `.gitignore`, но для Docker. (Разобрано — В1 Дополнения 2.)

**⚠️ Ловушка.** «Почему сборка медленная?» — первое, что проверяем, **размер build-контекста**. Если туда случайно попали `node_modules` или `.git` — вот и причина.

**💬 Идеальный ответ:**
> «`.dockerignore` — это как `.gitignore`, только он исключает файлы из build-контекста, который клиент отправляет демону перед сборкой. Без него в контекст улетают `.git`, `node_modules`, логи, `.env` — контекст раздувается, сборка тормозит, и есть риск запечь секреты в образ. Поэтому если спрашивают, почему сборка медленная, первое, что я проверю, — размер контекста и что в него случайно не попало лишнее.»

## В9. Как ограничить ресурсы контейнера?

**Ответ.** Флагами `docker run`: `--memory` (лимит RAM), `--cpus` (кол-во ядер), `--cpu-shares` (относительный вес между контейнерами). Это критично против проблемы **noisy neighbor** — когда один контейнер съедает все ресурсы хоста и роняет соседей. В Kubernetes аналоги — `resources.limits` и `resources.requests`.

**⚠️ Ловушка.** «Что при превышении лимита?» — при превышении **памяти** контейнер убивает **OOM Killer** с кодом выхода **137**. При превышении **CPU** процессы просто **тротлятся** (замедляются), но не убиваются.

**💬 Идеальный ответ:**
> «Ресурсы ограничиваю флагами `docker run`: `--memory` для лимита оперативки, `--cpus` для числа ядер, `--cpu-shares` для относительного веса между контейнерами. Это защита от noisy neighbor — когда один контейнер съедает всё и роняет соседей. Важно понимать разницу поведения при превышении: память — контейнер убивает OOM Killer с кодом 137, а CPU — не убивает, а тротлит, то есть замедляет. В Kubernetes это те же limits и requests.»

**Инженерная схема:**
- *Проблема:* без лимитов один контейнер может выесть всю память/CPU хоста (noisy neighbor).
- *Если проигнорировать:* один сервис роняет соседей на том же хосте; каскадные падения.
- *Куда дальше:* `--memory`/`--cpus`/`--cpu-shares` (в k8s — limits/requests); мониторинг `docker stats`.
- *Что даёт:* изоляция по ресурсам, предсказуемость, отказ одного не валит остальных.

## В10. Что происходит при `docker build`? (шаги изнутри)

**Ответ.** Конвейер: (1) клиент упаковывает весь build-контекст в **tar** и отправляет демону; (2) демон читает Dockerfile **построчно**; (3) для каждой инструкции создаёт **временный контейнер**, выполняет команду, **коммитит** изменения в новый **слой**; (4) слой кэшируется **по хэшу содержимого** — не менялся, берётся из кэша; (5) в конце все слои объединяются в финальный образ.

**⚠️ Ловушка.** «Почему сборка внезапно долгая при изменении одной строки?» — скорее всего, **порядок инструкций**: кэш инвалидируется слишком рано (правка вверху сбрасывает всё ниже).

**💬 Идеальный ответ:**
> «Сборка — это конвейер. Клиент сначала пакует build-контекст в tar и шлёт демону — поэтому важен `.dockerignore`. Дальше демон идёт по Dockerfile построчно: под каждую инструкцию создаёт временный контейнер, выполняет команду и коммитит результат в новый слой. Каждый слой кэшируется по хэшу содержимого — если он и всё выше не менялись, берётся из кэша. В конце слои склеиваются в финальный образ. Отсюда и типичная проблема “поменял одну строку, а пересборка долгая” — значит, инструкция стоит слишком высоко и рано инвалидирует кэш.»

## В11. Как правильно хранить секреты в Docker?

**Ответ.** **Никогда не зашивать секреты в Dockerfile через `ENV`** — они попадут в слой образа **навсегда**, даже если потом удалить инструкцию (останутся в истории слоёв). Правильно: передавать секреты **через переменные окружения при `docker run`**; использовать **Docker Secrets** в режиме Swarm; монтировать секреты **как файлы**; для build-секретов — флаг **`--secret`** в BuildKit (не попадает в слой вообще).

**⚠️ Ловушка.** Покажут Dockerfile с `ENV PASSWORD=...` — это **фейл сразу**. Даже если удалить строку позже, секрет **останется в истории слоёв**.

**💬 Идеальный ответ:**
> «Главное правило — секреты не запекать в образ. `ENV PASSWORD=...` в Dockerfile — это фейл: секрет уходит в слой навсегда, и даже если удалить инструкцию, он останется в истории слоёв, образ ведь неизменяем послойно. Правильно секреты приходят снаружи при запуске: через переменные окружения в `docker run` или `--env-file`, через Docker Secrets в Swarm, монтированием файлом, а для секретов на этапе сборки — через `--secret` в BuildKit, который не попадает в слой. Мнемоника: секрет в Dockerfile — это татуировка, останется навсегда.»

**Инженерная схема:**
- *Проблема:* секрет, зашитый в образ, живёт в слоях навсегда и утекает вместе с образом в реестр.
- *Если проигнорировать:* компрометация паролей/токенов при пуше образа.
- *Куда дальше:* секреты снаружи — env при запуске / Docker Secrets / BuildKit `--secret`; `.dockerignore` на `.env`.
- *Что даёт:* секреты не попадают в образ и историю слоёв.

## В12. EXPOSE vs публикация порта через `-p`

**Ответ.** `EXPOSE` в Dockerfile — **документационная метка**: говорит, что контейнер слушает порт, но физически порт на хосте **не открывает**. Флаг `-p` при запуске реально пробрасывает порт хоста в контейнер (через NAT). Дополнительно: `-P` (заглавная) **автоматически публикует все** порты из `EXPOSE` на случайные порты хоста. (База — глава 5, В5.)

**⚠️ Ловушка.** «Зачем тогда EXPOSE, если ничего не открывает?» — для документации и для работы флага `-P`.

**💬 Идеальный ответ:**
> «`EXPOSE` — это вывеска на двери “работаю на порту 80”, но сама дверь закрыта: наружу порт он не открывает. Реально пробрасывает только `-p хост:контейнер` через NAT. `EXPOSE` нужен для документации — чтобы было понятно, какой порт пробрасывать, — и для флага `-P` с большой буквы, который автоматически опубликует все объявленные в EXPOSE порты на случайные порты хоста.»

## В13. Что такое Docker Compose и когда его использовать?

**Ответ.** Инструмент **декларативного описания** мультиконтейнерных приложений в одном **YAML**. Одной командой поднимаешь окружение из нескольких сервисов с сетями, volumes, health-checks, переменными, портами и зависимостями. Идеален для локальной разработки и простых деплоев. (База — глава 10, В7.)

**⚠️ Ловушка.** «Чем Compose отличается от Kubernetes?» — Compose для локалки и простых случаев; Kubernetes — для прода с **автомасштабированием, самовосстановлением и rolling-обновлениями**.

**💬 Идеальный ответ:**
> «Docker Compose — это декларативное описание мультиконтейнерного приложения в YAML: сервисы, сети, volumes, health-checks, переменные, зависимости — всё в одном файле, и одной командой `up` поднимается целое окружение. Идеален для локальной разработки и простых деплоев. От Kubernetes отличается масштабом задачи: Compose — для локалки и несложных случаев, а Kubernetes — для прода, где нужны автомасштабирование, самовосстановление и rolling-обновления.»

## В14. Как дебажить упавший или зависший контейнер?

**Ответ.** Алгоритм:

1. **Логи** — `docker logs -t --tail 100 <контейнер>` (`-t` = timestamps).
2. Контейнер живой → **зайти внутрь**: `docker exec -it <контейнер> sh`.
3. Контейнер упал → **exit-код**: `docker inspect` (137 = OOM Killer, 1 = ошибка внутри приложения).
4. Проблема прямо со стартом → запустить образ с **переопределённым ENTRYPOINT** (например, `sh`), чтобы осмотреться.
5. **Ресурсы в реальном времени** — `docker stats`.

Мнемоника: логи — симптомы, `inspect` — анализы, `exec` — операция, `stats` — кардиограмма.

**⚠️ Ловушка.** «Контейнер упал с кодом 137 — что делать?» — это **OOM Killer**: увеличить лимит памяти либо оптимизировать приложение.

**💬 Идеальный ответ:**
> «Действую по алгоритму от дешёвого к дорогому. Сначала логи — `docker logs -t --tail`, timestamps помогают привязать к событиям. Если контейнер живой, захожу внутрь через `docker exec -it sh` и смотрю на месте. Если упал — беру exit-код через `docker inspect`: 137 — это OOM Killer, значит не хватило памяти; 1 — обычно ошибка самого приложения. Если падает прямо на старте, запускаю образ с переопределённым entrypoint на `sh`, чтобы осмотреться внутри. И `docker stats` — для ресурсов в реальном времени. Мнемоника: логи — симптомы, inspect — анализы, exec — операция, stats — кардиограмма.»

**Инженерная схема:**
- *Проблема:* контейнер упал/завис, причина неочевидна.
- *Если проигнорировать:* гадание вместо диагностики, долгий простой.
- *Куда дальше:* логи → exec внутрь → inspect exit-код (137 OOM / 1 app) → override entrypoint → stats.
- *Что даёт:* быстрый и системный поиск причины по симптомам.

## В15. Чем Rootless Docker отличается от обычного и зачем?

**Ответ.** В обычном режиме демон Docker работает **от root**, и компрометация контейнера потенциально даёт **root на хосте** через container escape. **Rootless** запускает демон и контейнеры от **непривилегированного пользователя** через **user namespaces** → заметно меньше поверхность атаки. Ограничения: нельзя биндить порты **ниже 1024**, работают **не все storage-драйверы**, нет поддержки AppArmor/SELinux.

**⚠️ Ловушка.** «Почему тогда не использовать rootless везде?» — чуть ниже производительность, меньше фич, сложности с сетью; но для **высокобезопасных окружений** это почти обязательное требование.

**💬 Идеальный ответ:**
> «В обычном режиме демон крутится от root, поэтому побег из контейнера потенциально даёт root на хосте. Rootless запускает демон и контейнеры от обычного непривилегированного пользователя через user namespaces — это заметно снижает поверхность атаки. Цена — нельзя слушать порты ниже 1024, не все storage-драйверы работают, нет AppArmor/SELinux и чуть ниже производительность. Аналогия: обычный Docker — админ с полными правами, rootless — обычный пользователь с ограничениями, но безопаснее. Везде подряд не ставят из-за ограничений, но в security-критичных окружениях это практически обязательно.»

# Дополнение 4. Docker под капотом + база Kubernetes (из DevOps-гайда)

Пятое видео — DevOps-гайд, где Docker это «база», а основное — Kubernetes. Ниже новое: **за счёт чего вообще работают контейнеры** (cgroups + namespaces) и **база Kubernetes** (архитектура, объекты, `kubectl apply`, self-healing, сеть) — с интервью-ответами.

## Часть A. За счёт чего работают контейнеры: cgroups + namespaces

**Контейнер — это не «мини-ВМ», а обычный процесс хоста**, огороженный двумя механизмами **ядра Linux**:

- **namespaces (пространства имён)** — **изоляция**, определяют, что процесс **видит**: свои процессы (PID), свою сеть (NET), свою файловую систему (MNT), свой hostname (UTS), IPC, пользователей (USER). Контейнер в своих namespace видит только своё, будто он один в системе.
- **cgroups (control groups)** — **ограничение ресурсов**, сколько процесс **может съесть**: CPU, память, I/O. Это ровно то, чем работают флаги `--memory` / `--cpus` (см. В9).

Формула: **namespaces = изоляция (что видно), cgroups = лимиты (сколько можно)**. Ядро при этом **общее** с хостом — поэтому контейнеры лёгкие (в отличие от ВМ, у которой своё ядро).

**⚠️ Классический вопрос собеса:** «За счёт чего вообще работают контейнеры / Docker?» — ответ ровно из двух слов: **cgroups и namespaces**.

**💬 Идеальный ответ:**
> «Контейнер — это не виртуалка, а обычный процесс Linux, изолированный двумя механизмами ядра. Namespaces дают изоляцию: у контейнера свой список процессов, своя сеть, своя файловая система, свой hostname — он видит только своё. А cgroups ограничивают ресурсы: сколько CPU, памяти, I/O он может занять — этим же работают `--memory` и `--cpus`. Ядро при этом общее с хостом, поэтому контейнер лёгкий и стартует за миллисекунды, в отличие от ВМ со своим ядром. Коротко: namespaces — что видно, cgroups — сколько можно.»

Посмотреть вживую: `lsns` (список namespaces), `/proc/<pid>/ns/` (namespace процесса), `unshare`/`nsenter` (поиграться с ними вручную).

## Часть B. Kubernetes — база

### Б1. Что это и зачем

**Kubernetes (k8s)** — **оркестратор контейнеров**: запускает, масштабирует, **самовосстанавливает**, обновляет без простоя (rolling update) и связывает контейнеры на **кластере машин**.

**Когда нужен:** много сервисов/машин; нужно **динамически масштабироваться** под нагрузку; нужны **self-healing**, **rolling-обновления**, **service discovery** (сервисы находят друг друга). **Когда НЕ нужен:** один-два сервиса на одной машине — это оверкилл, хватит **Docker Compose**. (Правильный ответ на собесе — назвать и «когда не нужен».)

### Б2. Managed vs on-prem

- **Managed** (EKS/GKE/AKS, Yandex Managed k8s) — облако управляет **control plane** за тебя; ты платишь и пользуешься.
- **On-prem / self-hosted** — сам разворачиваешь на своих серверах (`kubeadm`, `kubespray` — это набор Ansible-плейбуков). Больше контроля, но всё обслуживание на тебе.

### Б3. Архитектура кластера

**Control Plane (мозг кластера):**

- **API server** — **единая точка входа**; все запросы (kubectl, компоненты) идут через него.
- **etcd** — key-value база (как Redis по типу), хранит **всё состояние кластера**. Писать в неё может только API server. Потеряли etcd без бэкапа → **потеряли кластер**.
- **Scheduler (планировщик)** — выбирает **ноду для новых подов** по правилам: requests/limits, labels/селекторы, affinity/anti-affinity, taints/tolerations.
- **Controller Manager** — **«термостат»**: постоянно сверяет фактическое состояние с **желаемым (desired state)** и приводит к нему. Это движок self-healing.
- **Cloud Controller Manager** — интеграция с облаком (в managed); на on-prem его нет.

**Worker nodes (рабочие ноды — тут крутится нагрузка):**

- **kubelet** — агент на каждой ноде: запускает и следит за подами через runtime, докладывает статус.
- **kube-proxy** — настраивает **сетевые правила** (iptables/ipvs) для Service.
- **container runtime** (containerd / CRI-O) — собственно **запускает контейнеры** (Docker как runtime в k8s больше не используется — вытеснен containerd).

### Б4. Основные объекты (по нарастающей)

| Объект | Что это / зачем |
|---|---|
| **Pod** | минимальная единица запуска — **группа контейнеров** с общей сетью и томами. Почему группа, а не один: sidecar-паттерн (основной контейнер + вспомогательный, общий `localhost` и тома) |
| **ReplicaSet** | держит **N одинаковых реплик** пода |
| **Deployment** | управляет ReplicaSet, даёт **rolling update и rollback**. Основной объект для **stateless**-приложений |
| **StatefulSet** | для **stateful** (БД): стабильные имена, свои тома, порядок запуска |
| **DaemonSet** | по **одному поду на каждую ноду** (агенты логов/мониторинга) |
| **Service** | **стабильная точка доступа** к подам (по label selector) + балансировка. Типы: ClusterIP (внутри), NodePort, LoadBalancer. Даёт **service discovery по имени** через DNS |
| **Ingress** | HTTP-маршрутизация **снаружи** (домены, пути, TLS) |
| **ConfigMap / Secret** | конфиги / секреты (как env или файлы) |
| **PersistentVolume / PVC** | диски для **постоянных данных** |

### Б5. Что происходит при `kubectl apply -f deployment.yaml` (топ-вопрос DevOps-собеса)

1. **kubectl** отправляет манифест в **API server** → аутентификация, авторизация (**RBAC**), admission-проверки.
2. API server валидирует и **записывает desired state в etcd**.
3. **Controller Manager** (Deployment → ReplicaSet controller) видит: нужно N подов, их нет → создаёт объекты Pod (снова через API server в etcd).
4. **Scheduler** видит поды **без ноды** → по правилам выбирает подходящие ноды → проставляет каждому его ноду.
5. **kubelet** на выбранной ноде видит «мой под» → через runtime **стягивает образ и запускает контейнеры**.
6. **kube-proxy** настраивает сетевые правила, чтобы трафик на Service шёл в поды.
7. Дальше Controller Manager **бесконечно сверяет** факт с desired — это и есть self-healing.

**💬 Идеальный ответ:**
> «Когда я делаю `kubectl apply`, kubectl шлёт манифест в API server — там аутентификация, RBAC и admission. API server сохраняет желаемое состояние в etcd. Дальше включается контроллер: Deployment-контроллер видит, что нужно N подов, а их нет, и создаёт их. Scheduler подхватывает поды без ноды и раскидывает их по нодам по requests/limits и affinity. На выбранной ноде kubelet видит свой под и через containerd запускает контейнеры, стянув образ. kube-proxy настраивает сеть для Service. И дальше контроллер-менеджер постоянно сверяет факт с желаемым состоянием — если под упал, поднимает новый. То есть весь Kubernetes — это цикл “привести фактическое состояние к желаемому”.»

### Б6. Self-healing и отказы (частые вопросы)

- **Под упал** → ReplicaSet-контроллер видит «реплик меньше N» → **поднимает новый**.
- **Нода упала** → её поды **пересоздаются на других нодах** (desired state сохраняется).
- **Control Plane упал** → уже запущенная нагрузка **продолжает работать** (kubelet локально держит поды), но **нельзя управлять/масштабировать/катить новое**, пока control plane не поднимется.
- **etcd потерял кворум** → потеря состояния кластера. Поэтому etcd держат в **нечётном** числе (3/5) для кворума и **бэкапят**.

### Б7. Сеть: CNI, kube-proxy, iptables/ipvs (кратко)

- **CNI** (Container Network Interface) — плагин сети подов; в кубере это **Calico** или **Cilium**: настраивает маршруты, интерфейсы, сетевые политики (кто с кем может общаться).
- **kube-proxy** — правит **iptables** или **ipvs** на нодах, чтобы обращение к Service балансировалось между его подами. ipvs производительнее на больших кластерах.

### Итог дополнения 4

Пятое видео добавило два новых пласта: **под капотом Docker** — контейнер это процесс, изолированный **namespaces** (что видно) и ограниченный **cgroups** (сколько можно); и **база Kubernetes** — control plane (API server, etcd, scheduler, controller-manager) + worker nodes (kubelet, kube-proxy, runtime), объекты (Pod → ReplicaSet → Deployment, Service, Ingress, ConfigMap/Secret, PV/PVC, StatefulSet/DaemonSet), разбор **`kubectl apply`** и **self-healing** через desired state. Это уже уровень DevOps-собеса поверх чистого Docker.

# Дополнение 5. Практика: nginx как reverse proxy + многосервисный стек

Шестое видео — 4-часовой практический курс. Бо́льшая часть (образы/контейнеры, `run`, монтирование портов и директорий, тома, сети, сборка Python-образа, установка библиотек через `RUN pip`, alpine vs debian, Compose) **уже разобрана выше** — не повторяю. Реально новое: **nginx в роли reverse proxy** и **сборка практического стека из нескольких сервисов**.

## Часть A. nginx как reverse proxy (проксирование)

Раньше в пособии nginx был **статик-сервером** (глава 9.4). Здесь у него **новая роль — reverse proxy**: nginx стоит **перед приложением** (Flask/Django на gunicorn/uvicorn) и проксирует на него запросы.

**Зачем это (конкретно).** Бэкенд-приложение **не выставляют наружу напрямую**. Впереди ставят nginx, который:

- **терминирует HTTP/HTTPS** (SSL-сертификаты — на nginx, а не в приложении);
- **отдаёт статику** сам (CSS/JS/картинки — быстро, минуя приложение);
- **проксирует динамику** на бэкенд (`proxy_pass`);
- **балансирует** между несколькими репликами приложения (горизонтальное масштабирование).

**Конфиг nginx (монтируется в контейнер):**

```nginx
# default.conf
upstream backend {
    server app:8000;          # "app" — имя контейнера бэкенда в compose-сети
}
server {
    listen 80;

    location /static/ {        # статику отдаёт сам nginx
        root /var/www;
    }
    location / {               # всё остальное — на бэкенд (gunicorn/uvicorn)
        proxy_pass http://backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

Конфиг подкладывают **bind mount'ом**, чтобы править без пересборки образа:

```bash
docker run -d --name nginx -p 80:80 \
  -v ./default.conf:/etc/nginx/conf.d/default.conf \
  nginx:latest
```

В Compose nginx и бэкенд сидят в одной сети и общаются **по имени сервиса** (`app`), а наружу торчит только nginx.

**💬 Идеальный ответ (зачем reverse proxy):**
> «Приложение на gunicorn я не выставляю в интернет напрямую — впереди ставлю nginx как reverse proxy. Он терминирует HTTPS, сам быстро отдаёт статику, а динамические запросы проксирует на бэкенд через `proxy_pass`. Плюс он же балансирует между репликами приложения при горизонтальном масштабировании. Наружу торчит только nginx, а бэкенд доступен лишь внутри docker-сети по имени контейнера — это и удобнее, и безопаснее.»

**Горизонтальное масштабирование.** Подняв несколько реплик бэкенда за `upstream`, nginx раскидывает нагрузку между ними. В Compose это `docker compose up --scale app=3` (или `deploy.replicas` в compose-файле) — три контейнера `app`, а nginx балансирует запросы.

## Часть B. Практический многосервисный стек (worked example)

Курс собирает наглядный пример — **4 связанных сервиса** в одном Compose (табло цены Bitcoin/USDT, обновляется каждые 5 сек):

| Сервис | Роль |
|---|---|
| **mongo** | база данных |
| **collector** (Python) | каждые 5 сек тянет цену Bitcoin/USDT из API и **пишет в Mongo** |
| **web** (Flask) | **читает из Mongo** и отображает в браузере |
| **mongo-express** | веб-**админка** для Mongo (смотреть данные мышкой) |

**Пример `docker-compose.yml` (сокращённо):**

```yaml
services:
  mongo:
    image: mongo:7
    environment:
      MONGO_INITDB_ROOT_USERNAME: root
      MONGO_INITDB_ROOT_PASSWORD: secret
    volumes:
      - mongo_data:/data/db          # данные переживают пересоздание
    networks: [appnet]

  collector:
    build: ./collector               # свой образ Python-сборщика
    depends_on: [mongo]              # стартует после mongo
    networks: [appnet]

  web:
    build: ./web                      # Flask
    ports: ["8000:8000"]
    depends_on: [mongo]
    networks: [appnet]

  mongo-express:
    image: mongo-express
    ports: ["8081:8081"]
    environment:
      ME_CONFIG_MONGODB_URL: mongodb://root:secret@mongo:27017/
    depends_on: [mongo]
    networks: [appnet]

networks:
  appnet:
    driver: bridge

volumes:
  mongo_data:
```

**Ключевые уроки примера:**

- **Разбиение по ответственности:** сборщик данных, БД, веб-отображение, админка — **отдельные сервисы**, а не один контейнер «всё в одном».
- **Связь по имени сервиса:** `web` и `collector` обращаются к базе по хосту `mongo` (не по IP) — в общей compose-сети работает DNS.
- **`depends_on`** задаёт порядок старта (сначала `mongo`, потом зависящие). *(Важно: `depends_on` ждёт **запуска** контейнера, а не готовности БД принимать соединения — для этого нужен `healthcheck` с `condition: service_healthy`.)*
- **volume для БД** (`mongo_data`) — данные не теряются при пересоздании.
- **Admin-UI контейнером:** `mongo-express` для Mongo — как `adminer` для SQL или `pgAdmin` для Postgres: подняли контейнером, смотрим данные в браузере.

## Часть C. Мелкие новые практические детали

- **Готовые admin-UI образы:** `mongo-express` (Mongo), `adminer` (универсальный SQL), `pgadmin4` (Postgres) — поднимаются контейнером, дают веб-интерфейс к БД.
- **Bind-mount не только кода, но и конфига** (`nginx.conf`, `default.conf`) — правишь конфиг на хосте, перезапустил контейнер, изменения применились без пересборки.
- **`docker compose up`** (в foreground, логи в терминале) vs **`docker compose up -d`** (фоном); Compose **сам создаёт общую сеть**; `docker compose down` её удаляет.

## Итог дополнения 5

Из практического курса нового немного (база уже покрыта): главное — **nginx как reverse proxy** (`proxy_pass`, `upstream`, статика на nginx, балансировка реплик) и паттерн **многосервисной сборки** (сборщик данных + БД + веб + админка, связь по имени, `depends_on`, volume для БД, admin-UI контейнером). Плюс нюанс, что `depends_on` ждёт старта, а не готовности сервиса — для готовности нужен `healthcheck`.
